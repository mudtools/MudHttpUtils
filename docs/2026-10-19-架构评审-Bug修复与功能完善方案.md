# Mud.HttpUtils Bug 修复与功能完善方案

- 日期：2026-10-19
- 依据：《Mud.HttpUtils 架构评审报告》（2026-10-19，以 MudFeishu / MudWechat 两个下游实况为证据）
- 范围：`Mud.HttpUtils` 上游全部工程（Abstractions / Attributes / Client / Resilience / Generator / CodeFixes / OpenTelemetry / Newtonsoft.Json / Xml / Redis / Tools / Tests）
- 目标：修复已实证缺陷 → 补齐被下游绕过的扩展点 → 收敛过度配置面 → 建立"上游变更到下游"的传导治理

---

## 1. 背景与评审结论摘要

两个下游 SDK（`D:/Repos/MudFeishu/FeishuV3`、`D:/Repos/Mud.Wechat`）均以 PackageReference 钉死 3.0.8、无 ProjectReference，其每一处自建/绕行都是上游架构问题的可观测信号。评审确认的核心事实：

1. **依赖方向干净**：所有工程单向指向 Abstractions，无回环、无旁路；生成期与运行期职责切分清晰（URL 模板生成期、根地址运行期；错误截断为单一事实源 `Mud.HttpUtils.Abstractions/HttpClient/Execution/HttpExecutionConstants.cs:32`）。
2. **三类问题已被下游实证**：
   - 上游缺陷：桥接器读路径不降级、SSRF 严格模式默认开但无空名单诊断、`TokenRecoveryEnhancedClient.WithBaseAddress` 能力丢失（工作树已修、3.0.8 包未含）；
   - 上游扩展点缺失/形状不匹配：`IHttpClientResolver` 两下游均未采用、生成器豁免通道无目录/成员粒度、配置绑定被接口类型扩展点污染；
   - 修复未传导：3.0.4 已补的多判定器集合与纯 DTO 投影，下游注释与适配仍停留在旧认知。
3. **过度设计集中在三处**：咨询性诊断默认 Warning 制造屏蔽文化（微信 8 处目录级 `.editorconfig` 实证）、15+ 注册入口无决策树、个别预留扩展点零消费。

本方案按"正确性与安全 → 诊断与配置面 → 扩展点与功能 → 演进治理"分四批实施，每项给出问题定位、最小代码示例、影响面、验收标准。

---

## 2. 修复原则

1. **最小破坏**：修复正确性缺陷时，行为变更仅在"旧行为已被下游实证为缺陷"时引入，并在发布说明中单列。
2. **单一事实源**：新能力优先上收为契约（Abstractions），实现落在 Client/Resilience/Generator，禁止在适配包复制逻辑。
3. **下游可验证**：每项修复必须能在两个下游的守卫/冒烟测试中观测到效果（解除某处自建补偿或消除某处屏蔽）。
4. **AOT 优先**：任何新增配置/序列化面必须先过"配置绑定源生成器 + IL2026/IL3050 零新增"门禁。
5. **语义化表述**：方案与代码注释不使用内部追踪编号，诊断 ID 与公共 API 名除外。

## 4. 批次 A：正确性与安全缺陷（P0，目标 3.0.9）

### A-1 令牌存储桥接器读路径故障降级

**问题定位**：`Mud.HttpUtils.Client/TokenManager/Caching/TokenStoreBackedTokenCache.cs:577-613`
读穿透路径（租户 `:600-601`、用户 `:594-595`）无异常捕获；写路径已有补偿队列降级（`:619-651`）。存储抖动时读故障直接抛给业务调用方，违背"未命中 → 回落 API 刷新"的设计意图。

**下游证据**：`D:/Repos/MudFeishu/FeishuV3/Mud.Feishu.Abstractions/Authentication/TokenManager/PurgeGateTokenStoreDecorator.cs:22-24`——「上游桥接器 GetAsync 不捕获 store 异常，若不在此降级，存储抖动将从『回落 API 刷新』恶化为『把异常抛给业务调用方』」。

**方案**：读路径按"未命中"降级，与写路径对齐；新增读失败计数与日志事件（取当前未占用 EventId）：

```csharp
else
{
    var storeKey = MapStoreKey(key);
    try
    {
        access = await _store!.GetAccessTokenAsync(storeKey, cancellationToken).ConfigureAwait(false);
        refresh = await _store.GetRefreshTokenAsync(storeKey, cancellationToken).ConfigureAwait(false);
    }
    catch (Exception ex) when (ex is not OperationCanceledException)
    {
        // 读故障按「未命中」降级：回落 API 刷新，不把存储抖动抛给业务调用方（与写路径补偿队列对齐）。
        Interlocked.Increment(ref _readThroughFailures);
        MudHttpClientLog.TokenStoreReadThroughFailed(_logger, storeKey, ex);
        return null;
    }
}
```

用户维度分支（`:594-595`）同构处理。取消异常保持原样上抛（与写路径过滤器一致）。

**影响面与兼容性**：行为变更——此前依赖读异常传播的宿主将改为拿到"未命中"。该行为已被下游实证为缺陷，按原则 1 接受，发布说明单列。`_readThroughFailures` 暴露为公共只读计数（与 `WriteThroughFailures` 同形态，需登记 PublicAPI 基线）。

**验收标准**：
- 新增单测：store 读抛非取消异常 ⇒ `GetAsync` 返回 null、记 Warning、计数 +1；取消异常原样传播；
- 既有桥接器契约测试全绿；
- 飞书侧冒烟：`PurgeGateTokenStoreDecorator` 的读降级用例在"移除装饰器"后仍成立（验证上游接管）。

**涉及工程**：Client、Client.Tests、Docs（README 令牌存储选型指南补"读降级"口径）。

### A-2 SSRF 严格模式空白名单启动诊断

**问题定位**：`Mud.HttpUtils.Client/ServiceCollectionExtensions.cs:75-81`（严格模式判定"默认严格"）、`:1293-1305`（白名单种子化）

**下游证据**：`D:/Repos/Mud.Wechat/Tests/Mud.Wechat.Pay.Tests/Transport/WechatPayTransportPipelineTests.cs:243-277`——回归锁注释记录「纯支付宿主的每一笔请求都会被组件的连接期 SSRF 严格模式拦下」；登记端备注见 `D:/Repos/Mud.Wechat/Src/Core/Mud.Wechat.Abstractions/TokenManager/WechatTokenRecoveryRegistration.cs:42-47`。

**方案**：在 `AddMudHttpClientInfrastructure` 的白名单种子化之后增加空名单 + 严格模式组合检测：

```csharp
// 种子化之后：存在严格模式客户端且全局白名单为空时给出启动期提示（fail-closed 默认值的可观测性兜底）
private static void WarnIfStrictModeWithoutAllowlist(
    IServiceProvider sp, IReadOnlyList<string> clientNames, EnhancedHttpClientOptions options)
{
    if (options.Logger is null || UrlValidator.GetAllowedDomains().Count > 0)
        return;

    var strictClients = clientNames.Where(name => IsStrictModeForClient(sp, name)).ToList();
    if (strictClients.Count > 0)
        MudHttpClientLog.SsrfStrictModeWithoutAllowlist(
            options.Logger, string.Join(", ", strictClients));
}
```

日志消息需指明三个登记入口：`MudHttpClients:AllowedDomains` 配置节、`UrlValidator.AddAllowedDomain`（多产品线并存必须走追加语义）、`IUrlValidator` 容器级实现。

**影响面与兼容性**：纯增量（仅新增 Warning 日志与 EventId），无行为变更。

**验收标准**：
- 集成测试：严格模式客户端 + 空白名单 ⇒ 记 Warning 且消息含客户端名与入口指引；任一口径登记后 ⇒ 不记；
- 微信侧回归：`WechatPayTransportPipelineTests` 既有断言保持（下游修复不动），上游新增用例覆盖同名场景。

**涉及工程**：Client、Client.Tests / Integration.Tests、Docs（README SSRF 章节补"每宿主必须登记白名单" checklist）。

### B-2 令牌恢复配置入口 AOT 化

**问题定位**：`Mud.HttpUtils.Client/ServiceCollectionExtensions.cs:1833-1858`——官方配置绑定入口自身带 `[RequiresUnreferencedCode]`/`[RequiresDynamicCode]`，内部走 `services.Configure<TokenRecoveryOptions>(section)` 反射绑定；而 `TokenRecoveryOptions.TokenInvalidationDetector` 为接口类型属性，下游启用配置绑定源生成器后直接绑定即产出不可抑制的诊断。

**下游证据**：`D:/Repos/MudFeishu/FeishuV3/Mud.Feishu.Abstractions/Extensions/FeishuServiceCollectionExtensions.cs:325-354`——自建 DTO 投影 + 逐字段 `Apply` + 手工 `ConfigurationChangeTokenSource`；决策档案第四节同因。

**方案（复审修订：补热更新闭环）**：官方入口内部改走纯 DTO 投影（`Mud.HttpUtils.Abstractions/TokenManager/Recovery/TokenRecoveryConfiguration.cs:34` + `TokenRecoveryOptionsExtensions.Apply` 已存在），对外去掉 AOT 标注（反射宿主在库内以带理由的抑制收敛，诊断不再流向下游编译单元）；同时补一个无标注的委托式重载：

```csharp
public static IServiceCollection AddMudHttpTokenRecovery(
    this IServiceCollection services, Action<TokenRecoveryOptions> configure) // 无 Requires 标注：AOT 安全入口
{
    services.Configure(configure);
    services.TryAddSingleton<IValidateOptions<TokenRecoveryOptions>, TokenRecoveryOptionsValidator>();
    return services;
}

public static IServiceCollection AddMudHttpTokenRecoveryFromConfiguration( // 去掉 Requires 标注
    this IServiceCollection services, IConfiguration configuration, string sectionPath = TokenRecoveryOptions.SectionName)
{
    // 守卫省略…
    services.AddOptions<TokenRecoveryOptions>();
    services.Configure<TokenRecoveryOptions>(o =>
    {
        var dto = configuration.GetSection(sectionPath).Get<TokenRecoveryConfiguration>(); // 纯 DTO：绑定源生成器完整支持
        dto?.Apply(o);
    });
    // 【复审修订】显式挂配置变更令牌源：Configure(Action) 自身不带 reload token，
    // 不挂则改配置节不会触发委托重跑 ⇒ 热更新静默丢失（原 IConfigurationSection 重载由
    // NamedConfigureFromConfigurationOptions 内部挂载，语义等价补齐）。
    services.AddSingleton<IOptionsChangeTokenSource<TokenRecoveryOptions>>(
        _ => new ConfigurationChangeTokenSource<TokenRecoveryOptions>(Options.DefaultName, configuration));
    services.TryAddSingleton<IValidateOptions<TokenRecoveryOptions>, TokenRecoveryOptionsValidator>();
    services.TryAddSingleton(resolver => resolver.GetRequiredService<IOptions<TokenRecoveryOptions>>().Value);
    return services;
}
```

`Get<T>()` 的 BCL 反射标注在库内以带理由的抑制收敛（Client 已有同类内部抑制先例，如 `ServiceCollectionExtensions.cs` 配置绑定处的 ConfigurationBinder IL2026/IL3050 抑制），不流向调用方。

**影响面与兼容性**：绑定语义不变（DTO 与选项基元成员逐字段同名同默认值，非法值仍经 setter 校验抛错）；热更新语义与原 `IConfigurationSection` 重载等价（变更令牌源显式补齐）；下游从"必须自建投影"变为"可直接用官方入口"。

**验收标准（复审修订）**：
- 配置绑定测试全绿（含热更新：改配置节 ⇒ `IOptionsMonitor.CurrentValue` 反映新值——该用例同时守护变更令牌源未被遗漏）；
- AOT 严格门禁零新增 IL2026/IL3050；
- 飞书侧验证：改用官方入口后其编译单元 SYSLIB1100/1101 消失、热更新用例保持（下游动作，见第 11 节）。

**涉及工程**：Client、Abstractions（如需补 Apply 覆盖）、Client.Tests、Docs（README 令牌恢复章节补 AOT 口径）。

**问题**：破坏性行为变更（2.0.9 一批）与新增默认开启诊断（3.0.4 的 AOT 补漏）均迫使下游付出适配代价，上游无影响清单产出流程。

### 13.2 系统架构师视角（前后端逻辑闭环 / 架构合理性 / 兼容性）

1. **依赖方向**：抽样验证 Abstractions ← Attributes/Client/Generator 单向依赖，无回环、无旁路；生成期/运行期职责切分清晰（与上游评审报告结论一致）。
2. **B-1 第二部分的缓存模型冲突（最关键发现）**：增量生成器的 per-interface 节点输入为三元组（`InterfaceModel` 指纹、全局 `GeneratorConfigSnapshot`、全局 `BuildSalt`）。`.editorconfig` 目录键变更不改变任何一个输入 ⇒ 节点 `Cached` ⇒ `ProcessInterface` 输出回调不重跑。原方案"回调内读树值 + 盐含树键"双重不可行（回调不重跑；`BuildSalt` 只收 `GlobalOptions`，目录键从不出现在其中——这正是 `MudHttpAnalyzerConfig.cs:63-67`  remarks 自证的限制）。**根治唯一合理形态是把 018 上报迁至分析器**：本仓已有两次同向先例（MUD005 由分析器承载；AOT004/5/7 迁出生成管道的理由同为"配置变更不失效接口指纹"，见 `HttpInvokeClassSourceGenerator.cs:143-148`）。分析器随编译变化自然重算，且 `IsTokenManagerKeyInferenceSuppressed(global, tree)` 已支持树粒度。
3. **B-2 热更新闭环缺口**：原方案用 `services.Configure<T>(Action)` 承载 DTO 投影，但 `Configure(Action)` 不挂 `IOptionsChangeTokenSource` ⇒ appsettings 变更不会触发委托重跑 ⇒ 热更新静默丢失（而原 `IConfigurationSection` 重载由 M.E.Options 内部挂 token）。修订为显式注册 `ConfigurationChangeTokenSource<TokenRecoveryOptions>`，闭环补齐。

6. **C-2 兼容性**：`IAsyncHttpContentSerializer : IHttpContentSerializer` 的继承形状使既有实现零改动；运行期探测分支与 `ISynchronousContentSerializer` fast-path 同范式；生成代码不感知（内容构造在运行期完成），AOT 面无新增反射。
7. **C-6 架构澄清**：生成入口的"基础设施所有权"已收敛至 `AddMudHttpClient`（MT-14/BC-21，生成器注释自证）；再让生成器发射 TryAdd 会造成所有权双写。决策树文档 + 陈旧注释更正是正确收敛方向。
8. **版本纪律**：3.1.0 不复用、下一 minor 取 3.2.0 的决策合理；A 批补丁快速通道（3.0.9）与 B-1 第二部分的诊断位置变更（单独发版 + 影响清单）风险隔离充分。
