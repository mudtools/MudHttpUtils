## 1. 背景与目标

### 1.1 背景

Mud.HttpUtils 是以 NuGet 分发的**声明式 HTTP 客户端框架**：编译期由 Roslyn 源生成器产出接口实现，运行时经
`业务服务 → 生成代码 → IHttpRequestExecutor → Token/加密/拦截器 → IResiliencePolicyResolver → ResilientHttpClient → EnhancedHttpClient → System.Net.Http.HttpClient`
装饰器链执行。框架缺陷会**放大到所有下游使用者**，因此对正确性、线程安全、生命周期安全、AOT 兼容性与 API 契约稳定性要求极高。

目标框架：`netstandard2.0; net6.0; net8.0; net10.0`（多目标，条件编译分支必须行为一致）。

### 1.2 审查结论回顾

最近一轮针对 HttpClient 相关能力的 12 维度审查共发现 **29 项问题**：

- 🔴 严重 5 项（#1 #2 #3 #4 #5）
- 🟠 重要 13 项
- 🟡 一般 8 项
- 🔵 建议 2 项（含 1 项未实测确认项）

其中 **7 项列为阻塞合并**（#1 #2 #3 #4 #5 #6 #16）。

### 1.3 方案目标

| 目标 | 衡量口径 |
|------|----------|
| G1 消除资源耗尽风险 | 错误响应体、克隆请求体在任何 TFM 下均有**字节级**上限；新增 OOM 回归用例 |
| G2 消除敏感信息泄露 | Span tag / 日志 / 诊断事件中的 URL 默认脱敏；`ApiException.Content` 与 `RequestContent` 默认受 `MaxExceptionContentLength` 约束 |
| G3 消除并发数据竞争 | `UrlValidator` 白名单、`MemoryHttpResponseCache`、`MemoryTokenStore` 三处可变共享状态全部改为原子替换 |
| G4 拉齐重试语义 | 重试抖动、幂等性防护、TFM 判定三处不一致全部收敛 |
| G5 指标可控 | 移除所有高基数指标 tag，高基数信息仅进 Span 事件 |
| G6 契约稳定 | 全部新增公共 API 同步 4 个 TFM 的 `PublicAPI.Unshipped.txt`；行为变更进 CHANGELOG |

## 3. 修复原则

### P-1 修复必须落在"读取边界"，而不是"事后截断"

`MaxExceptionContentLength`、`MaxCloneContentSize` 这类上限**必须在 I/O 层生效**。
`TruncateErrorContent`（`DefaultHttpRequestExecutor.cs:666`）在字符串读完后再截断，只省了内存中的**一份副本**，
并未阻止 OOM —— 这是 #1 / #9 的根因，也是本方案最重要的设计约束。

### P-2 优先"原子替换"而非"加锁"

三处并发问题（#4 白名单、#14 缓存条目、#15 令牌条目）统一采用
**不可变条目 + 引用原子替换**（`Volatile.Write` / `TryUpdate` / `ImmutableHashSet` 快照交换），
避免在热路径引入锁竞争，也更易于推理。

### P-3 安全默认值，但保留运维开关

项目未发布，无兼容包袱：脱敏、截断、幂等防护**默认开启即一步到位**。仍保留少量显式开关
（Options / 请求属性标记），目的不是兼容旧行为，而是**运维便利**（如排障时临时查看完整 URL）。

### P-4 不破坏 `IResiliencePolicyProvider` / `IEnhancedHttpClient` 等公共契约

#12 的幂等防护若改成"给 Provider 接口加参数"就是破坏性变更。
本方案改为**在装饰器层用请求属性标记决策**（沿用 `SkipResilience` 的既有模式），接口零变更。
（未发布意味着其实可以改签名，但保持接口稳定能避免 Generator/Client/Resilience 三包联动改动，成本更低。）

### P-5 多 TFM 行为一致优先于"某个 TFM 更好"

`netstandard2.0` 缺少 `VersionPolicy`、`Options`、`AesGcm` 等能力时，
要么用 `#if` 提供**语义等价**实现（如 HMAC 替代 GCM），要么显式声明降级并在诊断中提示，
**禁止静默降级**。`ShouldRetry`（#20）当前的字符串猜测即反例。

### P-6 每个修复 = 一个可回滚 PR + 至少一条回归用例

## 6. 方案编制与验证过程中的新增发现

原方案编制时发现 N-1 ~ N-3；2026-09-11 逐项核对代码后，又确认 **N-4 ~ N-6** 三项原方案未覆盖的问题。

### N-1 🟠 `MaxExceptionContentLength` 默认值在两条路径上不一致，且 XML 文档与实现不符

- `EnhancedHttpClient.cs:1744`：`var maxLen = _maxExceptionContentLength ?? MaxErrorContentLength;`（常量 10240）
  → **默认即截断到 10240**。
- `DefaultHttpRequestExecutor.cs:666-671`：`TruncateErrorContent(errorContent, _maxExceptionContentLength)`
  → `_maxExceptionContentLength` 默认 null（构造参数 `:50`），`TruncateErrorContent` 遇 null **不截断** → **默认无限制**。
- `EnhancedHttpClientOptions.cs:82` XML 文档写"默认为 null（无限制）"，与 `EnhancedHttpClient` 的实际行为**相反**。

**影响**：同一配置项在"内置方法路径"与"生成代码路径"默认行为不同。

**修复**：统一默认值为 10240（两路径一致），抽共享常量；明确 `0` / 负数 = 不限制。归入 **M1**。

### N-2 🟡 成功响应体同样无上限（#1 的对称面）

`DefaultHttpRequestExecutor.SendAndDeserializeAsync:136` 与 `DownloadAsync` 对**成功**响应也全量读入内存。
修复 #1 时**不能**一并截断，否则破坏反序列化与下载语义。

**处理**：M2 中增加**可选**的 `MaxSuccessResponseBytes` 守卫（默认 `0` = 不限制，仅记录指标；设为正数则超限抛异常），
并对 `DownloadAsync`（`byte[]`）建议文档引导使用 `DownloadLargeAsync`（流式落盘）。详见 [02 §N-2](./02-P1-重要修复方案.md)。

### N-3 🟡 `ProgressableStreamContent` 与重试克隆组合时进度语义失真

首次尝试即克隆，克隆调用 `request.Content.ReadAsByteArrayAsync()`；`ProgressableStreamContent` 基类
`HttpContent` 经 `SerializeToStreamAsync` 把内容先缓冲到内存，`IProgress<long>` 在**尚未发出任何网络字节时**
跑满 100%。与 #19 合并处理（首次不克隆），见 [02 §12](./02-P1-重要修复方案.md)。

### N-4 🟠 方法级弹性路径完全绕过 `ResilientHttpClient`（原方案结构性遗漏）

`DefaultHttpRequestExecutor.ExecuteWithOrchestrationAsync:589-639` 通过 `SetSkipResilienceFlag`
使全局装饰器直通，方法级 `[Retry]`/`[Timeout]`/`[CircuitBreaker]` 策略在
`ResiliencePolicyResolver.ResolvePolicyWrapper:73-94` 内部执行（含每次尝试克隆请求，`:79`）。

**影响原方案的正确性**：

1. **#10**（超时异常包装）：原方案只在 `ResilientHttpClient` 出口包装 `TimeoutRejectedException` ——
   方法级路径的该异常仍会裸抛，修复不完整。正确做法：包装放在**两条路径共用的下层**
   `EnhancedHttpClient.ExecuteHttpRequestCoreAsync`（见 02 册 #10 修订）。
2. **#12**（幂等防护）：原方案只改 `ResilientHttpClient.ShouldSkipRetry` —— 方法级 `[Retry]` 的 POST
   仍会被重试。幂等判定必须下沉到**策略构建层**（`PollyResiliencePolicyProvider`），见 02 册 #12 修订。
3. **#19/N-3**（首次不克隆）：原方案只改 `ResilientHttpClient.ExecuteWithCloneAsync` ——
   `ResiliencePolicyResolver:79` 与流式路径 `ResilientHttpClient.cs:221/259` 首次仍克隆。三处必须同步改。

### N-5 🟡 `ExecuteWithoutCloneAsync` 便捷方法与重试组合存在"请求已发送"隐患

`ResilientHttpClient.cs:185-194`：`GetAsync`/`PostAsJsonAsync` 等便捷方法走
`GetCombinedPolicy`（含重试），但**不克隆请求**（`:192` 直接 `executeFunc(_innerClient, ct)`）。
便捷方法内部每次调用都会 `new HttpRequestMessage`（`EnhancedHttpClient.SendJsonWithBodyAsync:938`），
重试时 re-invoke executeFunc 会重建请求，因此**侥幸可用**；但 `request` 形参在该路径未被消费，
方法级 `ApplyRequestConfig` 类配置（`Version` 等）在该路径丢失（仅影响手动构造 `HttpRequestMessage`
再走 `SendAsync` 的场景——那走 K3 不受影响）。**处理**：并入 #19 一并梳理，便捷方法保持现状
（每次重建请求，语义安全），在 M2 补一条回归用例锁定该行为。

### N-6 🟡 `GetCombinedPolicy` 的组合顺序：重试在熔断之外

`PollyResiliencePolicyProvider.BuildMethodPolicy:500`：`retryPolicy.WrapAsync(policy)` →
重试包装熔断+超时。这意味着**熔断打开时抛 `BrokenCircuitException`，外层重试会捕获并静默重试**
（`BrokenCircuitException` 不在 `Handle`/`Or` 列表中，实际不会被重试 —— 复核确认：
`Handle<HttpRequestException>` + `Or<TimeoutRejectedException>` + `Or<TaskCanceledException>` 均不含
`BrokenCircuitException`，因此熔断打开会**直接失败**，语义正确）。结论：**非问题**，无需修复，
记录此复核结论防止后续误判。
