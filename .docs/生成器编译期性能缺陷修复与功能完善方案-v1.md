### 1.3 结论定性

- **HTTP 源码生成管线（FAWM + 逐接口注册点 + 值相等指纹）增量设计健康，不是瓶颈。**
- **瓶颈集中在随包分发的 AOT 诊断分析器**：`RegisterCompilationAction` 非增量 + 全语法树符号绑定 + 全引用程序集类型遍历，在每个项目 × 每个 TFM × 每次编译全量重跑。
- 成本放大机制：
  1. **多 TFM ×4**：netstandard2.0 / net6.0 编译不产出 AOT 产物，却仍支付扫描成本；
  2. **IDE 设计时构建**：CWT 缓存以 `Compilation` 为键，每次击键产生新 Compilation ⇒ 缓存永不命中，全量重算（输入卡顿主因）；
  3. **无关项目照付**：纯 DTO 项目（无任何 HTTP 接口）支付了 40% 的分析器耗时。

## 三、关键技术设计

> 设计纪律（对齐既有工程约定）：
> - 编译级缓存一律 `ConditionalWeakTable<Compilation, ...>` + `Lazy`/`StrongBox`（参照 `HasNet8OrGreaterDefine` 现行实现）；
> - 跨 Compilation 复用的缓存**不得**存放 `ISymbol`（符号身份不可跨编译比较），一律存元数据名字符串；
> - 所有预筛必须**保守不漏报**（宁可误触发全扫，不可漏触发）；
> - 诊断 ID / 级别 / 消息 / 位置零变更（诊断行为契约不变）。

### F-1（修 B-1）：覆盖集合两级缓存 —— 引用程序集级静态缓存 + Compilation 级聚合

**目标**：`ComputeCoveredTypes` 的「全引用程序集递归」只在**首次见到某引用程序集**时执行一次，IDE 稳态与多 TFM 编译近零成本。

**设计**：

1. 新增静态缓存 `ConcurrentDictionary<string, HashSet<string>>`，键为被引用程序集显示名（统一取 `reference.Display ?? asm.Identity.GetDisplayName()`，含名称+版本+公钥），值为该程序集贡献的覆盖类型**归一化全名**集合。
2. 仅缓存 `PortableExecutableReference` 来源的程序集：`CompilationReference`（IDE 中的项目引用，被引用项目随击键持续变化）**不入静态缓存**，回落到现行按 Compilation 扫描（项目引用数量少、可控）。显式假设：同一元数据程序集在不同 Compilation 中的符号虽身份不同，但**显示名恒定**，故名字化比较安全——这也是缓存值不能存 `ISymbol` 的原因。
   **[评审修正·P0 正确性]** 原稿称"元数据编译期不可变、静态缓存永不失效"不成立：常驻编译服务（VBCSCompiler / IDE）生命周期内，ProjectReference 在 CLI 下即解析为 PE 路径引用，兄弟项目重编后**同一路径、同一 Display、同一 AssemblyIdentity 的 PE 内容可变**，静态缓存会返回陈旧覆盖集合 → AOT004/005/006 误报/漏报（AotStrictMode 下误报即阻断构建）。**缓存键必须追加 MVID**（`IModuleSymbol.GetModuleVersionId()`，元数据读取、O(1)）：`key = $"{reference.Display}|{module.GetModuleVersionId():N}"`。内容变 ⇒ MVID 变 ⇒ 天然未命中重扫；同内容重复引用 ⇒ 命中零成本。
3. **名字键生成（关键正确性点，评审修正）**：原稿"一律先取 `type.OriginalDefinition` 归一"**不可采纳**——OriginalDefinition 会把构造泛型坍缩到定义（`List<Foo>` 与 `List<Bar>` 同键），破坏现行 `IsCovered` 以 `SymbolEqualityComparer` 区分构造泛型实例的语义，造成"误判已覆盖 → 漏报诊断"。正确做法：
   - 名字键 = 符号**原样** `ToDisplayString(SymbolDisplayFormat.FullyQualifiedFormat)`，写入（Context 侧 `[JsonSerializable]` 参数）与查询（DTO 侧）走**同一** `GetCoverageKey(ITypeSymbol)` 工具方法，杜绝两套格式漂移；
   - 开放泛型语义**保留在查询侧**：现行 `IsCovered` 对泛型定义做 `ConstructUnboundGenericType()` 后再查——该逻辑原样迁移（unbound 符号的显示名写入/查询两侧恒同）；
   - 元组元素名问题：`(int a, string)` 与 `(int, string)` 符号相等但显示名不同 → 误报。名字键生成的 display format 需附加 `SymbolDisplayMiscellaneousOptions.ExpandValueTuple`，把元组展开为 `ValueTuple<...>` 消除元素名差异；
   - Nullable/集合解包语义（`IsCovered` 现实现）原样保留，只是解包后的成员查询从符号 Contains 改为名字 Contains。
4. 本地 Context 部分（`GetLocalContexts`）仍按 Compilation 缓存，结果并入聚合集。

**核心结构（示意）**：

```csharp
// 跨编译静态缓存：元数据程序集 → 覆盖类型全名集合（元数据不可变，永不失效）
private static readonly ConcurrentDictionary<string, HashSet<string>> _assemblyCoveredNames = new(StringComparer.Ordinal);

private static HashSet<string> ComputeCoveredTypes(Compilation compilation)
{
    var result = new HashSet<string>(StringComparer.Ordinal);
    // ① 本地 Context（按 Compilation 缓存，现行逻辑）
    foreach (var localContext in GetLocalContexts(compilation))
        CollectFromContextType(localContext, jsonSerializableAttr, result);

    // ② 引用程序集：元数据引用走静态缓存；CompilationReference 回落全扫
    foreach (var reference in compilation.References)
    {
        if (reference is CompilationReference compRef)
        {
            CollectCoveredNamesFromNamespace(compRef.Compilation.Assembly.GlobalNamespace, ..., result);
            continue;
        }
        var asm = compilation.GetAssemblyOrModuleSymbol(reference) as IAssemblySymbol;
        if (asm is null) continue;
        if (reference is PortableExecutableReference)
        {
            // [评审修正] 键 = Display + MVID：PE 可在常驻编译服务内被原地重建，仅靠 Display 会陈旧
            var cacheKey = (reference.Display ?? asm.Identity.GetDisplayName()) + "|" + asm.Modules[0].GetModuleVersionId().ToString("N");
            var names = _assemblyCoveredNames.GetOrAdd(
                cacheKey,
                _ => ScanAssemblyCoveredNames(asm, ...));   // 仅首次付费
            result.UnionWith(names);
        }
        else
        {
            ScanAssemblyCoveredNames(asm, ..., result);     // 防御路径：无 MVID 可用时不入缓存
        }
    }
    return result;
}
```

**正确性要点**：
- 缓存值只读共享（与既有「覆盖集合按 Compilation 缓存」修复的纪律一致）；静态缓存值**不得**持有 `ISymbol`/`Compilation`/`MetadataReference`（生命周期纪律）；
- 缓存键与写入/比较的名字生成必须走同一工具方法（`GetCoverageKey`），避免两套格式漂移；
- 诊断输出中 `TypeProps` 仍基于 `INamedTypeSymbol` 生成（比较用名集合，输出用符号），行为不变；
- **[评审补充]** 静态缓存内存驻留为已知权衡：条目数 ≈ 引用程序集数 × 历史版本数（MVID 键控），值为字符串集合，长期 IDE 会话可接受，本期不做 LRU/清理。

### F-2（修 B-2 / B-4）：三分析器入口改造 —— 语法级预筛前移，保留编译级上报架构

**总原则**：把「便宜的否决」放在「昂贵的绑定」之前。**架构不换**（保留 `RegisterCompilationAction` + 编译级汇总上报）：AOT 诊断依赖全编译视野（覆盖集合含引用程序集），改 `RegisterSymbolAction` 会失去可靠汇总点、且 `GeneratedCodeAnalysisFlags.None` 与符号动作组合会改变生成代码中的诊断行为——与「诊断契约零变更」冲突。全量符号化/FAWM 化迁移登记为长期项（见 §六）。

**F-2a 语法预筛器（新增 `SyntaxPrefilter` 静态帮助类，按 SyntaxTree CWT 缓存）**：

```csharp
// 保守 token 级扫描：任何 SyntaxTree 的标识符 token 包含目标名 → 疑似存在，进入精确路径。
// 未命中（绝大多数项目）→ 各分析器直接返回，成本 O(文本 token)。
internal static bool MayContain(Compilation compilation, string marker1, string marker2 = null)
```

- **[评审修正·缓存粒度]** 原稿"按 Compilation CWT 缓存"与 §1.3 的核心结论（「CWT 以 Compilation 为键 ⇒ IDE 每击键新 Compilation ⇒ 永不命中」）自相矛盾。修正为**按 `SyntaxTree` 做 CWT 缓存**（`ConditionalWeakTable<SyntaxTree, ...>`）：语法树对象跨 Compilation 复用（文件未改动时树恒定），IDE 稳态下未改动文件的扫描结果**真正命中**；Compilation 层仅做各树结果的 O(树数) 布尔聚合。F-4 的 ProfileDiscovery 预筛同受益。

- AOT004/005 预筛标记：`HttpClientApi` / `HttpClientApiAttribute`；
- AOT006 预筛标记：`HttpJsonSerializable` / `HttpJsonSerializableAttribute`；
- AOT007 预筛标记：`HttpClientApi`（其分析对象就是 HTTP 接口方法）；
- Context 探测（`HasLocalJsonSerializerContext`）预筛标记：`JsonSerializerContext`。

token 扫描保守性：别名（`using JSC = System.Text.Json.Serialization.JsonSerializerContext;`）文件内仍含 `JsonSerializerContext` 标识符，不会漏报；生成文件同样被扫描，语义不变。

**F-2b AOT006 的 `GetLocalAnnotatedTypes`：符号绑定前加语法级属性名预检**：

保留现有「全类型枚举」结构，但在调用 `GetDeclaredSymbol`（昂贵）之前先做**纯语法属性名预检**：

```csharp
foreach (var typeDecl in root.DescendantNodes().OfType<TypeDeclarationSyntax>())
{
    // 便宜：仅比对 AttributeLists 的名称文本，不含目标属性名 → 跳过绑定
    if (!MayHaveAttribute(typeDecl, "HttpJsonSerializable", "HttpJsonSerializableAttribute")) continue;
    var symbol = semanticModel.GetDeclaredSymbol(typeDecl) as INamedTypeSymbol;   // 仅疑似类型才付费
    ...
}
```

对 2000+ 类型的 DataModels 项目，>99% 的类型在文本层即被跳过，`GetDeclaredSymbol` 调用量从「全部类型」降到「疑似标注类型」。诊断输出（含顺序、去重、`GeneratedCodeAnalysisFlags.None` 行为）与现状逐条一致——这是选择「预检」而非「RegisterSymbolAction 重构」的原因。

**F-2c AOT004/005 与 AOT007 的接口遍历加预筛与早期否决**：

- `AnalyzeCore` 调整后的门控顺序（**不新增 TFM 门控**——给 AOT004/005 加 `HasNet8OrGreaterDefine` 会改变 netstandard2.0/net6.0（含手写 Context 场景）的诊断输出，与 G3 契约冲突，明确不做）：
  1. `SyntaxPrefilter.MayContain(compilation, "HttpClientApi")` → 未命中直接返回（无 HTTP 接口的项目零成本）；
  2. **[评审补充]** `GetTypeByMetadataName(HttpClientApiAttributeFullName) == null` → 直接返回：属性符号解析是 O(1) 元数据查找，比任何扫描都便宜；现状代码在 `CollectCoveredTypes` **之后**才做此检查（AotDtoCoverageAnalyzer.cs L149），无 Attributes 引用的纯 Context 项目白付全引用程序集扫描——免费优化，一并前移；
  3. `HasLocalJsonSerializerContext`（token 预筛后才做）→ 现行门控语义不变；
  4. `CollectCoveredTypes`（F-1 后近零稳态成本）；
  5. 全树接口遍历（此时项目确认有 HTTP 接口 + Context，成本必然产生价值）。
- 遍历内部把「每接口 `GetAttributes().Any(SymbolEqualityComparer...)`」改为先比对属性名字符串（`a.AttributeClass?.Name == "HttpClientApiAttribute"`）再走精确比较，减少全量符号比较。
- AOT007 同款处理：入口先 `MayContain(compilation, "HttpClientApi")`，保留 `AotModeResolver` 三态判定次序不变。

### F-3（修 B-3）：AOT006 门控顺序对调

`AnalyzeHttpJsonSerializableCoverageCore` 调整为：

```csharp
if (!HasNet8OrGreaterDefine(compilation)) return Empty;   // ① 最便宜（CWT+StrongBox 已缓存）
var annotatedTypes = GetLocalAnnotatedTypes(...);           // ② 符号动作/预筛后才收集
if (annotatedTypes.Count == 0) return Empty;

```

行为不变（net8.0+ 路径结果一致），netstandard2.0 / net6.0 编译成本直接归零。

### F-6（修 B-7）：DEBUG 语法验证开关化

## 八、多维评审记录（2026-10-13）

> 评审基线：本方案 v1 + 仓库当前代码实测核对（AotDtoCoverageAnalyzer.cs / AotXmlRejectionAnalyzer.cs / 三分析器入口 / SdkToolProfileModel.cs（ProfileDiscovery）/ TransitiveCodeGenerator.cs / build props / 既有测试套件）。修正项已并入正文，此处留评审结论与证据。

### 8.1 高级程序员视角

**问题真实性：全部 7 项缺陷在代码中逐一坐实**（B-1 引用程序集递归扫描 `ComputeCoveredTypes`；B-2 三处 `RegisterCompilationAction` + 全树 `DescendantNodes`/`GetDeclaredSymbol`；B-3 `HasNet8OrGreaterDefine` 门控位于 `GetLocalAnnotatedTypes` 之后（L303-L312）；B-4 `AnalyzeCore` 无语法预筛；B-5 `ResolveProfilesCore` 全类型 `AllInterfaces` 闭包；B-6 无总开关；B-7 `ValidateGeneratedCode` 无开关）。方案必要性成立，目标值（P0 收敛到近零）与手段（预筛 + 缓存）匹配。

**发现的方案缺陷（已修正入正文）**：
1. **[P0 正确性] F-1 名字化归一化错误**：`OriginalDefinition` 归一会坍缩构造泛型（`List<Foo>`≡`List<Bar>`）→ 误判已覆盖 → 漏报诊断。已改为「符号原样显示名 + 查询侧保留 unbound 归一 + ExpandValueTuple」。
2. **[P0 正确性] F-1 静态缓存陈旧性假设错误**：PE 引用在常驻编译服务内可被原地重建（ProjectReference → PE 路径引用），Display/Identity 不变内容变。已改为 Display+MVID 键控。
3. **[P1 效能] F-2a 缓存粒度自相矛盾**：§1.3 把「Compilation 为键永不命中」定为核心机制，F-2a 却沿用之。已改为 SyntaxTree 级 CWT。
4. **[P2 免费优化] F-2c 缺属性符号前置否决**：`httpClientApiAttr == null` 检查现状在覆盖集合计算之后，已前移。
5. **[P2 事实性] F-5 注册先例描述与仓库事实不符**：无 Directory.Build.props 统一注册先例，实为逐 csproj；已修正并明确验收走单测注入。

**功能重复/冗余排查**：
- 三分析器的「接口遍历 + 属性精确比较」为三份复制骨架（历史上已有 GEN-22 口径漂移教训）。本期 F-2c 顺带把「属性存在性判定」改为先名字后精确的两段式；**整段遍历骨架的共享提取登记为后续项**（改动面大、与「诊断契约零变更」冲突风险高，本期收益/成本比不成立）。
- `_annotatedTypesCache` 与 `_localContextsCache` 同构（全类型声明 + GetDeclaredSymbol）；预检后仍有两次遍历。登记为后续项，不纳入本期。
- 其余无重复实现；`HasNet8OrGreaterDefine` 的 CWT+StrongBox 已是既有工程约定形态，无需重构。

**最优解评估**：在「诊断契约零变更」硬约束下，「预筛 + 分层缓存」优于「RegisterSymbolAction 化 / FAWM 化」——后者会改变生成代码诊断行为或丢失全编译视野，方案 §六 登记为长期项的判断正确。

### 8.2 系统架构师视角

**逻辑闭环**：三 AOT 分析器（编译级）+ ToolSurface（增量生成器级）+ TransitiveCodeGenerator（DEBUG 验证）三条性能路径各自独立修复、互不耦合，回退边界清晰。缓存分层收敛为三级且各层生命周期自洽：SyntaxTree 级（跨编译复用，预筛）→ Compilation 级（CWT+Lazy，符号/模型）→ 进程级静态（仅元数据名字，Display+MVID 键）。跨层纪律明确：静态层不持符号，与项目既有约定（ProfileDiscovery 缓存值不持符号、InterfaceModel 指纹 WithoutTrivia）一致。

**架构兼容性**：
- 保留 `RegisterCompilationAction` 的决策与既有迁移史一致（Phase2 修复 3.2 刚把 AOT004/005/007 从生成管道迁到分析器），不再翻烧饼；正确。
- F-5 开关与既有 `MudEnableAotCoverageAnalysis`/`MudAotRuntimeMode` 的层级已定义清楚（总闸优先），且受 `DocumentationContractTests` 双向守卫自动看护——新增属性若未注册/未读取会直接测试失败，闭环成立。
- F-6 环境变量方案与 `[Conditional("DEBUG")]` 的剥离特性匹配（build_property 对 Release 包无效），是唯一可行开关位；已补注意事项：IDE 场景环境变量需重启 IDE 进程生效，写入 README。

**遗留架构债（登记不修）**：AOT 诊断 FAWM 化、三分析器遍历骨架共享、`ComputeLocalContexts` 与 `ComputeLocalAnnotatedTypes` 双遍历合并——见 §六/8.1。
