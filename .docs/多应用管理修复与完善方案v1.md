## 0. 方案总览

### 0.1 设计原则

| # | 原则 | 在本方案中的体现 |
|---|------|-----------------|
| D1 | **单一事实来源** | 同一逻辑名（客户端名）只允许一套大小写语义（AM-08）；同一实例只允许一条解析路径语义（AM-10）；同一环境只允许一个 AsyncLocal 存储（AM-02/AM-03） |
| D2 | **写入只发生在显式切换点** | 多租户上下文写入收敛到 `UseApp/UseDefaultApp/BeginScope`；构造函数、查询方法一律只读（AM-02，与既有 G-1 决策对齐） |
| D3 | **锁外读、锁内一致写、锁外广播** | `DefaultAppManager` 热路径保持无锁；仅管理操作（低频）进入临界区；事件永不持锁广播（AM-04） |
| D4 | **渐进可退** | 每个工项独立可编译、可测试、可单独 revert；生成器改动集中在一次快照重生成窗口（AM-02+AM-16） |
| D5 | **不引入新依赖、不破坏 AOT** | 全部改动使用 BCL/DI 既有能力；新增类型避开反射；AOT 门禁场景同步追加（T5） |

## 1. P0 阶段：缺陷修复

### AM-01 Keyed Service 注册/消费门控对齐【来源 A1，风险：高】

**问题回顾**：注册端 `#if NET8_0_OR_GREATER`（ServiceCollectionExtensions.cs:127-131），消费端 `#if NET6_0_OR_GREATER` 即用 `GetRequiredKeyedService`（EnhancedHttpClientFactory.cs:61-65）→ net6.0 运行时必抛。

**设计决策**：对齐到 **net6+ 注册**，而非把消费端退回 ClientFactories。理由：
1. net6.0 目标引用的 ME.Http 8.0.1（csproj 条件组）已含 keyed API，无包缺失问题，属纯门控错位；
2. 保留双实现路径（keyed + 字典回退）在 net6 上同时活着，正是 A3 类"同义不同形"问题的温床——收敛为 keyed 单一路径，`ClientFactories` 字典仅服务 netstandard2.0；
3. netstandard2.0 无 keyed，回退分支维持现状不动。

**改动**（`Mud.HttpUtils.Client/ServiceCollectionExtensions.cs`）：
```csharp
private static void RegisterNamedClient(
    IServiceCollection services, string clientName, bool setAsDefault)
{
#if NET6_0_OR_GREATER   // ← 由 NET8_0_OR_GREATER 放宽，与 EnhancedHttpClientFactory 消费端同门槛
    services.AddKeyedTransient<IEnhancedHttpClient>(
        clientName,
        (sp, key) => CreateEnhancedClient(sp, (string)key));
#endif
    // ...其余不变
}
```

**验收**：
- 新增 `net6.0` 运行时测试：构建 `ServiceProvider` → `AddMudHttpClient("t", baseAddress)` → `GetRequiredService<IEnhancedHttpClientFactory>().CreateClient("t")` 不抛（当前必抛，作修复前红灯用例）；
- 快照/生成物零变化（运行时路径改动，无生成代码参与）。

**备注**：AM-10 会将此处 `AddKeyedTransient` 升级为转发单例，属同一文件同一注册点的二段改造；AM-01 先行合入，保证任何时刻该门控是自洽的。

### AM-02 生成客户端构造函数消除上下文写入【来源 A2，风险：高】

**问题回顾**：默认模式生成构造函数含 `_appContextHolder.Current = _defaultAppContext;`（ConstructorGenerator.cs:552）；DI 注册为 Transient（HttpInvokeRegistrationGenerator.cs:522）→ 每次解析都重置环境租户上下文。G-1 修复了 `GetTokenAsync` 查询副作用（AccessTokenGenerator.cs:58-60），但构造函数这次写入被遗漏。

**设计决策**：
1. **删除**构造函数写入（D2 原则：写入只发生在 `UseApp/UseDefaultApp/BeginScope`）；
2. 方法体的回退语义**联动修改**：默认模式由 `?? throw`（MethodGenerator.cs:276）改为 `?? _defaultAppContext`，与 TokenManager 模式 `?? _tokenManager.GetDefaultApp()`（:272）对齐。否则删除构造写入后，"从未显式切换"的首个调用直接抛异常，破坏单应用开箱即用路径；

### AM-03 `AsyncLocalAppContextSwitcher` 改 Holder 模式【来源 F1/P2，风险：高】

**问题回顾**：值快照式恢复（AsyncLocalAppContextSwitcher.cs:29-53）——Dispose 写"当前"ExecutionContext，跨上下文 Dispose 劫持无关执行流、乱序 Dispose 留下悬空租户；BeginScope 两次 AsyncLocal 写带来 ExecutionContext 复制放大。

**设计决策**：采用 BCL 标准的 **holder 模式**（与 `HttpContextAccessor` 同款）。备选取舍：
- *ExecutionContext.Run 包裹*：改变调用方控制流（需把业务逻辑变成委托），侵入性大，否决；
- *CallContext/LogicalCallContext*：.NET Core 后已无此 API，否决；
- *holder 模式*：AsyncLocal 只在首次创建 holder 时写一次，此后读/改/恢复全部发生在 holder 对象上——天然解决跨上下文 Dispose（改的是对象字段而非 ExecutionContext）与乱序 Dispose（后 Dispose 的内层 scope 恢复自己快照，虽仍非事务性回滚，但**不会污染无关上下文**，且嵌套正常顺序下行为正确）。

**改动**（`Mud.HttpUtils.Client/AppContext/AsyncLocalAppContextSwitcher.cs` 整体替换核心，公共形状 `IAppContextHolder` 不变）：
```csharp
public class AsyncLocalAppContextSwitcher : IAppContextHolder
{
    private sealed class Holder { public IMudAppContext? Value; }
    private readonly AsyncLocal<Holder> _context = new();

    public IMudAppContext? Current
    {
        get => _context.Value?.Value;
        set => (_context.Value ??= new Holder()).Value = value;
    }

    public IDisposable BeginScope(IMudAppContext context)
    {
        if (context == null) throw new ArgumentNullException(nameof(context));
        var holder = _context.Value ??= new Holder();
        var previous = holder.Value;
        holder.Value = context;
        return new AppContextScope(holder, previous);
    }

    private sealed class AppContextScope(Holder holder, IMudAppContext? previous) : IDisposable
    {
        private int _disposed;
        public void Dispose()
        {
            if (Interlocked.Exchange(ref _disposed, 1) == 0)
                holder.Value = previous;   // 原地改写：跨上下文可见、不劫持当前 ExecutionContext
        }
    }
}
```
**语义变化点（须写入 XML remarks）**：
1. `Current` setter 的可见范围从"当前 ExecutionContext 向下传播"变为"**逻辑调用链共享的 holder**"——在并行分支中 `Current = x` 后，兄弟分支也能读到 x（值快照版读不到）。这与 `HttpContextAccessor` 一致，是多租户场景的正确语义（同请求内所有子分支共享租户）；对依赖"兄弟分支隔离"的极端用法是行为变化，CHANGELOG 行为基线需记录；
2. 多次 Dispose 单个 scope 仍幂等（`Interlocked` 保留）；乱序 Dispose 下最终值 = 最后执行恢复的 scope 快照，**不再**保证"最外层 previous 胜出"，但错误仅限本调用链内部（F1 的跨上下文劫持消除）——文档明确推荐 `using` 顺序释放。

**验收**：现有 10 个用例（AsyncLocalAppContextSwitcherTests.cs）必须全绿（它们覆盖嵌套、多次 Dispose、跨 await、并发隔离——holder 模式对这些全部保持正确）；另新增 F1 两个破坏性用例（见 §5 T1 清单）。

### AM-04 `DefaultAppManager` 写路径一致性【来源 F2/F3/F4，风险：中高】

**问题回顾**：`UpdateApp` 检查-赋值非原子（:101-104），可与并发 `RemoveApp` 交错"复活"应用；`RegisterApp` 的 `isUpdate` 判定竞态致双 `Added`（:61-62）；`GetDefaultApp` 锁外二次查字典，默认键刚被移除时抛误导性"未注册"异常（:142-153）。

**设计决策**：
1. 把 `_defaultAppLock` 更名为 `_stateLock` 并升级为**管理写路径总锁**：`RegisterApp/UpdateApp/RemoveApp` 的"判定+写入+默认键维护"整体入锁，事件保持锁外广播（D3 原则：广播顺序与注册表状态的强一致不重要——订阅者以事件为提示、以 `HasApp` 等查询为准做收敛，锁外广播避免订阅者回调内再调管理 API 造成死锁）；
2. `GetDefaultApp` 改为锁内一致读（默认键 + 字典取值同一临界区），异常文案区分"未设置默认"与"默认已被移除"两种情况；
3. 热路径 `GetApp/TryGetApp/HasApp/GetAllApps` 维持无锁 `ConcurrentDictionary` 读不变（读性能不回退）。

**改动**（`Mud.HttpUtils.Abstractions/AppContext/DefaultAppManager.cs`）：
```csharp
private readonly object _stateLock = new();   // 原 _defaultAppLock，更名以反映职责扩大

public void RegisterApp(string appKey, TAppContext appContext, bool isDefault = false)
{
    // ...参数校验不变...
    bool isUpdate;
    lock (_stateLock)
    {
        isUpdate = _apps.ContainsKey(appKey);
        _apps[appKey] = appContext;
        if (isDefault) _defaultAppKey = appKey;
    }
    OnConfigurationChanged(new(appKey, isUpdate ? AppConfigurationChangeType.Updated
                                                : AppConfigurationChangeType.Added));
}

public void UpdateApp(string appKey, TAppContext appContext)
{
    // ...参数校验不变...
    lock (_stateLock)
    {
        if (!_apps.ContainsKey(appKey))
            throw new InvalidOperationException($"未找到应用标识为 '{appKey}' 的应用上下文，无法更新。请先调用 RegisterApp 注册应用。");
        _apps[appKey] = appContext;
    }
    OnConfigurationChanged(new(appKey, AppConfigurationChangeType.Updated));
}

public bool RemoveApp(string appKey)
{
    // ...空键早退不变...
    bool removed;
    lock (_stateLock)
    {
        removed = _apps.TryRemove(appKey, out _);
        if (removed && _defaultAppKey == appKey) _defaultAppKey = null;
    }
    if (removed)   // 事件移出锁外
        OnConfigurationChanged(new(appKey, AppConfigurationChangeType.Removed));
    return removed;
}

public virtual TAppContext GetDefaultApp()
{
    lock (_stateLock)
    {
        if (!string.IsNullOrEmpty(_defaultAppKey) && _apps.TryGetValue(_defaultAppKey!, out var ctx))
            return ctx;
        if (!string.IsNullOrEmpty(_defaultAppKey))
            throw new InvalidOperationException("默认应用已被移除。请重新注册默认应用（isDefault = true）。");
    }
    throw new InvalidOperationException("未设置默认应用。请在注册应用时设置 isDefault = true。");
}
```
**注意事项**：
- `NEW-MA-01`（RemoveApp 不 Dispose 上下文，:120-122 注释）与 `MA-03`（virtual 化，:138-141）决策保持不动；
- `RegisterAppAsync`（:78-91）体保持"锁外初始化 + 调用 RegisterApp"，初始化 I/O 不进锁；
- 单元测试断言文案需同步（DefaultAppManagerTests.cs:112-113 只断言 `InvalidOperationException` 类型，兼容；`GetApp_NonExistingApp_Throws`（:60-67）不受影响）。

**验收**：§5 T1 的并发三用例（Added 恰一次 / Update 不复活 / GetDefaultApp 移除后文案）全绿。

### AM-08 客户端名大小写语义统一【来源 A3，风险：中】

### AM-14 `DefaultHeaders` 密钥引用占位符【来源 S3，风险：低】
