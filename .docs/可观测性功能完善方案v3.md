## 2. 新发现的差距与问题

### 2.1 P0 级差距（与接入指南承诺直接冲突，必须修复）

#### G9：EnhancedHttpClient 兜底路径未发出 Span 事件

**指南承诺**（第 6.2 节 Span 事件表）：

> RequestStarted / RequestStopped / RequestFailed 事件应记录在出站请求 span 上。

**实际实现**：

Mud.HttpUtils 存在两条采集路径：

| 路径 | 适用场景 | Span 属性 | Span 事件 | 指标 |
|------|----------|:---------:|:---------:|:----:|
| **路径 A**：IHttpClientFactory + TracingDelegatingHandler | `services.AddHttpClient("name").AddHttpMessageHandler<TracingDelegatingHandler>()` | ✅ 全部 11 个 | ✅ 全部 7 类 | ✅ |
| **路径 B**：直接 `new EnhancedHttpClient(new HttpClient(), ...)` | 控制台应用 / 单元测试 / 非 DI 场景 | ✅ 全部 11 个 | ❌ **零事件** | ✅ |

路径 B 的核心方法 [EnhancedHttpClient.ExecuteWithObservabilityAsync](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/EnhancedHttpClient.cs#L1334-L1375) 与 [SendAsAsyncEnumerable](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/EnhancedHttpClient.cs#L240-L358)：

```csharp
// EnhancedHttpClient.cs:1334-1375（路径 B 兜底方法）
private async Task<T> ExecuteWithObservabilityAsync<T>(...)
{
    MudHttpObservability.SetClientName(request, ClientName);
    // ... 日志作用域 ...
    if (MudHttpObservability.IsObserved(request))
        return await ExecuteWithLoggingAsync(...);

    var activity = MudHttpObservability.StartRequestActivity(request, ClientName);
    var sw = ValueStopwatch.StartNew();
    try
    {
        var result = await ExecuteWithLoggingAsync(...);
        MudHttpObservability.RecordSuccessFromRequest(activity, request, sw.GetElapsedTime().TotalMilliseconds, ClientName);
        // ❌ 缺少：AddActivityEvent(RequestStarted) / AddActivityEvent(RequestStopped)
        MudHttpObservability.MarkObserved(request);
        return result;
    }
    catch (Exception ex)
    {
        MudHttpObservability.RecordError(activity, ex, sw.GetElapsedTime().TotalMilliseconds, ClientName, request);
        // ❌ 缺少：AddActivityEvent(RequestFailed)
        MudHttpObservability.MarkObserved(request);
        throw;
    }
    finally
    {
        activity?.Dispose();
    }
}
```

**影响**：
- 接入指南未区分两条路径，承诺的 Span 事件在路径 B 下完全缺失
- 通过 `AddMudHttpOpenTelemetry()` 接入但使用 `new EnhancedHttpClient()` 的用户，在 Jaeger 中看不到 RequestStarted/RequestStopped/RequestFailed 事件
- 集成测试 [ObservabilityIntegrationTests](file:///d:/Repos/MudHttpUtils/Tests/Mud.HttpUtils.Integration.Tests/ObservabilityIntegrationTests.cs) 仅覆盖路径 A，未捕获此差距
- 路径 B 是 v1 方案明确设计的"兜底采集"路径，应与路径 A 产出一致

**修复方向**：
1. 在 `ExecuteWithObservabilityAsync` 方法中，调用 `MudHttpActivitySource.AddActivityEvent` 分别在请求开始/成功完成/异常时写入 RequestStarted/RequestStopped/RequestFailed 事件
2. 在 `SendAsAsyncEnumerable` 方法中同步补齐（这是独立的迭代器路径，未复用 ExecuteWithObservabilityAsync）
3. 新增集成测试覆盖路径 B 的 Span 事件断言

#### G10：4xx 状态码设为 ActivityStatusCode.Error 违反 OTel 规范

**OTel 规范要求**（[HTTP Spans 语义约定](https://opentelemetry.io/docs/specs/semconv/http/http-spans/#status)）：

> **For HTTP client spans**: Set Status to `Error` if response status code is 5xx. For 4xx, Status should be `OK` or `Unset`（client made a valid request, server returned client error）.

**实际实现**：

[MudHttpObservability.cs:130-133](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/Observability/MudHttpObservability.cs#L130-L133)：

```csharp
if (statusCode >= 400)
    activity.SetStatus(ActivityStatusCode.Error);
else
    activity.SetStatus(ActivityStatusCode.Ok);
```

将 **所有 4xx 客户端错误** 设为 `ActivityStatusCode.Error`，违反 OTel 规范。

**影响**：
- Jaeger 中 401/403/404 等正常业务流（如令牌失效触发恢复、资源不存在）被标记为 Error span
- 基于 Span Status 的告警（如"错误率 > 5%"）会误报
- 与 .NET `HttpClient` 内置 Instrumentation（遵循 OTel 规范）行为不一致，混合使用时产生矛盾

**修复方向**：
```csharp
// 客户端 span：仅 5xx 与网络错误设为 Error
if (statusCode >= 500)
    activity.SetStatus(ActivityStatusCode.Error);
else
    activity.SetStatus(ActivityStatusCode.Ok);
```

### 2.2 P1 级差距（功能遗漏 / 规范不符，应修复）

#### G11：OTel 适配包缺少 Resource 配置

**OTel 规范要求**（[Resource 语义约定](https://opentelemetry.io/docs/specs/semconv/resource/)）：

> 所有遥测数据必须包含 Resource 属性，至少 `service.name`、`service.version`、`deployment.environment`。

**实际实现**：

[MudHttpOpenTelemetryExtensions.cs:53-95](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.OpenTelemetry/MudHttpOpenTelemetryExtensions.cs#L53-L95)：

```csharp
var builder = services.AddOpenTelemetry();
// ❌ 未调用 .ConfigureResource(r => r.AddService(...))
if (options.EnableTracing)
    builder.WithTracing(tp => { ... });
if (options.EnableMetrics)
    builder.WithMetrics(mp => { ... });
```

未配置任何 Resource 属性。导出的 span/metric 在 Jaeger/Prometheus 中 `service.name` 为空或自动推断为进程名，`service.version` 缺失。

**影响**：
- 多服务环境中无法区分 Mud.HttpUtils 应用与其他服务
- 无法按 service.version 聚合指标做版本对比
- 与 OTel 规范不符，影响可观测性平台的数据治理

**修复方向**：
```csharp
var builder = services.AddOpenTelemetry()
    .ConfigureResource(r => r
        .AddService(serviceName: options.ServiceName ?? "Mud.HttpUtils.Application",
                    serviceVersion: options.ServiceVersion ?? MudHttpActivitySource.Version)
        .AddAttributes(new[]
        {
            new KeyValuePair<string, object>("deployment.environment", options.DeploymentEnvironment ?? "production")
        }));
```

在 `MudHttpOpenTelemetryOptions` 新增 `ServiceName` / `ServiceVersion` / `DeploymentEnvironment` 属性。

#### G12：OTel 适配包缺少 Sampler 配置

**问题**：

[MudHttpOpenTelemetryExtensions.cs:57-75](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.OpenTelemetry/MudHttpOpenTelemetryExtensions.cs#L57-L75) 中 `WithTracing` 未配置采样器，默认使用 `AlwaysOnSampler`（100% 采样）。

**影响**：
- 高流量场景下 100% 采样产生海量 span，OTLP 导出器与后端存储压力大
- 生产环境通常使用 `TraceIdRatioBasedSampler`（如 10%）+ `ParentBasedSampler`（继承父采样决策）
- 当前无法通过配置调整采样率

**修复方向**：在 `MudHttpOpenTelemetryOptions` 新增 `SamplingRatio` 属性（默认 1.0，即 AlwaysOn，保持向后兼容），并在 `WithTracing` 中配置：

```csharp
tp.SetSampler(new ParentBasedSampler(
    new TraceIdRatioBasedSampler(options.SamplingRatio)));
```

#### G13：OTel 适配包缺少 Logs 导出支持

**OTel 三支柱理念**：Logs / Metrics / Traces 应统一导出。接入指南第 1 节明确提及"Logs / Metrics / Traces 三大可观测性支柱"。

**实际实现**：

[MudHttpOpenTelemetryExtensions.cs](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.OpenTelemetry/MudHttpOpenTelemetryExtensions.cs) 仅配置 `WithTracing` + `WithMetrics`，**无 `WithLogging`**。

**影响**：
- Mud.HttpUtils 使用 `LoggerMessage` 模式产出结构化日志（接入指南第 4 节），但无法通过 OTLP 导出至 Loki/Tempo 等日志后端
- 三支柱割裂：Traces/Metrics 走 OTLP，Logs 仅走文件/控制台
- 用户需自行配置 OTel Logs，与"一键开启"承诺不符

**修复方向**：新增 `EnableLogging` 选项（默认 `false` 保持向后兼容，因 Logs 导出依赖 .NET 8+ 的 `ILogger` 集成），在 `MudHttpOpenTelemetryExtensions` 中追加：

```csharp
if (options.EnableLogging)
{
    builder.WithLogging(lp =>
    {
        lp.AddOtlpExporter(o => { /* 同 Tracing/Metrics */ });
        options.ConfigureLogging?.Invoke(lp);
    });
}
```

**指南承诺**（第 6.4 节 Token Recovery 子 Span 示例）：

#### G15：异常记录使用 SetTag 而非 Activity.RecordException

**OTel 规范要求**（[Span Exceptions](https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-spans/)）：

> 异常应通过 `Activity.RecordException(ex)` 记录，该方法创建名为 `exception` 的 ActivityEvent，包含 `exception.type` / `exception.message` / `exception.stacktrace` tags。

**实际实现**：

[MudHttpObservability.cs:158-163](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/Observability/MudHttpObservability.cs#L158-L163)：

```csharp
activity.SetStatus(ActivityStatusCode.Error, ex.Message);
// 手动设置异常 tag，避免依赖 ActivityExtensions.RecordException（在 netstandard2.0 上可能不可用）
activity.SetTag("exception.type", ex.GetType().FullName);
activity.SetTag("exception.message", ex.Message);
activity.SetTag("exception.stacktrace", ex.StackTrace);
```

将异常作为 Span 属性（tags）而非 Span 事件（event）记录。

**影响**：
- Jaeger 中异常以属性形式展示，而非标准 `exception` 事件，不符合 OTel 规范
- 部分 APM 工具（如 Datadog / NewRelic）依赖 `exception` 事件做异常聚合，无法识别
- 异常作为 tag 会被某些后端索引为高基数维度，影响查询性能

**修复方向**：在 .NET 8+ 上使用 `activity.RecordException(ex)`（`ActivityExtensions.RecordException` 扩展方法），netstandard2.0 保持现有 tag 降级方案：

```csharp
#if NET8_0_OR_GREATER
    activity.RecordException(ex);  // 创建标准 exception 事件
#else
    activity.SetTag("exception.type", ex.GetType().FullName);
    activity.SetTag("exception.message", ex.Message);
    activity.SetTag("exception.stacktrace", ex.StackTrace);
#endif
```

### 2.3 P2 级差距（文档一致性 / 优化项）

#### G17：outcome 枚举值与文档不一致

**指南承诺**（第 5.2 节）：HTTP 请求 outcome 为 `success / client_error / server_error / error`

**实际实现**：[MudHttpObservability.cs:207-214](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/Observability/MudHttpObservability.cs#L207-L214) 返回 `success / redirect / client_error / server_error / unknown`，多出 `redirect` 与 `unknown` 两个值。

#### 3.2.1 EnhancedHttpClient 兜底路径补齐 Span 事件

在 [EnhancedHttpClient.cs](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/EnhancedHttpClient.cs) 的 `ExecuteWithObservabilityAsync` 与 `SendAsAsyncEnumerable` 方法中补齐事件：

```csharp
// ExecuteWithObservabilityAsync 修改示例
private async Task<T> ExecuteWithObservabilityAsync<T>(...)
{
    MudHttpObservability.SetClientName(request, ClientName);
    using var scope = _enableLogging ? MudHttpObservability.CreateLoggerScope(...) : null;

    if (MudHttpObservability.IsObserved(request))
        return await ExecuteWithLoggingAsync(...);

    var activity = MudHttpObservability.StartRequestActivity(request, ClientName);
    var sw = ValueStopwatch.StartNew();

    // ✅ 新增：RequestStarted 事件
    MudHttpActivitySource.AddActivityEvent(
        MudHttpDiagnosticNames.RequestStarted,
        () => new HttpRequestDiagnosticPayload(request.Method.Method, request.RequestUri?.ToString(), ClientName),
        MudHttpDiagnosticNames.RequestStarted,
        new[]
        {
            new KeyValuePair<string, object?>("method", request.Method.Method),
            new KeyValuePair<string, object?>("url", request.RequestUri?.ToString()),
            new KeyValuePair<string, object?>("client_name", ClientName ?? "(default)"),
        });

    try
    {
        var result = await ExecuteWithLoggingAsync(...);
        var elapsedMs = sw.GetElapsedTime().TotalMilliseconds;
        MudHttpObservability.RecordSuccessFromRequest(activity, request, elapsedMs, ClientName);

        // ✅ 新增：RequestStopped 事件
        int statusCode = 0;
        if (MudHttpObservability.TryGetProperty(request, "__mud_status_code", out var sc) && sc is int code)
            statusCode = code;
        MudHttpActivitySource.AddActivityEvent(
            MudHttpDiagnosticNames.RequestStopped,
            () => new HttpResponseDiagnosticPayload(request.Method.Method, request.RequestUri?.ToString(), ClientName, statusCode, elapsedMs),
            MudHttpDiagnosticNames.RequestStopped,
            new[]
            {
                new KeyValuePair<string, object?>("method", request.Method.Method),
                new KeyValuePair<string, object?>("url", request.RequestUri?.ToString()),
                new KeyValuePair<string, object?>("client_name", ClientName ?? "(default)"),
                new KeyValuePair<string, object?>("status_code", statusCode),
                new KeyValuePair<string, object?>("elapsed_ms", elapsedMs),
            });

        MudHttpObservability.MarkObserved(request);
        return result;
    }
    catch (Exception ex)
    {
        var elapsedMs = sw.GetElapsedTime().TotalMilliseconds;
        MudHttpObservability.RecordError(activity, ex, elapsedMs, ClientName, request);

        // ✅ 新增：RequestFailed 事件
        MudHttpActivitySource.AddActivityEvent(
            MudHttpDiagnosticNames.RequestFailed,
            () => new HttpRequestErrorDiagnosticPayload(request.Method.Method, request.RequestUri?.ToString(), ClientName, elapsedMs, ex),
            MudHttpDiagnosticNames.RequestFailed,
            new[]
            {
                new KeyValuePair<string, object?>("method", request.Method.Method),
                new KeyValuePair<string, object?>("url", request.RequestUri?.ToString()),
                new KeyValuePair<string, object?>("client_name", ClientName ?? "(default)"),
                new KeyValuePair<string, object?>("elapsed_ms", elapsedMs),
                new KeyValuePair<string, object?>("exception_type", ex.GetType().Name),
            });

        MudHttpObservability.MarkObserved(request);
        throw;
    }
    finally
    {
        activity?.Dispose();
    }
}
```

`SendAsAsyncEnumerable` 迭代器路径需同步补齐（finally 块中根据 `recordedSuccess` 决定写 RequestStopped 或 RequestFailed）。

## 5. 关键风险与对策

| 风险 | 等级 | 对策 |
|------|:----:|------|
| **路径 B 补齐 Span 事件导致重复写入**：若 TracingDelegatingHandler 与 EnhancedHttpClient 同时启用，可能重复写事件 | 中 | 沿用现有 `__mud_observed` 去重机制：路径 B 检查 `IsObserved(request)`，已被路径 A 采集则跳过事件写入 |
| **RecordException 在 netstandard2.0 不可用**：`ActivityExtensions.RecordException` 扩展方法在旧 SDK 包不存在 | 低 | 条件编译：`#if NET8_0_OR_GREATER` 使用 RecordException，否则降级为 tag |
| **Resource 配置覆盖用户自定义**：用户可能已在 `ConfigureTracing` 中配置 Resource | 低 | `ConfigureResource` 在 `WithTracing`/`WithMetrics` 之前执行，用户委托可覆盖；提供 `ConfigureResource` 委托选项 |
| **SamplingRatio=0 导致无 span**：用户误配置 0 采样率 | 低 | 限制 `SamplingRatio` 范围为 (0, 1]，默认 1.0 保持向后兼容 |
| **Logs 导出依赖 .NET 8+ ILogger 集成**：OTel Logs SDK 对 net6.0 支持有限 | 低 | EnableLogging 默认 false；csproj 已限定 net8.0/net10.0，满足条件 |
| **集成测试 ActivityListener 跨测试泄漏** | 低 | 已通过 `[CollectionBehavior(DisableTestParallelization = true)]` 串行执行解决（v2 已修复） |

v2 方案成功补齐了 TracingDelegatingHandler 路径的 Span 属性与事件，可观测性基础设施完整。v3 方案通过独立复审发现 **3 个维度的新差距**：

1. **双路径一致性（P0）**：EnhancedHttpClient 兜底路径未发出 Span 事件，与接入指南承诺直接冲突。这是 v2 方案未覆盖的最关键差距，影响所有非 IHttpClientFactory 场景的用户。

2. **OTel 规范符合度（P0/P1）**：4xx 状态码设为 Error 违反 HTTP 客户端 span 规范；异常记录使用 tag 而非标准 exception 事件；OTel 适配包缺少 Resource / Sampler 配置。

3. **生产级配置完整性（P1）**：OTel 适配包缺少 Logs 导出、批量导出配置、自定义 OTLP Headers 支持，与"一键开启"承诺存在差距。

v3 修复后预期综合评分达 **9.5+**，与接入指南承诺完全一致，且符合 OTel 语义约定规范，满足生产环境部署要求。
