### 0.4 逻辑漏洞与改进

#### 漏洞 1：DelegatingHandler 注入路径覆盖不全

`TracingDelegatingHandler` / `MetricsDelegatingHandler` 通过 `IHttpClientBuilder.AddHttpMessageHandler<T>()` 注入，**仅对 IHttpClientFactory 路径生效**。当用户直接 `new EnhancedHttpClient(new HttpClient(), ...)` 时，Handler 链不会被触发。

**改进**：在 `EnhancedHttpClient.ExecuteWithLoggingAsync` 入口直接采集指标 + 创建 Activity（作为兜底），DelegatingHandler 仅作为 IHttpClientFactory 链路的"前置采集点"（用于在 HttpClient 内置 Diagnostics 之前注入 traceparent）。两条路径指标去重通过 `request.Properties["__mud_observed"]` 标记实现。

#### 漏洞 2：与 .NET HttpClient 内置 Diagnostics 的关系

.NET HttpClient 在 `HttpClient.SendAsync` 内部会自动启动 `System.Net.Http` ActivitySource 的 OutboundActivity（.NET 5+）。`TracingDelegatingHandler` 在 `base.SendAsync` 之前调用 `StartActivity`，新建的 `Mud.HttpUtils.HttpClient` 活动会成为 `System.Net.Http` 活动的**父级**（而非子级），形成 `Mud → System.Net.Http → 网络` 链。

原方案"复用为父活动，不重复 StartActivity"的描述不准确，因为 DelegatingHandler 在 HttpClient 内置 Diagnostics 之前执行。**正确策略**：始终新建 Mud 活动，将其作为 System.Net.Http 活动的父级；不要尝试复用，避免依赖内部实现细节。当 Mud ActivitySource 无监听器时，`StartActivity` 返回 `null`，自然降级为零开销。

#### 漏洞 3：LoggerMessage 源生成器与 netstandard2.0

`[LoggerMessage]` 源生成器仅支持 .NET 6+。netstandard2.0 必须 fallback 到 `LoggerMessage.Define`。

**改进**：`MudHttpClientLog.cs` 使用条件编译：

```csharp
#if NET6_0_OR_GREATER
using Microsoft.Extensions.Logging;
[LoggerMessage(EventId = 101, Level = LogLevel.Warning,
    Message = "重试请求 {RetryCount}/{MaxRetries}: {Method} {Uri}, 等待 {Delay}ms")]
public static partial void RetryAttempting(ILogger logger, int retryCount, int maxRetries,
    string method, string uri, double delay);
#else
private static readonly Action<ILogger, int, int, string, string, double, Exception?> s_retryAttempting =
    LoggerMessage.Define<int, int, string, string, double>(
        LogLevel.Warning, new EventId(101, nameof(RetryAttempting)),
        "重试请求 {RetryCount}/{MaxRetries}: {Method} {Uri}, 等待 {Delay}ms");
public static void RetryAttempting(ILogger logger, int retryCount, int maxRetries,
    string method, string uri, double delay) => s_retryAttempting(logger, retryCount, maxRetries, method, uri, delay, null);
#endif
```

### 1.2 关键缺失（Gaps）

经全文检索确认：**项目源代码中不存在任何 `ActivitySource`、`Meter`、`Counter`、`Histogram`、`DiagnosticListener`、`DiagnosticSource`、`OpenTelemetry`、`IHealthCheck`、`EventSource`、`AddHealthChecks` 的引用**。

| 缺失项 | 影响 |
|--------|------|
| **分布式追踪（ActivitySource）** | 跨越拦截器/重试/令牌刷新的同一请求无法关联；无法接入 Jaeger/Zipkin/OTLP；与 .NET HttpClient 内置 `HttpClient.Diagnostics` 不会建立父子关系 |
| **指标（Meter/Counter/Histogram）** | 无法量化 QPS、错误率、P99 延迟、缓存命中率、重试次数、熔断状态、令牌刷新成功率；运维只能依赖日志聚合，成本高 |
| **DiagnosticSource** | 外部观察者（如 APM 探针）无法订阅请求开始/结束/重试/熔断事件，无扩展点 |
| **健康检查（IHealthCheck）** | 令牌后台刷新服务、HTTP 客户端可达性、熔断器状态、缓存健康均无法暴露给 ASP.NET Core `/health` 端点 |
| **OpenTelemetry 集成** | 无 `AddOpenTelemetry()` 扩展、无 OTel 包引用、无 instrumentation 配置包 |

### 1.3 已有日志的质量问题

1. **模式不统一**：仅 `EnhancedHttpClientLogs.cs` 采用 `LoggerMessage.Define`（零分配、级别短路）；`Resilience`、`TokenManager`、`CacheResponseInterceptor` 全部使用 `ILogger.LogWarning("...{X}...", x)` 扩展方法，每次调用都会进行参数装箱与字符串格式化（即使级别未启用也会计算参数）。
2. **无关联 ID**：同一请求经过请求拦截器 → 发送 → 响应拦截器 → 反序列化 →（可选）重试/熔断/令牌恢复，日志之间没有 `CorrelationId` / `Activity.Current?.TraceId` 串联，排障困难。
3. **无时长度量**：日志不含请求耗时；超时仅记录 Timeout 配置值，无实际耗时分布。
4. **无客户端名**：Named HttpClient 的 `clientName` 未写入日志属性，多客户端场景无法区分。
5. **无日志作用域（BeginScope）**：未使用 `using var scope = _logger.BeginScope(...)` 携带请求上下文。
6. **Polly 指标未接出**：Polly v8 自带 `Metrics`（`ResiliencePipelineBuilder.AddMetering`），但当前 `PollyResiliencePolicyProvider` 未启用，重试/熔断事件仅落日志。

## 二、设计目标

1. **可插拔**：可观测性为可选功能，不破坏现有最小依赖；默认开启轻量日志，Metrics/Tracing 按需开启。
2. **AOT 兼容**：避免反射；优先使用 `LoggerMessage` 源生成器（.NET 6+）、`ActivitySource`、`Meter`（.NET 6+ 原生 AOT 友好）。
3. **多框架一致**：netstandard2.0 通过 `System.Diagnostics.DiagnosticSource` 包补充能力；.NET 6+ 使用原生 API。
4. **OpenTelemetry 友好**：默认产出 W3C TraceContext、OTel 标准属性（`http.method`、`http.url`、`http.status_code`、`http.response_content_length`）。
5. **零侵入业务代码**：尽量通过 `DelegatingHandler` / 拦截器 / 后台服务钩子实现，避免污染核心路径。

**新增 `TracingDelegatingHandler`**（最关键的接入点）：

```csharp
public sealed class TracingDelegatingHandler : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken cancellationToken)
    {
        if (!MudHttpActivitySource.Instance.HasListeners())
            return await base.SendAsync(request, cancellationToken);

        using var activity = MudHttpActivitySource.Instance.StartActivity(
            MudHttpActivitySource.ActivityNameRequest, ActivityKind.Client);

        if (activity is null)
            return await base.SendAsync(request, cancellationToken);

        var uri = request.RequestUri;
        activity.SetTag(MudHttpActivitySource.Tags.HttpMethod, request.Method.Method);
        activity.SetTag(MudHttpActivitySource.Tags.HttpUrl, uri?.ToString());
        activity.SetTag(MudHttpActivitySource.Tags.HttpScheme, uri?.Scheme);
        activity.SetTag(MudHttpActivitySource.Tags.HttpHost, uri?.Host);

        var sw = ValueStopwatch.StartNew();
        try
        {
            var response = await base.SendAsync(request, cancellationToken);
            activity.SetTag(MudHttpActivitySource.Tags.HttpStatusCode, (int)response.StatusCode);
            activity.SetTag(MudHttpActivitySource.Tags.HttpResponseContentLength,
                response.Content.Headers.ContentLength);
            activity.SetTag(MudHttpActivitySource.Tags.HttpStatusCodeClass,
                ((int)response.StatusCode).ToString()[0] + "xx");

            if ((int)response.StatusCode >= 400)
                activity.SetStatus(ActivityStatusCode.Error);
            else
                activity.SetStatus(ActivityStatusCode.Ok);

            return response;
        }
        catch (Exception ex)
        {
            activity.SetStatus(ActivityStatusCode.Error, ex.Message);
            activity.RecordException(ex);
            throw;
        }
        finally
        {
            activity.SetTag(MudHttpActivitySource.Tags.MudRetryCount,
                request.Properties.TryGetValue("__mud_retry_count", out var c) ? c : 0);
        }
    }
}
```

**接入方式** [修正：覆盖直接 new HttpClient 路径]：
1. **IHttpClientFactory 路径**：在 `ServiceCollectionExtensions.AddMudHttpClient` 中通过 `IHttpClientBuilder.AddHttpMessageHandler<TracingDelegatingHandler>()` 注册。
2. **直接 `new EnhancedHttpClient(new HttpClient(), ...)` 路径**：在 `EnhancedHttpClient.ExecuteWithLoggingAsync` 内部直接调用 `MudHttpActivitySource.Instance.StartActivity(...)` 作为兜底，与 DelegatingHandler 中的逻辑一致。
3. **去重**：两条路径同时存在时（IHttpClientFactory 路径下 EnhancedHttpClient 内部仍会兜底），通过 `request.Properties["__mud_observed"]`（或 .NET 5+ 的 `request.Options`）标记，第二个采集点跳过。

> 注：直接 new HttpClient 路径下，DelegatingHandler 链不会触发，需依赖 EnhancedHttpClient 内部兜底。这部分代码应抽取为静态方法 `MudHttpObservability.TryStartActivity(request, out var activity)` 供两条路径共用。

**与 .NET HttpClient 内置 Diagnostics 的关系** [修正：原描述不准确]：

.NET HttpClient 在 `HttpClient.SendAsync` 内部会自动启动 `System.Net.Http` ActivitySource 的 OutboundActivity（.NET 5+）。`TracingDelegatingHandler` 在 `base.SendAsync` 之前调用 `StartActivity`，因此 Mud 活动会成为 System.Net.Http 活动的**父级**，形成 `Mud.HttpUtils.HttpClient → System.Net.Http → 网络` 链。

**不要尝试复用 System.Net.Http 活动**作为 Mud 活动，因为这依赖 HttpClient 内部实现细节，且 DelegatingHandler 在内置 Diagnostics 之前执行（此时 OutboundActivity 尚未创建）。当 Mud ActivitySource 无监听器时，`StartActivity` 返回 `null`，自然降级为零开销。

internal static class TokenRefreshStatsCollector
{
    private static readonly ConcurrentQueue<RefreshEvent> s_events = new();
    private static readonly TimeSpan s_retention = TimeSpan.FromMinutes(5);

    public static void Record(bool success, string? tokenManagerKey, long elapsedMs)
    {
        s_events.Enqueue(new RefreshEvent(DateTimeOffset.UtcNow, success, tokenManagerKey, elapsedMs));
        Trim();
    }

    public static RefreshStats GetSnapshot(int windowSeconds)
    {
        var since = DateTimeOffset.UtcNow.AddSeconds(-windowSeconds);
        int total = 0, failures = 0;
        foreach (var e in s_events)
            if (e.Timestamp >= since) { total++; if (!e.Success) failures++; }
        return new RefreshStats(total, failures);
    }
}

- 调用 `services.AddMudHttpHealthChecks()` 后，`HealthCheckService` 中注册 `mud_token_refresh` 与 `mud_circuit_breaker` 两个检查项；

- netstandard2.0 / net6.0 / net8.0 / net10.0 全部编译通过。

| 风险 | 等级 | 对策 |
|------|:----:|------|
| **AOT 兼容性破坏**：反射、`DynamicInvoke`、`Assembly.Load` | 高 | 全部使用源生成器与静态 API；CI 增加 `dotnet publish -r linux-musl-x64 /p:PublishAot=true` 验证 |

| **日志爆炸**：Debug 级别原始响应体日志（`JsonResponseBodyRaw`）在生产环境可能泄露/过载 | 中 | 已通过 `_enableLogging` 短路，需进一步确保生产环境默认 Debug 关闭；考虑增加 `MudHttpLoggingOptions.EnableBodyLogging` 开关（阶段二实现） |
| **DelegatingHandler 路径覆盖不全** [修正：新增]：直接 `new EnhancedHttpClient(new HttpClient(), ...)` 不经 IHttpClientFactory，Handler 链不触发 | 中 | 在 `EnhancedHttpClient.ExecuteWithLoggingAsync` 内部兜底采集 Activity/指标；通过 `request.Properties["__mud_observed"]` 标记去重 |

## 十、结论

当前 Mud.HttpUtils 项目在**日志层具备良好基础**（结构化 LoggerMessage + 完善脱敏），但在可观测性三大支柱中**仅实现了 Logs 一项**，且日志本身存在模式不统一、缺少关联 ID 与时长度量等问题。**Metrics、Traces、Health Checks、DiagnosticSource、OpenTelemetry 集成**均为完全空白，无法满足生产级 HTTP 客户端库的运维需求。

按本方案 P0 阶段实施后，项目将具备：
- 完整的分布式追踪能力（W3C TraceContext、OTel 语义属性）；

- 统一高性能的 LoggerMessage 日志；
- 请求级关联 ID 串联全链路。

P1/P2 阶段补齐健康检查与一键 OTel 适配后，可观测性综合评分预期可由 **4.2 → 8.5+**。
