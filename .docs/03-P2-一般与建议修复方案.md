## #20 🟡 `ShouldRetry` 在 netstandard2.0 与 net6+ 行为不一致

### 问题定位

```
Mud.HttpUtils.Resilience/PollyResiliencePolicyProvider.cs:539-569
 541:  #if NETSTANDARD2_0
 544:      if (exception.Data.Contains("HttpStatusCode") && ...) return retryStatusCodes.Contains(code);
 552:      foreach (var retryCode in retryStatusCodes)
 554:          if (message.Contains($" {retryCode} ")) return true;      // ← 字符串猜测，脆弱
 559:      return true;                                                  // 无法确定则重试
 561:  #else
 561:      if (exception.StatusCode.HasValue) ... return retryStatusCodes.Contains(statusCode);
 567:      return true;
```

两条分支在"异常无状态码信息"时结论可能不同（ns2.0 依赖消息文本，恰好含 `" 500 "` 才重试；
net6+ 直接 `return true`），违反"多 TFM 条件编译分支行为一致"要求。

### 修复设计

统一为**结构化判定**，删除字符串猜测：

```csharp
private static bool ShouldRetry(HttpRequestMessage? request, HttpRequestException exception, int[] retryStatusCodes)
{
    // 1) 结构化状态码：net5+ 用 StatusCode；ns2.0 用 Data["HttpStatusCode"]
    //    （由 EnhancedHttpClient.EnsureSuccessStatusCodeAsync:1737 统一写入，两 TFM 都有）
    if (TryGetStatusCode(exception, out var code))
        return retryStatusCodes.Contains(code);

    // 2) 无状态码 = 传输层故障（连接失败、DNS、TLS）→ 重试（两 TFM 一致）
    return true;
}

private static bool TryGetStatusCode(HttpRequestException ex, out int code)
{
#if NETSTANDARD2_0
    if (ex.Data.Contains("HttpStatusCode") && ex.Data["HttpStatusCode"] is int c) { code = c; return true; }
#else
    if (ex.StatusCode.HasValue) { code = (int)ex.StatusCode.Value; return true; }
#endif
    code = 0; return false;
}
```

**配套**：确认 `ApiException` 在 **netstandard2.0** 下也写入 `Data["HttpStatusCode"]`
（当前 `EnhancedHttpClient.cs:1737` 无条件写入 ✓）；
`DefaultHttpRequestExecutor.CreateApiException` 未写入 → **需补齐**（否则执行器路径在 ns2.0 下同样退化）。

### 验收

- 用例（双 TFM 参数化）：同一 `HttpRequestException`（含/不含状态码）→ 断言 ns2.0 与 net6+ 重试判定一致。

## #22 🟡 流式路径未应用 `ApplyRequestConfig` / `CaptureRequestContent`


## #23 🟡 `jsonSerializerOptions as JsonSerializerOptions` 丢失 `JsonTypeInfo<T>`

### 问题定位

```
DefaultHttpRequestExecutor.cs:170    var options = jsonSerializerOptions as JsonSerializerOptions;
DefaultHttpRequestExecutor.cs:237    content = _contentSerializer.Deserialize<TInner>(rawContent, jsonSerializerOptions as JsonSerializerOptions);
SystemTextJsonContentSerializer.cs:149  if (options is JsonTypeInfo<T> jsonTypeInfo) { ... }   // ← 永远不可达
```

### 修复设计

直接把 `object?` 透传给序列化器，由 `SystemTextJsonContentSerializer` 自行分派：

```csharp
result = _contentSerializer.Deserialize<TResult>(rawContent, jsonSerializerOptions);
content = _contentSerializer.Deserialize<TInner>(rawContent, jsonSerializerOptions);
```

（`SystemTextJsonContentSerializer.Deserialize<T>` 的签名本身就是 `object? options`，已有 `JsonTypeInfo<T>` 快路径。）

**现状影响说明**：当前生成器（`MethodGenerator.cs:402` 附近）传的是 `null` 或 `JsonSerializerOptions`，
所以暂不影响功能；但这是**契约陷阱**，必须修掉，否则未来接入 AOT 重载时静默失效。

### 验收

- 用例：传入 `JsonTypeInfo<T>` → 断言命中 `JsonSerializer.Deserialize(json, jsonTypeInfo)` 重载（用自定义 `IHttpContentSerializer` 探针或 `JsonSerializerContext` 未覆盖类型验证抛错行为）。

## #24 🟡 `_fetchLocks` 可能无界增长

### 问题定位

```
MemoryHttpResponseCache.cs:114   var fetchLock = _fetchLocks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
MemoryHttpResponseCache.cs:182   仅当 key 不在 _cache 中时才移除（60 s 清理周期）
```

### 修复设计

1. 给 `_fetchLocks` 加容量上限（与 `_maxCacheSize` 联动，如 `2 * _maxCacheSize`），
   超限时在 `CleanupExpiredEntries` 中按"不在 `_cache` 中"优先移除，仍超限则记录 `LogWarning`。
2. 或使用 `ConcurrentDictionary` + `Lazy<SemaphoreSlim>` 并在 `GetOrFetchAsync` 的 `finally` 中按引用计数移除。

**推荐方案 1**（改动小、可观测）。

### 验收

- 用例：10 万次不同 key 的失败回源 → 断言 `_fetchLocks.Count` 有界（内部可通过 `internal` 可见性或反射断言）。

## #25 🟡 `QueryParameterBuilder.Build()` 对相对路径 baseUrl 抛异常，文档未声明

### 问题定位

```
QueryParameterBuilder.cs:202   var uriBuilder = new UriBuilder(_baseUrl);   // 要求绝对 URI
```

### 修复设计（修订：采用 B —— 未发布无兼容负担）

原方案推荐 A（只补文档）的唯一理由是"该类型是公共 API，改行为属破坏性变更"——
项目未发布（`PublicAPI.Unshipped.txt` 尚未 Shipped），无兼容负担，直接选更合理的 **B**：

```csharp
public string Build()
{
    var query = BuildQueryString();
    if (string.IsNullOrEmpty(_baseUrl))
        return query;
    // 相对 baseUrl：降级为字符串拼接（合法且常见："/api/users" + "?page=1"）
    if (!Uri.TryCreate(_baseUrl, UriKind.Absolute, out _))
        return _baseUrl + (query.Length > 0 ? "?" + query : string.Empty);
    var uriBuilder = new UriBuilder(_baseUrl) { Query = query };   // 绝对路径维持现状
    return uriBuilder.ToString();
}
```

- 相对路径拼接语义简单明确，消除"必须绝对 URI"的隐含约束；
- 保留 `<exception>` 文档说明构造抛 `ArgumentNullException` 的路径。

### 验收

- 用例：`Create("/relative").Add("page","1").Build()` → 返回 `/relative?page=1`。
- 用例：`Create("https://x.y").Build()` → 绝对路径行为与现状一致（防回归）。

## #26 🟡 chunked 空响应体被当作有效 JSON 反序列化

### 问题定位

```
EnhancedHttpClient.cs:1111-1114   if (contentLength == 0) { ...return default; }
EnhancedHttpClient.cs:1209-1213   同上（XML 路径）
```

无 `Content-Length` 的 chunked 空体不会命中该分支，直接进入反序列化并抛 `JsonException`。

### 修复设计

在读取流后判断实际内容长度，而不是依赖 `Content-Length`：

```csharp
// 已有 Debug 日志路径会先 CopyUpToAsync 到 MemoryStream，可直接判断 memoryStream.Length == 0
// 非 Debug 路径：改用"先读 1 字节探测"或由序列化器容忍空流
if (stream.CanSeek && stream.Length == 0) { _logger.JsonResponseBodyEmpty(requestUri!); return default; }
```

更稳妥：为 `IHttpContentSerializer` 的 `FromHttpContentAsync` 约定"空内容返回 `default`"，
在 `SystemTextJsonContentSerializer` 中统一实现（**不改接口，仅改默认实现**）。

### 验收

- 用例：无 `Content-Length` 的 200 空体 → 断言返回 `default(T)` 而非抛 `JsonException`（需 T-0.2 chunked Stub）。

## #27 🟡 `HTTPCLIENT019`（`[Cache]` 属性被忽略）级别过低

### 问题定位

```
Diagnostics.cs:175-181（Mud.HttpUtils.Generator）  id "HTTPCLIENT019"，DiagnosticSeverity.Info
```

`UseSlidingExpiration` / `Priority` 被生成器忽略（`InterfaceImplementationGenerator.cs:788-798`，
`CacheOptions`（`ExecutionDescriptor.cs:39-53`）无 `UseSlidingExpiration` 字段），用户显式配置却静默失效。

### 修复设计（推荐"支持"优先于"告警"）

1. **M3 方案 A（推荐）**：让生成器支持 `UseSlidingExpiration`
   —— `IHttpResponseCache.Set` 已支持该参数（`IHttpResponseCache.cs:41`），`CacheResponseInterceptor.Set:116`
   已透传；只需 `CacheOptions`（Abstractions `ExecutionDescriptor.cs`）新增 `UseSlidingExpiration` 字段 +
   `MethodGenerator.WriteExecutionDescriptorCode` 生成 + `ExecuteWithOrchestrationAsync:614` 的
   `GetOrFetchAsync` 路径把滑动语义传给 `Set`（`GetOrFetchAsync` 若无滑动参数重载，需在 `IHttpResponseCache`
   增加 `useSlidingExpiration` 参数的 `GetOrFetchAsync` 重载 —— internal 评估后决定）。
2. **方案 B（兜底）**：若 A 的改动面过大，将 `HTTPCLIENT019` 升为 `Warning`，并在消息中给出替代方案。

`Priority` 若无对应实现，保留 Info 但在 XML 文档中标注 `[Cache(Priority = ...)]` 当前无效。

### 验收

- 用例：`[Cache(DurationSeconds = 60, UseSlidingExpiration = true)]` → 断言缓存条目在每次命中后顺延过期（方案 A）；

# 4. 功能完善 Roadmap

> 不属于"修 bug"，而是基于本次审查暴露的架构缺口提出的演进方向。
> 每项给出价值、设计要点与建议版本。

## R-1 可观测性治理层（`MudHttpObservabilityOptions` 配置对象）

**价值**：目前遥测行为（是否脱敏、`http.url` 是否记录、指标 tag 白名单）散落在各个静态调用中，无法集中配置。

**设计**

```csharp
public sealed class MudHttpObservabilityOptions
{
    public bool RedactUrlInTelemetry { get; set; } = true;      // #5/M2 落地（本项与 #5 合并实施）
    public bool RecordFullUrlOnSuccess { get; set; } = false;   // 默认只记 scheme+host+path
    public IReadOnlySet<string> MetricTagAllowlist { get; set; } =
        new HashSet<string> { "client_name", "method", "host", "outcome", "status_code", "policy_key" };
    public bool EmitDiagnosticEvents { get; set; } = true;      // 高频场景可关闭（见 R-2）
}
```

在 `MudHttpMeter` / `MudHttpObservability` 的指标写入处做 tag 白名单过滤，**从机制上杜绝高基数回归**（#6 的治本之策）。

**建议版本**：M3（`RedactUrlInTelemetry` 在 M2 随 #5 先行，其余字段 M3）。

## R-2 诊断事件（DiagnosticListener）高频开销治理

**现状（验证修正）**：`MudHttpActivitySource.AddActivityEvent:56-72` **已实现**
"无订阅者时 payloadFactory 不调用、零分配"（经 `MudHttpDiagnosticListener.Instance.WriteIfEnabled` 短路）；
`StartRequestActivity:40` 也已有 `HasListeners` 检查。**剩余缺口**仅是：Activity 事件部分在
`Activity.Current` 是 Mud Activity 时仍会构造 tags 数组（KVP 数组分配）——低收益，且 `EmitDiagnosticEvents`
开关（R-1）即可覆盖。

**设计**：M3 把 `EmitDiagnosticEvents` 开关接入 `AddActivityEvent` 短路即可，不做更多优化。

**建议版本**：M3（低风险，收益中等）。

## R-3 `IUrlValidator` 实例化 + 热更新（#4 步骤 2）

随 `UrlValidatorOptions` 支持 `IOptionsMonitor` 热更新，白名单可配置化、租户隔离化。
**建议版本**：M3 提供；因未发布，静态门面是否标记 `[Obsolete]` 待首次发布前评估（非本轮）。

## R-4 端点级弹性策略（按 host/路径维度隔离熔断）

**价值**：当前熔断策略按 `TResult` 类型缓存（`PollyResiliencePolicyProvider.PolicyCacheKey`），
同一 `TResult` 的**所有下游端点共享一个熔断器** → 单端点故障会误熔断全部（审查维度 4 的"共享实例全局误熔断"）。

**设计**：`PolicyCacheKey` 增加 `endpoint` 维度（scheme+host+path 模板），
由 `IResiliencePolicyResolver.ResolvePolicyWrapper` 的调用方传入；
默认仍按类型缓存（兼容），通过 `ResilienceOptions.IsolateCircuitBreakerByEndpoint` 开启。

**建议版本**：M4（需评估策略实例数量增长）。

## R-5 成功响应体大小守卫（N-2 的能力化）

`MaxSuccessResponseBytes` + `MaxDownloadBytes`，配合 `MudHttpMeter.ResponseBytes` 直方图做容量治理。

**建议版本**：M2 先落地 `MaxSuccessResponseBytes`（N-2）；直方图 M4。

## R-6 重试与幂等性的编译期治理

在生成器/分析器层（`Mud.HttpUtils.Analyzers`）新增规则：
接口方法声明 `[Retry]` 且 HTTP 方法为非幂等、且未显式 `AllowNonIdempotent = true` → 报 Warning（#12 的编译期闭环）。
**修订**：#12 实施时已在 Generator 侧加 `HTTPCLIENT020`（Warning）覆盖最小需求；R-6 剩余部分
（独立分析器包、跨项目规则）仍属 M4。

**建议版本**：M4（#12 已在 M2 提供 Generator 级最小实现）。

## R-7 AOT 一致性守卫

新增分析器规则：禁止在核心路径新增未标注的反射调用；
对 `#if NETSTANDARD2_0 / #else` 分支中**语义不等价**的实现（如 #20 的字符串猜测）给出提示。

**建议版本**：M4。

## R-8 `ValidateUrlAsync` 异步化（#8 的遗留项）

#8 M2 只做 DNS TTL + 工厂竞态治理；把 `ValidateUrl` 全调用链异步化
（`EnhancedHttpClient.ValidateRequest` 等同步调用点改造）列入本项。

**建议版本**：M4。
