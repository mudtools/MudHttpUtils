## 一、总体判断

**安全设计已达标，工程纪律问题突出。**

- 22 条历史锚点中 **17 条已在前序批次修复完毕**（逐条复核了修复后代码）。越权默认拒绝、租户 bind-once 守卫、scope 键单射化、恢复去重有界化、Dispose 链完整性等关键安全面**未发现跨租户令牌泄漏路径**。
- 剩余 20 项中，**真正具备"框架缺陷"性质的只有 1 项**（P0-1，跨 TFM 能力误用 ⇒ net6.0 宿主启动即崩）；其余集中在**边界值处理、跨 TFM 行为漂移、并发状态机遗漏点、文档边界未闭合**。
- 最有价值的发现是一个**结构性工程问题**：**测试矩阵无法覆盖其自身声称支持的目标框架**（详见 P0-1「为何测试未发现」）。修复方案必须先补这个能力缺口，否则同类问题会持续逃逸。

### 修复策略

1. **先补能力缺口，再修缺陷。** P0-1 的根因不是"写错了一个 `#if`"，而是"没有任何机制阻止在错误的 TFM 上使用新能力"。批次 A 与批次 F 必须同批交付。
2. **破坏性变更全部收敛进未发布的 `3.0.0`**。`Directory.Build.props` 的 `<Version>3.0.0</Version>` 与 `CHANGELOG.md`「3.0.0（2026-10-01）」表明 3.0.0 尚未发布（首个正式版为 2.0.5），此刻是收纳破坏性变更的**唯一低成本窗口**。
3. **每项修复必须带"能复现原缺陷"的测试**，不接受"修复后无新增测试"，不接受"仅靠快照文本固定行为"（对应 P1-9）。
4. **不引入新的公共 API 面**，唯一例外是 P1-8 的 `RequireSingletonAppServices`（与既有 `Require*` 开关同构，不新增概念），且已论证替代方案不可行。

## 四、架构决策记录（ADR 级）

### ADR-1：删除 keyed 路径，而非收紧 TFM 守卫

**决策**：**方案 2（删除）为主，方案 1（收紧守卫）为兜底。**

| 方案 | 内容 | 评价 |
| --- | --- | --- |
| 方案 1 | 3 处 `#if NET6_0_OR_GREATER` → `NET8_0_OR_GREATER` | 改动最小，但保留两条语义重复的解析路径 |
| **方案 2（推荐）** | 按 `EnhancedHttpClientFactory.cs:62-76`（L-6 注释）自身得出的结论，**删除 keyed 注册与 net6 回退**，`IEnhancedHttpClientFactory.CreateClient(name)` 成为唯一入口 | 净减代码，一并解决 P0-5 |

**采纳理由**

1. L-6 注释已论证 keyed 路径的**唯一价值**（配置热更新可失效）由 `EnhancedHttpClientFactory._clientCache` + `InvalidateAll()` 提供，keyed 注册是**纯冗余**。
2. 删除后 P0-5（keyed / 非 keyed 胜者矛盾）**自动消失** —— 只剩一条路径，MT-23 注释所述"两处缓存偶然一致"的脆弱性随之消失。
3. 框架自有解析路径**本就不依赖 keyed**：`HttpClientResolver.cs:46` 走 `_clientFactory.CreateClient(name)`。keyed 仅被测试与 `Mud.HttpUtils.Resilience` 的装饰逻辑引用，二者都可迁移。
4. 少一个 `#if` 分支 ⇒ 少一个 TFM 能力误用点。

**迁移路径**

| 受影响面 | 迁移 |
| --- | --- |
| net6.0 / net7.0 消费方 | 无影响（这些 TFM 上 keyed 从来不可用，当前是**启动即崩**） |
| net8.0+ 消费方用 `GetKeyedService<IEnhancedHttpClient>(name)` | 改为注入 `IEnhancedHttpClientFactory` 后 `CreateClient(name)`；`Invalidate(name)` / `InvalidateAll()` 一并可用（能力等价且更强） |
| `Mud.HttpUtils.Resilience` 的 `DecorateKeyedServices` | net8+ 保留（宿主可能自行 keyed 注册）；net6/7 无 keyed 描述符可装饰，天然 no-op |
| 生成器 | 零变更（生成代码注入类型级 `IEnhancedHttpClient`，由 `TryAddTransient` 回指工厂） |

**破坏性标注**：⚠️ **BC-32** —— net8.0+ 消费方的 `GetKeyedService<IEnhancedHttpClient>(name)` 将编译失败。

**兼容措施**：`RegisterNamedClient` 检测到"宿主已自行 keyed 注册 `IEnhancedHttpClient`"时记一条 `Warning`（复用现有 `:225-235` 的探测位置），让"删除"对已误用 keyed 的宿主**可诊断**而非静默失效。

### ADR-2：scope 缓存键空间用「保留哨兵」隔离，而非全量重构

| 方案 | 做法 | 迁移代价 | 评价 |
| --- | --- | --- | --- |
| (a) 全量改键空间 | 所有键加 `\u0000` 前缀 | **最大**：所有 `ITokenCache` / `ITokenStore` / 分布式条目全部失效 | ✗ 过度 |
| **(b) 保留哨兵（推荐）** | `DefaultKey = "\u0000"`，并把 `U+0000` 纳入 `EscapeElement` 转义集合 | **最小**：仅"无 scope"这一个键的值改变；带 scope 的键**完全不变** | ✓ |
| (c) 长度前缀编码（复用 `CompositeKey`） | 全量改键空间 | 同 (a) | ✗ 过度 |

**采纳 (b)**：语义前提是"真实 scope 名不可能含控制字符"，与仓库既有约定一致（`AppKeyValidator` 拒绝控制字符；`EnsureValidUserId` 拒绝 C0）。单射性证明：`Escape(x)` 的输出不含裸 `U+0000`，而 `DefaultKey` 含裸 `U+0000` ⇒ 不相交。

**破坏性标注**：⚠️ **BC-33** —— 分布式缓存中**默认作用域**条目的键由 `"default"` 变为 `"\u0000"`，升级后首次访问重新获取令牌（**幂等，无正确性影响**）。带 scope 的条目不受影响。

### ADR-3：短 TTL 令牌的有效期钳位采用「margin ≤ TTL/2」

| 方案 | 公式 | 问题 |
| --- | --- | --- |
| (a) 硬下界 | `ttl = Max(expires_in - margin, 1)` | 1 秒 TTL 令牌仍会每请求刷新 |
| **(b) 比例钳位（推荐）** | `margin' = Min(margin, Max(0, expires_in / 2))` ⇒ `ttl ≥ expires_in/2` | 无 |
| (c) 改判定侧 | 让 `EffectiveThresholdSeconds` 容忍负 TTL | 治标：缓存条目"刚签发即在阈值内"，LRU / 清理逻辑仍误判 |

**采纳 (b)**，并额外要求：**钳位发生时必须可观测**（一次性 `LogWarning`）。理由：本仓库对"静默失效面"的一贯立场（`ConcurrentDictionaryTokenCache` 的 S1-5 诊断、`UrlValidator` 的 MT-28 警示）都要求"降级必须留痕"，此处必须一致。

### ADR-4：把「TFM 能力守卫」建成编译期机制而非人工约定

1. **立即**：统一到 `NET8_0_OR_GREATER`（若采纳 ADR-1 则删除相关代码）。
2. **机制**：新增 `TfmCapabilityGuardTests` —— 维护一张 `{ API → 最低 TFM }` 登记表，对全仓 `#if` 表达式做文本扫描，发现"guard 允许但 API 需要更高 TFM"即失败。这只是**廉价的早期门禁**。
3. **终局验证**：`test-strategy.md` 的「net6.0 真实容器测试」才是 ADR-1 的终局验证，静态扫描不能替代它。
4. **文档化**：把第二节的「TFM 能力矩阵」落入 `Generator/README.md` 或新建 `docs/architecture/tfm-matrix.md`，作为新增贡献者必读。

## 七、明确不做（避免过度设计）

1. **不引入 keyed services 的 net6/net7 polyfill。** keyed 是**容器能力**（`IServiceProvider` 实现级），无法用扩展方法 polyfill；即便能，也等于自造一个与 .NET 8 语义不同的私有 keyed 系统，跨 TFM 行为分叉风险远大于收益。
2. **不新增 `IAppManager<>` / `IAppContextHolder` 的 captive dependency 硬失败。** 框架无法可靠判定"宿主是否有意为之"，只做启动期 Warning + 既有 `Require*` 开关控制的 Fatal。
3. **不为 `UseDefaultAppScope` 增加强制授权判定。** 默认应用是宿主自选的受信任目标；3.0.0 CHANGELOG「明确不做」已确立此边界。本轮只做**文档边界闭合**。
4. **不重构 `AsyncLocalAppContextSwitcher.BeginScope` 的归属判定。** 设计约定 6 已豁免，且 `AppManagementP1Tests.CrossFlowDispose_*` 有真实断言；审查已核实该兜底分支无并发缺陷。
5. **不引入 `IServiceCollection` 之外的 DI 校验框架。** 成本高于收益。
6. **不为 `ScopeKeyBuilder` 记忆化做深度性能重构。** 仅修正文档表述（P2-3），实际收益不足以支撑改动风险。
7. **不实现"框架自动 Dispose 被替换 / 被移除的上下文"。** 在途请求可能正持有旧上下文的 `HttpClient` / `TokenManager`，`RemoveApp` 的 NEW-MA-01 注释已记录过一次这样的回归。所有权归宿主是唯一安全默认（文档化见 P1-2）。

> 目标：在补上「跨 TFM 运行时行为不可验证」这一**结构性缺口**的前提下，为 20 项修复提供"能复现原缺陷"的测试。

### A.1 核心问题：测试矩阵无法验证其自身声称支持的 TFM

**现象**　`Tests/Mud.HttpUtils.Client.Tests.csproj` 含 `net6.0` 目标，但其加载的容器程序集实测为 `bin/Debug/net6.0/Microsoft.Extensions.DependencyInjection.dll -> 8.0.1`，即 **NuGet 的 8.0.1**，而非真实 net6.0 宿主从 `Microsoft.AspNetCore.App` 6.0 加载的 **6.0.x**。因此凡"依赖容器运行时能力"的断言（keyed services 是典型）在 net6.0 目标下**永远不会失败** —— 这正是 P0-1 逃逸的原因。

**已验证的复现方式**　最小控制台工程（`net6.0` + `Microsoft.Extensions.DependencyInjection` **6.0.1** + `Abstractions` **8.0.0**，与 `Mud.HttpUtils.Client.csproj:32-40` 的引用组合一致）：

```csharp
var services = new ServiceCollection();
services.AddKeyedTransient<IThing>("order-api", (sp, k) => new Thing("KEYED:" + k));
services.TryAddTransient<IThing>(sp => new Thing("DEFAULT"));
var sp = services.BuildServiceProvider();   // <- 抛异常
```

实测输出：

```
System.InvalidOperationException: This service descriptor is keyed.
Your service provider may not support keyed services.
   at Microsoft.Extensions.DependencyInjection.ServiceDescriptor.get_ImplementationFactory()
```

两种情形均复现：(A) 仅 keyed 注册；(B) 完整复刻 `RegisterNamedClient` 的注册顺序。

### A.2 F-1：net6.0 真实容器测试层（新建工程）

**工程形态决策**

### A.3 F-2：`TfmCapabilityGuardTests`（静态门禁）

**职责**　在 CI 中以**毫秒级**拦住"在错误的 TFM guard 下使用高版本 API"，属**早期门禁**，不能替代 A.2 的运行期验证。

**实现要点**

1. 维护一张登记表：

```csharp
// API -> 首次可用的 TFM。key 为 API 关键字，value 为最低 TFM 常量名。
private static readonly TheoryData<string, string> ApiMinTfm = new()
{
    { "AddKeyedSingleton", "NET8_0_OR_GREATER" },
    { "AddKeyedTransient", "NET8_0_OR_GREATER" },
    { "AddKeyedScoped",    "NET8_0_OR_GREATER" },
    { "GetKeyedService",         "NET8_0_OR_GREATER" },
    { "GetRequiredKeyedService", "NET8_0_OR_GREATER" },
    { "DecorateKeyedServices",   "NET8_0_OR_GREATER" },
    // 每新增一个 netX-only API 须登记
};
```

2. 扫描仓库 `**/*.cs`（排除 `bin` / `obj` / `Demos`），对每个 `#if <GUARD>` 块：若块内出现登记表中的 API，而 `<GUARD>` 的 TFM **低于**该 API 的最低 TFM，则失败，输出文件:行号 + 建议 guard。
3. 复用既有测试的**仓库根定位**手法（参考 `Tests/Mud.HttpUtils.Tests/PolyfillBoundaryGuardTests.cs:27-38`）。

**局限（必须在测试注释中写明）**　静态扫描**无法**判断跨文件 / 跨项目的间接使用，也无法覆盖运行时反射。它是"廉价早期门禁"，**不是** ADR-1 的验证手段；验证手段始终是 A.2。

- **net6.0 / net7.0 目标上框架不可用（BC-32）**：`AddMudHttpClient` 曾在 `#if NET6_0_OR_GREATER` 内注册 keyed `IEnhancedHttpClient`，而 keyed services 是 **.NET 8 才引入的容器能力** —— .NET 6/7 容器在 `BuildServiceProvider()` 遍历描述符时即抛 `InvalidOperationException: This service descriptor is keyed`。**任何 net6.0 宿主调用 `AddMudHttpClient` / `AddMudHttpClientsFromConfiguration` / `AddMudHttpGeneratedClient` / `AddMudHttpResilienceDecorator(Action<>)` 均在启动期崩溃。** 现按 L-6 结论删除 keyed 注册与 net6 回退，`IEnhancedHttpClientFactory.CreateClient(name)` 成为命名客户端的唯一解析入口（详见 ADR-1）。
  - **迁移**：net8.0+ 消费方若使用 `GetKeyedService<IEnhancedHttpClient>(name)`，改为注入 `IEnhancedHttpClientFactory` 后调用 `CreateClient(name)`；`Invalidate(name)` / `InvalidateAll()` 一并可用。net6.0 / net7.0 消费方无迁移成本（当前为启动即崩状态）。
  - 附：`Mud.HttpUtils.Resilience` 的 `AddMudHttpResilienceDecorator(Action<>)` 内 `DecorateKeyedServices` 的 guard 同步由 `NET6_0_OR_GREATER` 修正为 `NET8_0_OR_GREATER`（与同文件 `IConfiguration` 重载一致）。
  - 新增测试工程 `Tests/Mud.HttpUtils.LegacyTfm.Tests`（显式引用 6.0.x 容器）作为回归门禁。
- **`DefaultAppManager.RegisterApp` 并发覆盖可复活已删除应用**：`TryAdd` 判型与索引器赋值是两段非原子操作，窗口内若 `RemoveApp` 抢先移除该键，索引器（add-or-update）会把键重新插入 —— 已撤销应用的凭据重新可被 `GetApp` / `UseAppScope` / `GetDefaultApp` 取用，且事件被误报为 `Updated`（实际是 `Added`）。MT-08 的 CAS 修复此前只覆盖 `UpdateApp` / `UpdateAppAsync`，现 `RegisterApp` 同样改为单次 CAS（`TryAdd` → `TryUpdate` → 失败抛错）。
  - 行为变化仅在"并发 `RegisterApp` 与 `RemoveApp` 同一 key"这一此前未定义的场景。
- **短 TTL 令牌签发即被判废**：`StandardOAuth2TokenManager.CalculateExpire` 直接计算 `now + (expires_in - ExpirySafetyMarginSeconds)`，当 `expires_in <= 60`（默认 margin）时 `Expire` 落在过去；而 `TokenExpiryPolicy.EffectiveThresholdSeconds` 在 `ttl <= 0` 时回退到配置阈值、不再钳位 —— 令牌缓存永不命中，**每个请求都触发一次完整刷新**，令牌端点 QPS 随流量线性放大。现按 `min(margin, expires_in / 2)` 钳位，并在钳位发生时记一次 `Warning`（此前完全静默）。`expires_in > 2 × margin` 时行为与修复前完全一致。

#### 安全（Security）

- 命名客户端解析入口收敛后，配置热更新的唯一失效通道为 `IEnhancedHttpClientFactory.InvalidateAll()`（由 `EnhancedHttpClientFactoryChangeNotifier` 订阅 `IOptionsMonitor` 驱动），`AllowCustomBaseUrls` / `BaseAddress` / `DefaultHeaders` 的热更新语义**不变**且不再依赖 keyed 缓存。
- 重复注册同一 `clientName` 且宿主已自行 keyed 注册 `IEnhancedHttpClient` 时，改为记一条结构化 `Warning`（此前为 `Debug.WriteLine`，Release 下不可见），提示迁移到 `IEnhancedHttpClientFactory`。

### 3.0.1（其余项）

- 用户令牌失效路径（`InvalidateCachedUserAccessToken` / `InvalidateUserAccessTokenInCache`）改为写时复制，消除并发读到半失效条目的风险；同时修正"已清零的 `AccessTokenExpireTime` 使绝对过期降级为滑动过期"导致已作废条目被续命的问题。
- `netstandard2.0` 的 `TokenRefreshBackgroundService` 此前声明 `_retryDelay` 后**从未使用**，`RetryDelaySeconds` 配置项在该 TFM 上完全无效；现实现"失败周期用 `RetryDelaySeconds`、成功周期用 `RefreshIntervalSeconds`"的一次性跳调度，并给出 TFM 行为对照表。
- 后台刷新注册表的默认键此前是类型全名，导致**同类型的不同实例**（典型：多租户各一个）静默互相覆盖、被覆盖者的令牌永不参与后台刷新且无任何日志；现改为「类型全名 + 序号」并在覆盖不同实例时记 `Warning`。
- `RevokeTokenAsync` 此前吞掉 `OperationCanceledException`（把"被取消"伪装为"IdP 拒绝撤销"），现按 `ResolveClientSecretAsync` 同口径传播取消。
- `MudHttpAppManagementOptions` 新增 `RequireSingletonAppServices`（默认 `false`）：`IAppContextHolder` / `IAppManager<>` 会被 Singleton 的 `IHttpRequestExecutor` 一次性解析，注册为 Scoped / Transient 时构成 captive dependency（后续实例不可见 + IDisposable 永不释放）。启动期自检新增该检查，判定基于 `IServiceCollection` 声明数据（零反射、AOT 友好）。**默认仅告警，不阻断启动。**
- `AddMudHttpClientsFromConfiguration` 在配置节不存在时仅有 `Debug.WriteLine`（Release 下完全静默，且会连带跳过全部基础设施注册）；新增启动期可观测探针，仍不阻断启动。
- 生成器守卫顺序新增语义级断言（`ConstructorGeneratorGuardOrderTests`），此前越权用例为自证式断言（手工复制守卫链），生成器顺序回归时仍会全绿。
- 文档：默认应用切换（`UseDefaultAppScope`）**不参与** `IAppAccessAuthorizer` 判定这一刻意不对称的边界已闭合；`IAppManager` 五个成员补齐"上下文所有权归宿主，框架永不 Dispose"与"`RegisterApp` 不执行异步初始化"两条契约；`ConfigurationChanged` 补退订责任说明。
- CHANGELOG 未列出的其余项见 `.docs/fix-items-d-e.md`（P2-1 ~ P2-6，目标 3.1.0）。
