**评估日期**：2026-07-06
**评估范围**：Mud.HttpUtils 全项目（Abstractions / Client / Resilience / Attributes / Generator / OpenTelemetry）
**评估依据**：[可观测性接入指南.md](./可观测性接入指南.md) 文档承诺 + 源代码静态分析 + 测试验证

## 0. 评估背景

v1 方案（[可观测性功能完善方案v1.md](./可观测性功能完善方案v1.md)）已实施完成三个阶段：

本 v2 方案的目的是**以接入指南文档为基准**，验证已实现的功能是否与文档承诺一致，识别逻辑断链与遗漏埋点，并制定完善方案。

## 3. 发现的差距与问题

### 3.1 P0 级差距（与接入指南承诺直接冲突，必须修复）

#### G1：Mud 自定义 Span 属性未写入 Activity

**指南承诺**（第 6.1 节 Span 属性表）：

| 属性 | 来源 | 示例 |
|------|------|------|
| `mud.http.client_name` | Mud 自定义 | `myApi` |
| `mud.http.retry.count` | Mud 自定义 | `2` |
| `mud.http.cache.hit` | Mud 自定义 | `true` |
| `mud.token.manager_key` | Mud 自定义 | `feishu` |
| `mud.http.circuit_breaker.state` | Mud 自定义 | `Open` |
| `mud.correlation_id` | Mud 自定义 | `0a1b2c3d...` |

**实际实现**：

| 属性 | 常量定义 | 是否 SetTag 到 Activity | 问题 |
|------|:--------:|:-----------------------:|------|
| `mud.http.client_name` | ✅ MudClientName | ✅ [MudHttpObservability.cs:58](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/Observability/MudHttpObservability.cs#L58) | 正常 |
| `mud.http.retry.count` | ✅ MudRetryCount | ❌ **从未设置** | `SetRetryCount()` 方法存在于 [MudHttpObservability.cs:248](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/Observability/MudHttpObservability.cs#L248)，但全项目无任何调用方；PollyResiliencePolicyProvider 的 onRetry 回调未调用此方法，重试次数仅写入指标维度，不回传到请求属性，Activity 上永远不出现此 tag |
| `mud.http.cache.hit` | ✅ MudCacheHit | ❌ **从未设置** | CacheResponseInterceptor 只写指标和 DiagnosticSource，未设置当前 Activity 的 tag |
| `mud.token.manager_key` | ✅ MudTokenManagerKey | ❌ **从未设置** | TokenManagerBase.RecordTokenRefresh 只写指标和 DiagnosticSource，未设置当前 Activity 的 tag |
| `mud.http.circuit_breaker.state` | ✅ MudCircuitBreakerState | ❌ **从未设置** | CircuitBreakerStateObserver.SetState 只写 DiagnosticSource，未设置当前请求 Activity 的 tag |
| `mud.correlation_id` | ✅ MudCorrelationId | ❌ **从未设置** | CorrelationId 只写入 logger scope 字典（[MudHttpObservability.cs:292](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/Observability/MudHttpObservability.cs#L292)），未作为 Activity tag |

**影响**：用户按指南在 Jaeger 中展开 span 时，只能看到 `http.method`/`http.url`/`http.status_code`/`mud.http.client_name` 这 4 个属性，指南承诺的另外 5 个 Mud 自定义属性全部缺失。这直接违反文档承诺。

**修复方向**：
1. `mud.http.retry.count`：在 PollyResiliencePolicyProvider 的 onRetry 回调中调用 `MudHttpObservability.SetRetryCount(request, retryCount)`，并在 `MudHttpObservability.RecordResponse`/`RecordSuccessFromRequest` 中从请求属性读取并 `activity.SetTag(MudRetryCount, ...)`。
2. `mud.http.cache.hit`：在 CacheResponseInterceptor.TryGet 命中时，通过 `Activity.Current` 设置 tag。
3. `mud.token.manager_key`：在 TokenManagerBase.RecordTokenRefresh 中通过 `Activity.Current` 设置 tag。
4. `mud.http.circuit_breaker.state`：在 CircuitBreakerStateObserver.SetState 中通过 `Activity.Current` 设置 tag。
5. `mud.correlation_id`：在 `StartRequestActivity` 中生成 correlationId 并 `activity.SetTag(MudCorrelationId, correlationId)`，与 logger scope 共用同一值。

#### G2：Span 事件未以 Activity.AddEvent 记录

**指南承诺**（第 6.2 节 Span 事件表 + 第 10.6 节 FAQ）：

> "Mud.HttpUtils 的 ActivitySource 只创建一个出站请求 span，重试事件以 **Span Event** 形式记录在该 span 上。在 Jaeger UI 中展开 span 详情可见 `RetryOccurred` 事件。"

指南第 6.3 节 Jaeger 示例明确展示：
```
├─ Event: RequestStarted
├─ Event: RetryOccurred (retry_count=1, delay_ms=200)
├─ Event: RetryOccurred (retry_count=2, delay_ms=400)
├─ Event: RequestStopped (status_code=200, elapsed_ms=1234.5)
```

**实际实现**：

全项目搜索 `Activity.AddEvent` / `.AddEvent(` **零匹配**。所有 7 类事件只通过 `MudHttpDiagnosticListener.Instance.WriteIfEnabled()` 写入 DiagnosticSource，**未调用 `Activity.AddEvent()`**。

| 事件名 | DiagnosticSource 写入 | Activity.AddEvent |
|--------|:---------------------:|:-----------------:|
| RequestStarted | ✅ TracingDelegatingHandler | ❌ |
| RequestStopped | ✅ TracingDelegatingHandler | ❌ |
| RequestFailed | ✅ TracingDelegatingHandler | ❌ |
| RetryOccurred | ✅ PollyResiliencePolicyProvider | ❌ |
| CircuitBreakerStateChanged | ✅ CircuitBreakerStateObserver | ❌ |
| TokenRefreshed | ✅ TokenManagerBase | ❌ |
| CacheHit / CacheMiss | ✅ CacheResponseInterceptor | ❌ |

**影响**：
- DiagnosticSource 事件需要外部订阅者（APM 探针）才能消费；而 OTel SDK 默认不订阅 DiagnosticSource，只读取 ActivitySource。
- 通过 `AddMudHttpOpenTelemetry()` 接入的用户，在 Jaeger 中看不到任何 Span 事件，与指南承诺直接冲突。
- DiagnosticSource 与 Activity Event 是互补关系，不应只实现前者。

**修复方向**：在 MudHttpObservability 中新增 `AddActivityEvent` 辅助方法，在各埋点点同时写入 DiagnosticSource 和 Activity.AddEvent（当 `Activity.Current` 属于 MudHttpActivitySource 时）。ActivityEvent 的 tags 与 DiagnosticSource 负载字段保持一致。

### 3.2 P1 级差距（功能遗漏，应修复）

#### G3：TokenRecoveryDelegatingHandler 缺少子 Activity 与恢复指标

**v1 方案承诺**（第八节对接点表）：
> "TokenRecoveryDelegatingHandler | 增加 Activity 子 span `mud.token.recovery`；记录恢复成功/失败指标；迁移到 LoggerMessage | 中"

**实际实现**：
- `MudHttpActivitySource.ActivityNameTokenRecovery = "Mud.HttpUtils.Token.Recovery"` 常量已定义但**从未使用**
- TokenRecoveryDelegatingHandler 仅完成 LoggerMessage 迁移，**未创建子 Activity、未记录恢复指标**
- 全文件搜索 `StartActivity` / `ActivitySource` 零匹配（仅日志调用）

**影响**：令牌恢复流程（401 重试）在 Jaeger 中不可见，无法追踪恢复耗时与成败；恢复成功/失败无独立指标。

**修复方向**：在 TokenRecoveryDelegatingHandler.SendAsync 中创建 `MudHttpActivitySource.ActivityNameTokenRecovery` 子 Activity，设置 `mud.token.manager_key` tag，记录恢复耗时与结果；新增 `mud.token.recovery` Counter 指标（维度：token_manager_key, outcome）。

#### G4：TokenRefreshStatsCollector 保留期与窗口不匹配

**问题**：[TokenRefreshStatsCollector.cs](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Abstractions/HttpClient/Observability/TokenRefreshStatsCollector.cs) 中：
- 保留期固定：`s_retention = TimeSpan.FromMinutes(5)`（第 82 行）
- 窗口可配置：`WindowSeconds` 默认 300，可通过 `TokenRefreshHealthCheckOptions` 调整

若用户配置 `WindowSeconds = 600`（10 分钟），`GetSnapshot(600)` 会扫描最近 10 分钟的事件，但 `Trim()` 已在 5 分钟时裁剪，导致快照只含最近 5 分钟数据，**6-10 分钟前的事件丢失**，失败率计算偏低。

**影响**：自定义更大窗口的健康检查判定不准确。

**修复方向**：将保留期改为 `Math.Max(5分钟, 配置的最大窗口)`，或在 `AddMudHttpHealthChecks` 时将 `WindowSeconds` 传入 `TokenRefreshStatsCollector` 设置保留期；同时在文档中说明保留期约束。

#### G5：缺少可观测性端到端集成测试

**v1 方案承诺**（第七节）：
> "集成测试：在 Mud.HttpUtils.Integration.Tests 中增加 ObservabilityIntegrationTests：发起真实 HTTP 请求，验证 Activity 与指标产出"

**实际实现**：仅有单元测试（[ObservabilityTests.cs](file:///d:/Repos/MudHttpUtils/Tests/Mud.HttpUtils.Client.Tests/ObservabilityTests.cs) / [HealthChecksTests.cs](file:///d:/Repos/MudHttpUtils/Tests/Mud.HttpUtils.Client.Tests/HealthChecksTests.cs)），使用 ActivityListener / MeterListener 断言常量与采集逻辑，**无端到端测试**验证"真实 HTTP 请求 → span 含完整属性与事件 → 指标产出"的全链路。

**影响**：G1/G2 类问题（Span 属性/事件缺失）未被现有测试捕获，因为单元测试不验证 Activity.Tags / Activity.Events 的完整内容。

**修复方向**：在 `Tests/Mud.HttpUtils.Integration.Tests` 新增 `ObservabilityIntegrationTests.cs`，使用 `HttpClientFactory` + 本地服务器或 `WireMock.Net`，启用 ActivityListener + MeterListener，断言：
- span.Tags 包含指南承诺的全部 11 个属性
- span.Events 包含 RequestStarted/RequestStopped
- 重试场景下 span.Events 包含 RetryOccurred
- 指标值正确递增

### 3.3 P2 级差距（文档准确性 / 一致性优化）

#### G6：EnhancedHttpClientLogs 未使用 LoggerMessage 源生成器

**指南承诺**（第 4 节）：
> "Mud.HttpUtils 使用 `LoggerMessage` 源生成器（.NET 6+）实现零分配日志"

**实际实现**：[EnhancedHttpClientLogs.cs](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/EnhancedHttpClientLogs.cs) 在所有框架（含 .NET 6+）上均使用 `LoggerMessage.Define`，未使用 `[LoggerMessage]` 源生成器。仅 [MudHttpClientLog.cs](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/MudHttpClientLog.cs) 使用了源生成器 + Define 双轨。

**影响**：功能等价（Define 也是零分配），但与指南描述不完全一致；源生成器在编译期生成代码，比 Define 的运行时委托构建更优。

**修复方向**：将 EnhancedHttpClientLogs 迁移到 `[LoggerMessage]` 源生成器（.NET 6+）+ Define（netstandard2.0）双轨模式，与 MudHttpClientLog 保持一致。或修正指南措辞为"LoggerMessage 模式（源生成器或 Define）"。

#### G7：健康检查默认阈值比指南描述更严格

**指南描述**（第 7.3 节）：
> "Open 计数 > 1 → Unhealthy；HalfOpen > 1 → Degraded"

**实际实现**：`MudCircuitBreakerHealthCheckOptions` 默认 `MaxOpenCount = 0`、`MaxHalfOpenCount = 0`，即任何 Open 即 Unhealthy。指南第 7.4 节配置示例用 `MaxOpenCount: 1`，与描述一致。

**影响**：默认行为比指南描述更严格（更安全），但用户若不配置则可能困惑。

**修复方向**：修正指南第 7.3 节描述为"Open 计数 > MaxOpenCount（默认 0）→ Unhealthy"，明确默认值。

#### G8：CacheCounter 缺少 client_name 维度

**v1 方案**（第 6.2 节命名规范）列出 `mud.http.cache` 维度为 `client_name, outcome(hit/miss)`。

**实际实现**：[CacheResponseInterceptor.cs](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/CacheResponseInterceptor.cs) 只添加 `outcome` 和 `cache_key` 两个维度，**无 client_name**。

**影响**：多客户端场景下无法区分缓存命中率归属。接入指南第 5.1 节指标表未列 client_name，与指南不冲突，但与 v1 方案不一致。CacheResponseInterceptor 作为响应拦截器不持有 clientName 上下文（需通过请求属性传递）。

```csharp
// MudHttpObservability.cs 新增

/// <summary>
/// 将重试次数写入请求属性并同步到当前 Activity tag。
/// </summary>
public static void RecordRetryCount(HttpRequestMessage? request, int retryCount)
{
    if (request != null)
        TrySetProperty(request, RetryCountPropertyKey, retryCount);
    // 同步到当前 Activity（Polly 回调可能在请求 Activity 上下文内执行）
    Activity.Current?.SetTag(MudHttpActivitySource.Tags.MudRetryCount, retryCount);
}

/// <summary>
/// 在当前 Activity 上记录 Span 事件（同时写入 DiagnosticSource）。
/// 仅当 Activity.Current 属于 MudHttpActivitySource 时才添加 ActivityEvent。
/// </summary>
public static void AddActivityEvent(
    string diagnosticEventName,
    Func<object?> diagnosticPayloadFactory,
    string activityEventName,
    IEnumerable<KeyValuePair<string, object?>>? tags = null)
{
    // 写入 DiagnosticSource
    MudHttpDiagnosticListener.Instance.WriteIfEnabled(diagnosticEventName, diagnosticPayloadFactory);

    // 写入 Activity Event（仅 Mud Activity）
    var activity = Activity.Current;
    if (activity != null && IsMudActivity(activity))
    {
        var activityEvent = new ActivityEvent(activityEventName, tags: tags);
        activity.AddEvent(activityEvent);
    }
}

private static bool IsMudActivity(Activity activity)
    => activity.Source == MudHttpActivitySource.Instance;
```

#### 4.2.3 Polly 回调获取 HttpRequestMessage 的挑战

Polly v7 的 `onRetryAsync(outcome, timeSpan, retryCount, context)` 中 `context` 可通过 `Policy.Context` 传递请求。需在 ResilientHttpClient 调用 policy 前将 request 放入 context：

```csharp
// ResilientHttpClient 或 PollyResiliencePolicyProvider 调用处
var context = new Context
{
    ["__mud_request"] = request  // 或 request 的标识
};
await policy.ExecuteAsync(async ct => ..., context, cancellationToken);
```

> 若 ResilientHttpClient 调用链不便传递 request，可降级为仅通过 `Activity.Current` 设置 retry count tag（Polly 回调在请求线程执行时 Activity.Current 通常仍为请求 span），不写请求属性。此降级方案可覆盖 IHttpClientFactory + TracingDelegatingHandler 路径。

## 6. 关键风险与对策

| 风险 | 等级 | 对策 |
|------|:----:|------|
| **Polly 回调中 Activity.Current 不可用**：onRetry 回调可能在请求线程外的上下文执行（如 Task 调度），Activity.Current 为 null | 中 | 通过 Policy.Context 传递 request 引用；或在 ResilientHttpClient 调用 policy 前 capture Activity 到局部变量，回调中显式使用；降级方案：仅写 DiagnosticSource 不写 Activity Event（保持现状） |
| **Activity.AddEvent 性能开销**：每次 AddEvent 会分配 ActivityEvent 结构 | 低 | 仅在 `activity != null && IsMudActivity(activity)` 时调用；无监听器时 StartActivity 返回 null，天然短路 |
| **netstandard2.0 的 ActivityEvent API**：ActivityEvent 在 netstandard2.0 上通过 System.Diagnostics.DiagnosticSource 包可用 | 低 | 已引用该包 >= 8.0；验证编译通过 |
| **Activity.Current 跨模块污染**：TokenManagerBase 可能在后台服务上下文执行（无请求 Activity） | 低 | `AddActivityEvent` 方法已检查 `IsMudActivity(activity)`，非 Mud Activity 不写入 |
| **集成测试环境依赖**：端到端测试需真实 HTTP 服务器 | 低 | 使用 `HttpMessageHandler` mock 或 `WireMock.Net`，无需真实端口 |
