## #1 🔴 执行器路径响应体无限读取（`MaxExceptionContentLength` 形同虚设）

### 问题定位

```
Mud.HttpUtils.Client/HttpClient/DefaultHttpRequestExecutor.cs
  120:  using var response = await httpClient.SendRawAsync(request, cancellationToken)...
  125:      var errorContent = await ReadContentAsync(response, cancellationToken)...   // 全量读入
  126:      _logger.LogError("HTTP 请求失败: 状态码={StatusCode}, URI={RequestUri}, 响应内容={ErrorContent}", ...);
  136:  var rawContent = await ReadContentAsync(response, cancellationToken)...          // 成功路径同样全量
  653:  private static async Task<string> ReadContentAsync(...) => ReadAsStringAsync      // 全量读取本体
  666:  private static string TruncateErrorContent(string content, int? maxLength)      // 读完之后才截断
```

`TruncateErrorContent` 只在字符串**已完整进入托管堆之后**缩减副本，既不阻止 OOM，也未减少峰值内存。

### 修复设计

#### 1.1 新建共享的限量读取工具类

新建 `Mud.HttpUtils.Client/Helpers/LimitedContentReader.cs`（`internal static`）：

```csharp
internal static class LimitedContentReader
{
    /// <summary>
    /// 以字符数上限读取 HttpContent。返回 (content, truncated)。
    /// 无论 Content-Length 是否存在，都不会读取超过 maxChars 个字符（maxChars <= 0 表示不限制）。
    /// </summary>
    public static async Task<(string Content, bool Truncated)> ReadLimitedStringAsync(
        HttpContent content, int maxChars, CancellationToken cancellationToken)
    {
        // 1) 已知长度且为 0 → 快路径
        if (content.Headers.ContentLength is 0)
            return (string.Empty, false);

        // 2) StreamReader 按"字符"读取（多字节字符不会被切断），
        //    detectEncodingFromByteOrderMarks: true 顺带解决 BOM（见 #29）
        //    读 maxChars 个字符后再尝试读 1 个字符判断是否截断
        //    截断时追加 "...[已截断]"
        //    ns2.0 分支：ReadAsStreamAsync() 无 ct 重载 → ReadAsync(buffer, 0, len, ct)
    }
}
```

**实现要点**

- `maxChars <= 0` 表示不限制（`MaxExceptionContentLength = 0`/负 的语义）。
- **字符 vs 字节**：`EnhancedHttpClient.CopyUpToAsync`（`EnhancedHttpClient.cs:1774`）是**字节级**限量拷贝
  （服务 #2 的克隆缓冲与 Debug 日志体），与 #1 的**字符级**读取是两种语义。二者保留各自方法，
  但统一放在 `LimitedContentReader`（或 `Helpers`）下，消除"限量读取"实现四处散落的局面。
- 必须处理 `netstandard2.0` 无 `ReadAsStreamAsync(ct)` 的分支（沿用仓库既有 `#if` 约定）。

#### 1.2 改造 `DefaultHttpRequestExecutor`

```csharp
// 构造：统一默认值（N-1）
private readonly int _maxErrorChars = maxExceptionContentLength
    ?? HttpExecutionConstants.DefaultMaxExceptionContentLength;   // 10240

// 错误路径（L125）
var (errorContent, _) = await LimitedContentReader
    .ReadLimitedStringAsync(response.Content, _maxErrorChars, cancellationToken)
    .ConfigureAwait(false);
// 日志中的 URI 走 #5 的脱敏；错误内容过 Sanitize
```

#### 1.3 成功路径（**不可截断**）

`SendAndDeserializeAsync:136` 的成功响应体**必须全量读取**，否则反序列化被破坏。
此处只做两件事：

1. 语义上保持全量读取（`maxChars: 0`），实现上可直接保留 `ReadContentAsync`（统一入口非必需，避免无谓改动）；
2. 预留 `MaxSuccessResponseBytes` 守卫钩子（M2 落地，见 02 册 N-2）。

### 兼容性

- 未发布：无兼容义务。`ApiException.Content` 在错误路径统一为默认 10240 截断（N-1 语义）。
- 成功路径行为**不变**。

### 验收

- 用例：Stub 返回 100 MB 且**无 `Content-Length`** 的 500 响应 → 断言 `ApiException.Content.Length <= 10240 + 后缀长度`，且进程工作集无异常增长（需 T-0.2 的 StubHttp chunked 能力）。
- 用例：正常 2xx 大响应（> 10 MB）反序列化**仍成功**（防回归）。

## #2 🔴 请求克隆在分块传输下无大小上限、无取消令牌

### 问题定位

```
Mud.HttpUtils.Resilience/HttpRequestMessageCloner.cs
   19:      var contentLength = request.Content.Headers.ContentLength;
   20:      if (contentLength.HasValue && contentLength.Value > maxContentSize)   // ← 仅声明长度时校验
   22:          throw new InvalidOperationException(...);
   32:      var contentBytes = await request.Content.ReadAsByteArrayAsync()...     // ← 无上限、无 CancellationToken
```

`TryCloneAsync`（`:58-68`）吞 `InvalidOperationException` 返回 null —— 但**注意：当前代码库中
`TryCloneAsync` 无任何调用方**（仅 README 提及），`ResilientHttpClient` 用的都是 `CloneAsync`。

### 修复设计

```csharp
public static async Task<HttpRequestMessage> CloneAsync(
    HttpRequestMessage request,
    long maxContentSize,
    CancellationToken cancellationToken = default)      // ← 新增，默认参数保持源码兼容
{
    if (request == null) throw new ArgumentNullException(nameof(request));

    if (request.Content != null)
    {
        byte[]? contentBytes = null;
        if (maxContentSize >= 0)
        {
            // 按 maxContentSize + 1 限量缓冲，chunked/伪造 Content-Length 均不会多读
            var (bytes, truncated) = await LimitedBufferAsync(
                request.Content, maxContentSize, cancellationToken).ConfigureAwait(false);
            if (truncated)
                throw new InvalidOperationException(
                    $"请求体大小超过最大克隆限制 ({maxContentSize:N0} 字节)。" +
                    "大文件上传场景建议禁用重试策略或调整 MaxCloneContentSize。");
            contentBytes = bytes;
        }
        else
        {
            contentBytes = await request.Content.ReadAsByteArrayAsync(cancellationToken).ConfigureAwait(false);
        }
        // 仅给 clone.Content 赋值，不得修改入参 request
        clone.Content = new ByteArrayContent(contentBytes);
        // …拷贝 Content 头
    }
}
```

**关键细节**

1. **`maxContentSize < 0` 表示不限制**：`ResilienceOptions.MaxCloneContentSize` 文档已声明 `-1` 为不限，必须尊重。
2. **不得修改入参请求**：只对 `clone.Content` 赋值（`ReadAsByteArrayAsync` 本身会触发 BCL 缓冲，行为与现状等价）。
3. **异常类型保持不变**：仍抛 `InvalidOperationException`。超限时的**实际后果**由调用方决定：
   - 全局路径 `ResilientHttpClient.ShouldSkipRetry:74-87`（发送前按 `Content-Length` 预判）→ 走
     `ExecuteWithoutRetryAsync`（保留超时+熔断，跳过重试）——**这是现状已有的降级，不是新引入的行为**；
   - 克隆阶段才发现超限（Content-Length 缺失）→ `InvalidOperationException` 上抛为普通失败。
     如需与全局路径一致的"超限降级为不重试"，应在 `ExecuteWithCloneAsync` 内 catch 后改走
     `ExecuteWithoutRetryAsync`（可选增强，见 #19 改造时一并处理，避免二次改动）。
4. **取消令牌**：`LimitedBufferAsync` 内部所有 `ReadAsync` 透传 `cancellationToken`；
   ns2.0 用 `ReadAsync(buffer, 0, len, ct)`。
5. 调用方同步更新：`ResilientHttpClient.cs:121/221/259` 与 `ResiliencePolicyResolver.cs:79` 传入 `ct`（后者见 N-4）。

### 验收

- 用例：`Content-Length` 为 null、`MaxCloneContentSize = 1024`、实际 1 MB 请求 → 断言抛 `InvalidOperationException`。
- 用例：克隆过程中取消 `CancellationToken` → 断言抛 `OperationCanceledException`。
- 用例：断言克隆后**原请求未被修改**（`Content` 引用与头部不变）。

### 修复设计

```csharp
internal static void CopyMetadata(HttpRequestMessage source, HttpRequestMessage target)
{
    target.Version = source.Version;
#if NET5_0_OR_GREATER
    target.VersionPolicy = source.VersionPolicy;
#endif

#if NETSTANDARD2_0
    foreach (var kvp in source.Properties)
        target.Properties[kvp.Key] = kvp.Value;
#else
    // net5+ Options 与 Properties 都拷：
    // 仓库自身两者都在用（EnhancedHttpClient.cs:947/949 写 __mud_captured_request_content；
    // MudHttpObservability.cs:311-323 TryGetProperty 双查）
    foreach (var option in source.Options)
        target.Options.TryAdd(option.Key, option.Value);
    foreach (var kvp in source.Properties)
        target.Properties[kvp.Key] = kvp.Value;
#endif
}
```

### 兼容性

未发布：无兼容负担，直接修正（原方案的 `PreserveVersionPolicyOnRetry` 逃生舱**不再需要**——
保留 `VersionPolicy` 本来就是正确语义）。

### 验收

- 用例：`request.Version = 2.0; request.VersionPolicy = RequestVersionExact;` 触发一次重试 → 断言克隆请求的 `VersionPolicy == RequestVersionExact`。
- 用例（ns2.0 专项）：设置 `request.Properties["k"] = v` → 断言克隆后 `Properties` 与 `client_name`/`SkipResilience` 等键可读取。

## #4 🔴 `UrlValidator` 静态可变白名单无锁 + 全局污染

### 问题定位

```
Mud.HttpUtils.Client/Helpers/UrlValidator.cs
   11:  private static readonly HashSet<string> _allowedDomains = new(...);   // 非线程安全集合
   15:  private static readonly ConcurrentDictionary<string, IPAddress[]> _dnsCache = new();  // 无 TTL（见 #8）
   42:  ConfigureAllowedDomains: _allowedDomains.Clear(); foreach(...) Add()  // 清空→逐个加，存在空窗
  253-270: AddAllowedDomain / RemoveAllowedDomain 静态可变                     // 同样无锁
```

- 并发 `Clear()/Add()` 与 `Contains()` 会抛 `InvalidOperationException: Collection was modified`，或读到空集导致**全量请求被拒**。
- 进程级静态状态 → 多租户 / 多命名客户端互相污染。

### 修复设计（分两步，M1 只做第 1 步）

#### 步骤 1（M1，低风险）：静态门面 + 不可变快照

**采用"构造新 HashSet + Volatile.Write 原子交换"**（不引入 `System.Collections.Immutable`，零新增依赖）：

```csharp
public static class UrlValidator
{
    private static HashSet<string> _allowedDomains = CreateDefaultSet();

    public static void ConfigureAllowedDomains(IEnumerable<string> domains)
    {
        if (domains == null) throw new ArgumentNullException(nameof(domains));
        var newSet = new HashSet<string>(StringComparer.OrdinalIgnoreCase);
        foreach (var d in domains)
            if (!string.IsNullOrWhiteSpace(d)) newSet.Add(d.Trim());
        Volatile.Write(ref _allowedDomains, newSet);   // 原子替换，无空窗
    }

    private static HashSet<string> Snapshot => Volatile.Read(ref _allowedDomains);
    // AddAllowedDomain / RemoveAllowedDomain：Snapshot.CopyTo → 新集合 → Volatile.Write
}
```

- 读取方只读不写（`Contains`/遍历），快照期间安全；一次性替换消除"清空后逐个添加"的空窗。
- `GetAllowedDomains` 返回快照的只读包装（`IReadOnlyCollection`），继续满足公共 API 契约。

#### 步骤 2（M3/Roadmap R-3）：下沉为 DI 实例服务

```csharp
public interface IUrlValidator                      // 放 Mud.HttpUtils.Abstractions
{
    void ValidateUrl(string? url, bool allowCustomBaseUrls = false);
    void ValidateBaseUrl(string? baseUrl, bool allowCustomBaseUrls = false);
}

public sealed class UrlValidatorOptions             // 支持 IOptionsMonitor 热更新
{
    public HashSet<string> AllowedDomains { get; set; } = new(StringComparer.OrdinalIgnoreCase);
    public bool AllowLoopback { get; set; } = true;
    public TimeSpan DnsCacheTtl { get; set; } = TimeSpan.FromMinutes(5);   // 顺带修 #8 的永久缓存
}
```

`EnhancedHttpClient` 构造增加**可选** `IUrlValidator? urlValidator = null`（经 Options 传入，
与现有 `_sensitiveDataMasker` 等注入方式一致），为 null 时回退静态门面。
当前 `EnhancedHttpClient` 在 `ValidateRequest`（`:1665/1677` 附近）静态调用 `UrlValidator`，
改造为"优先实例、回退静态"。

### 兼容性

- 步骤 1 纯内部实现变更，公共签名不变 → **零破坏**。
- 步骤 2 为新增 API，`UrlValidator` 静态方法保留。

### 验收

- 用例：8 线程并行 `ConfigureAllowedDomains` + 32 线程并行 `ValidateUrl` → 断言无 `InvalidOperationException`，且最终结果集完整（无"空集"瞬间）。
- 用例：断言配置切换过程中不会误拒已有白名单域名。

#### 5.1 新增 URL 脱敏器（复用现有敏感词表）

```csharp
internal static class SensitiveUrlRedactor
{
    private const string Mask = "***REDACTED***";

    public static string Redact(string? url, ISensitiveDataMasker? masker = null)
    {
        if (string.IsNullOrEmpty(url)) return url ?? string.Empty;
        var qIndex = url!.IndexOf('?');
        if (qIndex < 0) return url;                    // 无 query，无需处理

        var basePart = url.Substring(0, qIndex + 1);
        var query = url.Substring(qIndex + 1);

        // 按 & 切分；key 命中 MessageSanitizer.SensitiveFields 则 mask value
        // 词表（MessageSanitizer.cs:23-35，验证摘录）：token / access_token / refresh_token /
        //   api_key / password / secret / phone / email / id_card / bank_card / real_name /
        //   address / 住址 / passport …（无 authorization —— 顺带把 Authorization/code/state 加入）
        // 未命中则原样保留（保证排障可用性）
        var redacted = string.Join("&", query.Split('&').Select(RedactOne));

        return masker != null ? masker.Mask(basePart + redacted) : basePart + redacted;
    }
}
```

- **复用** `MessageSanitizer.SensitiveFields`（`MessageSanitizer.cs:23`）作为敏感键名表，避免维护两份词表；
  实施时**顺带审查词表**，把 `authorization` / `code` / `client_secret` 等常见 OAuth 键补入（词表是公共
  行为，加键即同步生效于日志脱敏）。
- 默认**只掩码 value**，保留 key 与 URL 结构，兼顾排障。

## #16 🔴 `ApiException.Content` 未脱敏、未截断

### 问题定位（验证修正）

```
Mud.HttpUtils.Client/HttpClient/EnhancedHttpClient.cs
  1709-1713:  sanitizedContent 仅用于日志（SanitizeContent, maxLength:200）
  1716:  var apiEx = new ApiException(response.StatusCode, errorContent, ...);   // errorContent 已受 10240 截断
  1719-1732:  capturedRequestContent 从请求属性读出 → apiEx.RequestContent     // ← 请求体捕获【无任何上限】
  1735:  _exceptionRedactor?.Redact(apiEx);                                    // Redactor 已调用 ✓
```

准确表述（比原方案更细）：

1. `Content` 在本路径**已有**默认 10240 截断（`ReadErrorContentWithLimitAsync:1744`），**真正缺口是
   Content-Length 缺失时不截断**（`#9`，`EnhancedHttpClient.cs:1765-1767`）；
2. `RequestContent` 读取（`EnhancedHttpClient.cs:930/932` 与执行器 `CaptureRequestContentAsync:682`）
   **无上限**——1 MB 请求体会全文进入异常对象；
3. 两条路径的 `IExceptionRedactor` 调用**已存在**（`1735` / `CreateApiException:740`），不需要补调用，
   需要补的是**默认 Redactor 行为**（未注册时无脱敏）与请求体上限。

### 修复设计

```csharp
private async Task EnsureSuccessStatusCodeAsync(HttpResponseMessage response, CancellationToken ct)
{
    if (response.IsSuccessStatusCode) return;

    // #9+#1：限量读取（含 chunked），并与执行器路径同一实现
    var errorContent = await ReadErrorContentWithLimitAsync(response, ct).ConfigureAwait(false);
    //     ↑ 内部改为 LimitedContentReader.ReadLimitedStringAsync(response.Content, effectiveMax, ct)

    var sanitizedContent = _enableLogging ? SanitizeContent(errorContent, maxLength: 200) : "[日志未启用]";
    _logger.HttpRequestFailedWithResponse((int)response.StatusCode, sanitizedContent);

    var apiEx = new ApiException(response.StatusCode, errorContent, SafeUrl(response.RequestMessage?.RequestUri)); // #5

    if (capturedRequestContent != null)
        apiEx.RequestContent = Truncate(capturedRequestContent, effectiveMax);  // 请求体同样受限

    _exceptionRedactor?.Redact(apiEx);
    apiEx.Data["HttpStatusCode"] = (int)response.StatusCode;
    throw apiEx;
}
```

**要点**

- 截断由 `LimitedContentReader` 在**读取阶段**完成（#9 修复后 chunked 同样受限）。
- `RequestContent` 上限在**捕获源头**加：`EnhancedHttpClient.SendJsonWithBodyAsync:930` 与
  `DefaultHttpRequestExecutor.CaptureRequestContentAsync:682` 都改为限量读取（`effectiveMax`），
  超限截断并标记 `...[已截断]`。
- 执行器路径 `CreateApiException:730` 已有 `TruncateErrorContent`，随 N-1 统一后两条路径行为一致。

### 验收

- 用例：`CaptureRequestContent = true` + 1 MB 请求体 + 500 响应 → 断言 `ApiException.RequestContent.Length` 受限。
- 用例：注册自定义 `IExceptionRedactor` → 断言两条路径（内置方法 / 生成代码）**都**会调用它。

## N-1 🟠 `MaxExceptionContentLength` 两路径默认值不一致 + XML 文档与实现相反
