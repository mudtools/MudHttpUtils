### 0.3 本方案目标

以**上游源码现状**为唯一事实来源，只保留"真实存在且上游可修"的项，做到：

1. **只修真 Bug**：每项都能在上游源码定位根因；下游存在对应 workaround 且修复后**可删除该 workaround**。
2. **只补真缺口**：把下游靠反射 / 手工 new / 覆写补偿才能达成的能力，补成正式公共 API；**与既有能力重复的一律不做**。
3. **零兼容破坏**：修复落在既有扩展点 / 新增可选成员 / 新增重载上；**不改既有 `virtual` 默认实现的行为语义**，不改既有公共成员签名。
4. **上收被下游自建的"半个能力"（本版新增目标）**：二次盘点显示，下游大量绕行的根因是"上游已有相邻机制的另一半"（`IssuedAt` 有而时钟无、`TokenStoreValue` 有而编解码无、`GetApp` 虚而 `RegisterApp` 不虚、工厂有而恢复创建入口无）——本版把这些"半成品"补成闭环，**以最小加法换取下游整套自建代码的删除**。

### 0.4 本轮复核对原方案的总体结论

原方案 15 项（B1–B8、F1–F7）中：

| 结论 | 条目 | 数量 |
|------|------|------|
| ✅ **成立**（根因、方案均属实，仅需细化表述） | B3、B4、B5、F2、F4 | 5 |
| ⚠️ **部分成立 / 需改案** | B6、B7、B8、F1、F3、F5、F6、F7 | 8 |
| ❌ **不成立 / 应撤回** | B1、B2 | 2 |
| 🆕 **本版新增（二次盘点）** | G1–G10（§3.8–§3.17） | 10 |
| ⛔ **明确判定为非缺口（不改）** | N1–N5（§3.18） | 5 |

其中**原方案的 4 处技术性错误必须纠正**（否则实施即踩坑）：

1. **B4**：`TryAddEnumerable` **不接受工厂委托描述符**（`ServiceDescriptor.Singleton<TService>(factory)` 的 `ImplementationType` 为 null，调用即抛 `ArgumentException`）；改用类型描述符又会破坏"`IHostedService` 与 `ITokenRefreshBackgroundService` 解析到同一实例"的既有不变量。
2. **F1**：直接"把 internal `EnhancedHttpClientOptionsCloner` 转 public"会得到**语义错误的克隆**——该 Cloner **刻意不拷贝** `Logger`/`RequestInterceptors`/`ResponseInterceptors`/`SensitiveDataMasker`/`AppAccessAuthorizer`（P2；见 `EnhancedHttpClientOptionsCloner.cs:20-25,55-56`），而下游手写 Clone 恰恰拷贝这些字段。
3. **B1**：拟新增的 `CredentialToken.ExpiresInSeconds` 与既有 `CredentialToken.IssuedAt` **重复建模**，且 TTL 感知阈值**早已实现**（见 §2.1）。
4. **B8/F 系列遗漏了更本质的缺陷（本版新增 G3/G7）**：`DefaultAppManager` 的**注册与默认键入口非 virtual**，而查询入口是 virtual —— 这一**不对称**使基类无法支撑"懒加载多应用"，**微信因此整体弃用基类**；`IAppContextHolder` 的默认实现与下游切换器各持一个 `AsyncLocal`，是 F3/G8-A 顺序不变量被永久固化的**根因**。B8 只提"字段加锁 + 懒加载"，未识别出这两点。

## 2. Bug 修复清单（逐项细粒度）

### 2.1 B1 ❌ 撤回：TTL 感知阈值**已实现**，`ExpiresInSeconds` 属重复建模

**原方案主张**：`TokenExpiryPolicy.EffectiveThresholdSeconds` 在 `issuedAtMs <= 0` 时回退配置阈值，导致短 TTL 令牌缓存永不命中；建议给 `CredentialToken` 新增 `ExpiresInSeconds` 并加分支。

**实测复核**：

1. **TTL 钳位早已落地**（P2.4/TK-04）：
   `Mud.HttpUtils.Abstractions/TokenManager/TokenExpiryPolicy.cs:61-72`
   ```csharp
   if (issuedAtMs <= 0) return configuredThresholdSeconds;
   var ttlSeconds = (expireMs - issuedAtMs) / 1000L;
   if (ttlSeconds <= 0) return configuredThresholdSeconds;
   return Math.Min(configuredThresholdSeconds, ttlSeconds / 2L);   // ← 文档主张的分支已存在
   ```
   并已接入两条主链：`TokenManagerBase.cs:797`（`IsValid(entry.IssuedAt, entry.Expire, …)`）、`:825`（清理路径 `IsExpired`）、`UserTokenManagerBase.cs:865`（`IsUserTokenValid`）。
2. **租户/客户端路径由框架自动填充签发时间**，不存在"`IssuedAt` 缺失"：
   `Mud.HttpUtils.Client/TokenManager/StandardOAuth2TokenManager.cs:616-620`
   ```csharp
   AccessToken = tokenResponse.AccessToken ?? string.Empty,
   RefreshToken = tokenResponse.RefreshToken,
   IssuedAt = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds(),   // 与 CalculateExpire(ExpiresIn) 同一构造块
   Expire   = CalculateExpire(tokenResponse.ExpiresIn)
   ```
   用户令牌侧由拷贝入口透传：`UserTokenInfo.cs:139`（`FromCredentialToken`）、`:168`（BC-34 补齐）、`:187`、`:209-211`。
   ⇒ `issuedAt <= 0` 只出现在**手工构造**、**历史存量**或**派生管理器未回填**三种情形，而非框架自动解析路径。
3. **测试已覆盖该行为**（`Tests/` 实测）：
   - `Mud.HttpUtils.Client.Tests/Token/TokenContractGuardTests.cs:72-155` — `TokenExpiryPolicyBoundaryTests`：`:113` 显式覆盖 `issuedAt<=0` 回退分支、`:138` 断言"刚签发短 TTL 判有效"。
   - `TokenManagerBaseTests.cs:391-403` — `TtlAwareThreshold_ShortTtlToken_ShouldNotRefreshOnEveryCall`（TTL=200s，`RefreshCount==0`）。
   - `Regression/MtRoundRegressionTests.cs:272-302`、`Mud.HttpUtils.Tests/UserTokenInfoIssuedAtTests.cs:53-`。
4. `TokenExpiryPolicy.cs:52-55` 已经把"`issuedAtMs<=0` 时回退配置阈值"写为**明示契约**。

**结论**：原方案对该项的定位（🟠 高优 Bug）与事实不符，**撤回**。下游补偿的真正含义是"派生管理器需自行回填签发时间"——属**集成约定**，不是上游缺陷。

**残留改进（降级为远期低优，见 §7）**：可提供一个**规范化构造入口**（如 `UserTokenInfo.FromIssuedCredential(...)` / `CredentialToken.Create(accessToken, expiresInSeconds, …)`），把"填 `IssuedAt` + 由 `expires_in` 算 `Expire`"收敛为一次调用，消除下游手工治理。**明确不做**：新增 `ExpiresInSeconds` 字段（与 `IssuedAt` 争同一真相源，属重复建模；且 `TokenStoreValue.ExpiresInSeconds` 已在持久层存在，再扩公共面会造成"同一语义两处表达"）。

### 2.2 B2 ❌ 撤回：整条移除 = **登出语义**，字段级失效入口已存在

**原方案主张**：`InvalidateUserTokenAsync(string userId, …)` 默认"整条移除"经桥接写穿删除 access+refresh 两个物理键，误删 refresh；建议把默认实现改为字段级失效。

**实测复核**：

1. **机制属实**：`UserTokenManagerBase.cs:729-737` → `:435-438` → `:444-479`，对裸键与前缀键逐个 `_userTokenCache.TryRemove`；`TokenStoreBackedTokenCache.TryRemove`（`:272-289`）在镜像命中时 `WriteThroughCoreAsync`，用户维度最终调 `_userStore.RemoveAsync(userId, tokenType)`；而 `IUserTokenStore.RemoveAsync` **契约即为"移除该用户和令牌类型的所有令牌数据"**（`IUserTokenStore.cs:65-71`）⇒ access 与 refresh 物理键都会被删。
2. **但这是刻意的登出语义，不是 Bug**：
   - README 明确"清除该用户全部作用域（登出语义）"；
   - 既有测试断言`登出后必须不可用`（`UserTokenKeyInjectionGuardTests.cs:74-91`、`UserKeyIndexTests.cs:85-88`）；
   - `UserTokenManagerBase.cs:797-801` 的 XML 注释**显式**把 `InvalidateUserTokenAsync` 的"整条移除"作为与字段级失效**相对的既有契约**。
   ⇒ 修改默认实现 = **行为级破坏性变更**（违背 §0.3 零破坏目标），并使"登出"失去唯一语义入口。
3. **"仅失效 access、保留 refresh"的正式入口早已存在且已发布**：
   - `protected void InvalidateUserAccessTokenInCache(string userId, string[]? scopes = null)` — `UserTokenManagerBase.cs:814-835`，行为：`AccessToken=null` / `AccessTokenExpireTime=0` / `IssuedAt=0` + 保序写回（`UpdateUserTokenCachePreservingExpiry`，`:841-851`）+ `BumpWriteGeneration` + 镜像未命中落"空访问令牌墓碑"（`:828-831`，防止读穿透复活旧令牌）。
   - 已在公共 API 面登记（待发布）：`Mud.HttpUtils.Client/PublicAPI/net8.0/PublicAPI.Unshipped.txt:41`。
   - ⚠️ **勘误（E4）**：401 恢复链路（`TokenRecoveryExecutor.cs:1401-1413`）调用的是**另一个方法** ——
     `InvalidateCachedUserAccessToken`（`UserTokenManagerBase.cs:774`，**internal**，**镜像未命中为 no-op**，
     专供 401 自愈：字段置空 + 保序写回 + 代际作废），与 `InvalidateUserAccessTokenInCache`（`:814`，protected，
     **镜像未命中落"空访问令牌墓碑"**，供派生类跨进程/桥接场景使用）**刻意不同**（参见 `:800-810` 的 XML 对照说明）。
     二者不可混称"同一入口"；本项的撤回结论不因此改变（字段级失效的两条入口均已存在）。
   - **下游已改用**：飞书 `UserTokenManager.cs:348-366` 明确注释"不得委派基类实现"并调用 `InvalidateUserAccessTokenInCache(userId)`（`:364`）。

**结论**：**撤回**。上游无需改默认实现；下游 workaround 已完成迁移（只剩 3.0.0→新版升级动作）。仅建议在 `InvalidateUserTokenAsync` 的 XML 注释中显式指向字段级入口（**纯文档，零代码风险**）。

### 2.3 B3 ✅ 成立：用户侧移除路径未复用异步写穿（冷启动不落库）

### 2.4 B4 ✅ 成立（**方案必须改**）：`RegisterTokenRefreshService` 非幂等

**原方案的技术错误（本次复核纠正）**：

- 建议写法 `TryAddEnumerable(ServiceDescriptor.Singleton<IHostedService>(sp => …))` **不可行**：`ServiceCollectionDescriptorExtensions.TryAddEnumerable` 先取 `descriptor.GetImplementationType()`，工厂委托描述符返回 `null` 即**抛 `ArgumentException`**。

private static void RegisterTokenRefreshService(IServiceCollection services)

    if (services.Any(d => d.ServiceType == typeof(TokenRefreshHostedService)))

    services.AddHostedService(sp => sp.GetRequiredService<TokenRefreshHostedService>());
    services.AddSingleton<ITokenRefreshBackgroundService>(sp => sp.GetRequiredService<TokenRefreshHostedService>());
#else
    services.TryAddSingleton<ITokenRefreshBackgroundService, TokenRefreshBackgroundService>();

**✅ 已实施（批次 A，§8）**：net6+ 以「`TokenRefreshHostedService` 类型是否已注册」为守卫；

### 3.14 G7 ✅ 成立（**F3/G8-A 的治本项**）：`IAppContextHolder` 默认实现自持 `AsyncLocal` ⇒ 顺序不变量无法消除

**问题**：`AddMudHttpClient` **已经**自动注册 `IAppContextHolder`（`ServiceCollectionExtensions.cs:142-143`，"A1 修复：任何客户端注册路径都能用多应用"）→ `TryAddSingleton<IAppContextHolder, AsyncLocalAppContextSwitcher>()`（`:941`）。而 `AsyncLocalAppContextSwitcher` 的 `AsyncLocal<IMudAppContext>` 是**实例私有字段**（`AsyncLocalAppContextSwitcher.cs:14`）。⇒ 下游若在 `AddMudHttpClient` **之后**注册自己的切换器/持有器，框架默认持有器已占位（`TryAdd` no-op），下游写入的是**另一个 AsyncLocal**，生成代码与 `DefaultHttpRequestExecutor` 读不到 ⇒ 多应用**静默失效**。这正是 `G8-A`/`P0-1` 把"必须早于 `AddMudHttpClient`"写成硬约束的根因。

**下游实证**：微信 `WechatWorkMultiAppExtensions.cs:127-134`（"AddMudHttpClient 内部会 TryAdd `IAppContextHolder`…若在此之后注册，TryAdd 失效…故必须先注册（先注册者胜）"）、`:209-210`（"不得重复注册——重复会再次出现两个 AsyncLocal"）、`WechatContractGuards.cs:1197-1219`（`G8-A` 源码级顺序守卫 + 同实例断言）；飞书 `FeishuServiceCollectionExtensions.cs:268-272`（`C-3` 手工注册 `IAppContextHolder`）+ `:226-228` 顺序注释。

**方案（使顺序**不再影响语义**）**：
1. `AddMudHttpAppContextHolder` 改为注册一个**委托式适配器**：`IAppContextHolder` 的实现持有 `IServiceProvider`，在每次 `Current` / `SwitchTo` / `BeginScope` 时解析容器中**最后注册**的应用上下文切换器/持有器（`GetServices<IAppContextHolder>().Last()`），转发调用。
   > ⚠️ **约束已实证（E11，第 3 版列为"未验证假设"，本版已定位到根因）**：
   > `IAppContextHolder.Current` 的**接口声明本身就是 `{ get; init; }`**（`Abstractions/AppContext/IAppContextHolder.cs:28`）
   > ⇒ 适配器**必须**实现一个 `init` 访问器；而 `init` 只能在**对象初始化期**写入，**无法转发**给被委托实例。
   > 影响面被限定为：`Current` 的 **get** 可完整转发；`SwitchTo`/`BeginScope` 可完整转发；
   > **`init` 写入路径不可转发** —— 这是可接受的，因为 `init` 的组织约定本就是"仅对象初始化期可见"
   > （`IAppContextHolder` 的 XML 明确"运行时切换请用 `SwitchTo`/`BeginScope`"），DI 构造的 holder 不会被任何消费方经 `init` 赋值。
   > 适配器的 `init` 应采用"**暂存 + 首次 get 前生效**"或"**显式 `NotSupportedException`**"，具体形态由探针决定。
   > **实施闸门：先做 30~50 行探针工程**（验证：`AddMudHttpClient` 之前/之后注册切换器两种顺序下，
   > 生成式客户端与 `DefaultHttpRequestExecutor` 是否读到同一当前上下文；`SwitchTo`/`BeginScope` 是否正确转发；
   > `init` 形态不破坏既有契约测试）。**探针不通过则降级为 F3 的"公开单点 + 文档 + 定向测试"**（顺序不变量保留）。
   >
   > ✅ **探针结论（本版已执行，7/7 通过）**：以真实接口实现"委托适配器"（`Tests/Mud.HttpUtils.Client.Tests/AppAuth/AppContextHolderAdapterProbeTests.cs`）
   > 验证了 ①**自身排除防递归**（不加排除则 `Last()` 恒为自己）、②`Current`(get)/`SwitchTo`/`BeginScope` **完整转发**、
   > ③`init` 修饰符在接口与实现两侧均存在（`IsExternalInit`）且**无法转发**、④无下游实现时**安全降级**。
   > ⇒ 方案**可行**，已按 §8.5 实施（默认注册改为委托适配器 + 无下游时回退内部 `AsyncLocalAppContextSwitcher`）。
2. 无任何下游注册时，回退 `AsyncLocalAppContextSwitcher`（单应用零配置行为不变）。
3. `AsyncLocalAppContextSwitcher` 保留（显式注册仍可用），但**不再由 `AddMudHttpClient` 抢先 TryAdd 其具体类型**，避免"框架默认抢占"。
4. 结果：无论下游在 `AddMudHttpClient` **之前还是之后**注册切换器，holder 都转发到下游实现 ⇒ `T-F3` 的"无序注册等价"从"文档承诺"变为**机制保证**。
5. 风险：需核对"下游显式 `services.AddSingleton<IAppContextHolder, X>()`（非 `TryAdd`）"的情形——最后注册者胜，行为与今日一致；以及 `init` 访问器的形态选择（见上条 E11 约束）。
   另需核对：适配器若经 `GetServices<IAppContextHolder>().Last()` 解析，会**把自己也解析出来**（自身即 `IAppContextHolder` 注册项）⇒ 必须排除自身实例（或改用专用标记接口/按 `ServiceType`+实现类型过滤），否则构成无限递归。**这是本项第二个必须由探针验证的点。**

**验收**：见 §5 `T-G7`。

#### 8.7.3 实施中确认的关键陷阱（写入方案正文）

1. **`UtcNow` 接缝自身必须直取 `DateTimeOffset.UtcNow`** —— 批量替换时若把接缝的**实现体**也替换成 `UtcNow`，会立即产生**无限递归**（实测：Stack overflow，测试主机崩溃）。已在代码中加注释锁死。
2. **`RemoveApp` 的返回值必须纳入懒加载项** —— 否则"只声明未实例化"的应用移除后返回 `false`，且 `HasApp` 与 `GetApp` 视图分裂。
3. **`GetAllApps` 不触发实例化**（已定义为公开语义）：枚举不应有副作用；懒加载项在首次 `GetApp`/`GetDefaultApp` 命中后才进入枚举视图。
4. **向既有 public 接口加成员 = 二进制破坏** —— G4 因此落在 Client 侧扩展方法（E9），并加"接口成员数恒为 3"的反射守卫。
5. **白名单改并集后"配置删除域名"不再有增量式公开路径** —— 已在代码注释与 CHANGELOG 中显式声明（E10）。
