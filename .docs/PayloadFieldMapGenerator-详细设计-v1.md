> 1. **契约方法首参缺可空标注 ⇒ `CS8604`**（缺陷 24）：`static string Text(PayloadNode node)` /
>    `Method` 路径的 `static string Parse(string text)` 此前零诊断 + 产出，生成文件在
>    `Nullable=enable` 的消费工程里报「可能传入 null 引用实参」（生成物传入的正是**可能为 null** 的
>    `n` / `n?.Value`；`// <auto-generated/>` 不抑制该告警）⇒ 改为 `PAYLOAD004` 拦截。
>    裁决口径（与 P4 同源）：**oblivious（`NullableAnnotation.None`，即声明处 nullable 未启用）仍接受** ——
>    此时生成文件同样处于 oblivious 上下文、不会产生该告警，强行要求 `?` 反而给消费方引入 `CS8632`。
> 2. **类名 / 属性名是 C# 保留字 ⇒ 生成文件语法错误**（缺陷 25）：`@class` / `@event` 这类写法
>    （XML 报文中 `event` / `default` / `class` 是常见元素名）此前渲染成 `partial class class` /
>    `t.event = …`，生成文件报 `CS1001`/`CS1519`/`CS1513`，且消费方的类被连带报
>    `CS0260`「缺少 partial 修饰符」（指向完全错误的位置）⇒ **渲染期补 `@` 前缀**（`ISymbol.Name` 不含 `@`，
>    而 `TypeDisplay` 用的 `FullyQualifiedFormat` 自带 `EscapeKeywordIdentifiers`，故仅声明处需补）。
> 3. **继承链上的同名 `PayloadFieldMap` ⇒ `CS0108`**（缺陷 26）：`PAYLOAD008` 此前只查**本类**成员；
>    基类（含引用程序集）已有同名成员时生成物会**隐藏**它（`CS0108`，`TreatWarningsAsErrors` 下即构建失败）
>    ⇒ `PAYLOAD008` 扩面为「本类（CS0102）∪ 继承链（CS0108）」。
> 4. **同名同元数重载并存 ⇒ 误报 `PAYLOAD004`**（缺陷 27）：`FindContractMethod` 只看**首个**结构候选，
>    而 `GetMembers` 的顺序不保证契约签名在前（实测 `Delimited<T>(string, char)` 先声明时必误报）
>    ⇒ 改为收集**全部候选**并优选「形参类型 + 可空标注」双符合者。
> 5. **命名空间段为保留字 ⇒ hintName 含 `@` ⇒ 生成器抛内部异常**（缺陷 28）：`namespace @class.Sub` 下
>    `ns` 取自 `ToDisplayString()`（**自带** `@` 转义，用于渲染 `namespace` 声明是对的），但它被一并拼进
>    **hintName** ⇒ `context.AddSource` 抛 `ArgumentException`「包含无效字符 "@"」⇒ 被兜底捕获后表现为
>    **`PAYLOAD001`「生成器内部错误」**（用户无法从该文案定位到命名空间）⇒ hintName 用**剥离转义**的命名空间。
> **本轮有产品代码改动**（生成器 3 个文件 + 诊断文案），并新增 **8 个用例**
> （3 负向 + 5 正向对照：关键字属性名 / 关键字类名 / 关键字命名空间 / 重载优选 / oblivious 首参，
> 其中「生成物零新增错误/告警」被抽成可复用的通用断言 `AssertProducesCompilableOutput`）：
> 全量 **985 通过 / 0 失败**；5 个 Verify 快照**零变更**；生成器工程 `-t:Rebuild` → **0 错误 / 2 个存量告警**
> （`CS1574` 仅命中既有的 `GeneratorContext` / `ConstructorGenerator` 两处，本生成器相关告警 0）。

## 0. 验证结论（v2.0 新增）

### 0.1 必要性评估（高级程序员视角）

**必要性：成立，且不存在功能重复。**

| # | v1 提出的缺口 | 核验结果 |
|---|---|---|
| 1 | 字段映射靠**手写声明**（`Map("UserID", …)` 逐行） | **成立**。仓库内不存在任何「报文 → 载荷」映射能力（`grep Payload` 在生成器中零命中）。 |
| 2 | 元素名与属性名并列维护，无编译期校验 | **成立**。手写链的两处字符串无任何交叉校验。 |
| 3 | 转换方法引用靠字符串 | **成立**（v1 示例 `Method = "ParseGender"`；本设计实现后由 `PAYLOAD004` 覆盖）。 |
| 4 | 消费方 `scripts/*.ps1` 是文本扫描 | **成立**（属消费方仓库事实，本仓库无法核验其细节，但不影响结论）。 |
| 5 | 转换语义散在载荷类里 | **成立**，收敛到消费方 Converter（G-ADR-3）。 |

**冗余性判定**：与仓库既有能力**无重复**——
`FormContentGenerator` / `EventHandlerSourceGenerator` / `HttpInvoke*` 三个族分别处理「表单内容」「事件处理器骨架」「HTTP 调用」，
与本设计处理的「外部报文节点 → 载荷字段」**无交集**；本设计是第 4 个**正交**能力。

**非最优项（v1 中被本版删除）**：
- v1 §5.3 的**独立 salt 节点**：生成器版本已在 `GeneratorConfigSnapshot.Version` 内并随快照参与值相等比较 ⇒
  再挂一个盐节点是**纯冗余**（多一条 `.Select` 链路 + 多一个下游 `Combine`）。
- v1 §8 的**2 个新开关**：`PayloadFieldMapEmitMarkers` 与既有 `MudEmitGeneratedCodeMarkers` **语义完全相同**；
  `DisablePayloadFieldMapGenerator` 与既有 `DisableMudSourceGenerator` 高度重叠。新增两个只服务一个生成器的开关，

### 0.6 核心设计决策（ADR 摘要）

| 编号 | 决策 | 一句话理由 |
|---|---|---|
| G-ADR-1 | **生成物是「委托表」而非「XML 解析代码」** | 生成物只被手写引擎消费 ⇒ 规避 roslyn#57239；引擎可单测，生成物只测「形状」 |
| G-ADR-2 | **上游只认「元素名 + 委托」，格式知识全在生成器侧** | 上游运行时契约极小（`PayloadNode` + 一个 `Map` 原语），消费方换映射策略不必改上游 |
| G-ADR-3 | **转换逻辑委托给消费方 Converter（`typeof` 强类型，非字符串）** | 上游不反向依赖下游类型；转换语义集中单测；生成器可**语义校验**方法存在性与返回类型 |
| G-ADR-4 | **节点类型 `PayloadNode` 定义在上游，XML-free** | 消费方只需「XElement → PayloadNode」一个适配器；AOT 安全；无 `System.Xml` 越过上游边界 |
| G-ADR-5 | **`[PayloadContract]` 即渐进迁移开关**（有无特性决定生成与否） | 消费方无需编译期条件符号逐类切换；手写 binder 与生成物可按类共存迁移 |
| G-ADR-6 | **诊断仅 001 带 `NotConfigurable`**，其余全部 Error 但不参与连坐 | 守住 `Diagnostics.cs:17-51` 的红线，不让本生成器遮蔽 `MUD*`/`AOT*` 诊断 |
| G-ADR-7 | **生成代码按「C# 7.3 + netstandard2.0」基线书写**（**v2.0 收紧**） | 实测 ns2.0 消费工程默认 `LangVersion=7.3`；禁 `static` lambda / 集合表达式 / `init` / `record` / 目标类型 `new` |
| G-ADR-8 | **提供非泛型桥 `IPayloadContractAccessor`**（F2） | 泛型上下文无法访问 `TPayload.PayloadFieldMap`（CS0712），`static abstract` 需 net7+ ⇒ 必须有无反射消歧路径 |
| G-ADR-9 | **fluent `Map()` 链是受支持的手写公共 API** | 生成器只是「另一种写链的方式」⇒ 消费方可**逐类**渐进迁移，把生成器从「架构风险」降级为「书写方式升级」 |
| G-ADR-10 | **映射表无状态、恒为静态单例**（v1.2） | 多运行模式共用契约的诉求会诱使把上下文闭包进 `Map` 委托 ⇒ 跨请求串扰且单线程测试全绿 |
| **G-ADR-11** | **运行时契约落位 `Mud.HttpUtils.Abstractions`**（v2.0） | `Mud.HttpUtils` 是元包（无程序集）；Abstractions 依赖最小且被 Attributes/Client 传递可达 |
| **G-ADR-12** | **复用既有配置快照与开关，不新增配置面**（v2.0） | `DisableMudSourceGenerator` / `MudEmitGeneratedCodeMarkers` / `NullableEnable` 已覆盖全部需求；新增即冗余且要三处同步 |
| **G-ADR-13** | **诊断全 Error 且「有错不产出」**（v2.0） | 本能力的故障模式是「静默丢字段」；降级为 Warning 或产出半成品都会把故障留到运行期 |
| **G-ADR-14** | **特性统一落 `Mud.HttpUtils.Attributes` 命名空间**（v2.0） | 满足既有 G8-13 守卫（该程序集公开面命名空间白名单为空），消费方 `using` 组合可预期 |
| **G-ADR-15** | **凡「生成物必然编译失败」或「声明/字段会被静默丢弃」的形态，一律生成期拦截**（v2.2） | 生成物报 `CS0718/CS0310/CS1001/CS1061/CS1503/CS0315` 时错误指向**生成文件**（用户无法定位、也无法修）；静默丢弃则直接违背本能力的存在理由 ⇒ 与 G-ADR-13 同源，只是把「拦截面」从「属性类型」扩展到「类形态 + 属性形态 + 转换器签名 + 泛型约束」 |
| **G-ADR-16** | **生成物类型实参保留可空标注**（v2.2） | `SymbolDisplayFormat.FullyQualifiedFormat` 会丢弃 `?`，使 `List<string?>` 渲染成 `Delimited<string>` ⇒ 消费方收 `CS8619`（`// <auto-generated/>` 不抑制）；同时该标注必须进入指纹，否则「只补一个 `?`」会命中增量缓存 |
| **G-ADR-17** | **嵌套对象声明式递归 Bind**（v2.5）：新增 `PayloadFieldFormat.Object` / `ItemsObject`，生成器对 `TSingle?` / `List<TNested>`（内层标 `[PayloadContract]`）递归引用 `TInner.PayloadFieldMap` | 嵌套结构是「树形单向聚合」，与既有 `Items`/`ItemsWithAttributes` 同构，只差「项是否自带契约」；运行时复用既有非泛型桥（F2），生成器只多一种 Format 推断/渲染；把消费方 `Method` 逃生舱的「元素名字符串零编译器防护」整类故障面纳入 PAYLOAD 诊断体系 |

> **1 项是误报**（合法声明被判非法）。

| # | 类别 | v2.3 的实际行为（实测） | v2.4 处置 |
|---|---|---|---|
| **P23** | 转换器签名 | 首参**非可空**标注（`static string Text(PayloadNode node)`、`Method` 路径的 `static string Parse(string text)`）：零诊断 + 产出 1 个文件 + 生成文件报 **`CS8604`**（可能传入 null 引用实参） | `PAYLOAD004`，不产出（`HasNullableNodeParameter`：`NullableAnnotation != NotAnnotated`）。**oblivious 仍接受**（避免给 nullable 未启用的消费方引入 `CS8632`） |
| **P24** | 渲染（标识符） | 类名 / 属性名为 C# 保留字（`@class` / `@event`）：零诊断 + 产出 1 个文件 + 生成文件报 `CS1001`/`CS1519`/`CS1513`/`CS1026`，且**消费方的类**被连带报 `CS0260`（指向错误位置） | 渲染期 `EscapeIdentifier`：保留字补 `@` 前缀（`SyntaxFacts.GetKeywordKind`） |
| **P25** | 声明冲突 | 基类（含引用程序集）已有同名 `PayloadFieldMap`：零诊断 + 产出 1 个文件 + 生成文件报 **`CS0108`**（隐藏继承成员） | `PAYLOAD008` 扩面：本类（CS0102）∪ 继承链（CS0108），不产出（`FindInheritedMember`） |
| **P26** | **误报** | 转换器同时提供 `Delimited<T>(string, char)` 与 `Delimited<T>(PayloadNode?, char)`（后者后声明）：**误报 `PAYLOAD004`**（合法声明被判非法）——`FindContractMethod` 只取 `GetMembers` 顺序里的首个结构候选 | 改为收集**全部候选**（`FindContractMethods`）并优选「形参类型 + 可空标注」双符合者；无符合者时才按（类型不符 / 缺可空标注 / 不存在）分别报错 |

> **本轮的方法论补充（与消费方 §13.5/13.6 同源）**：P23~P25/P27 与 v2.2 的 P15~P21 属**同一族**
> （「未拦截形态 ⇒ 静默产出坏代码 / 抛内部异常」），说明「拦截面」不是一次性可以想全的，
> 只能靠**通用断言 + 逐个形态探针**持续收口；而 P26 提醒：**收紧拦截时必须同时准备正向对照**，
> 否则「越拦越严」会把合法写法判死。
> ⇒ 本轮的 8 个新用例里有 **5 个是正向对照**（关键字属性名 / 关键字类名 / 关键字命名空间 / 重载优选 /
> oblivious 首参），只有 3 个负向用例；且「生成物零新增错误/告警」这条**与形态无关**的断言被抽成
> 可复用方法 `AssertProducesCompilableOutput`（本轮 4 个缺陷都是被它直接钉死的）。
> ⇒ P27 还说明「兜底诊断（`PAYLOAD001`）的**可达性**本身就是一条不变量」：内部兜底一旦被合法输入触发，

## 3. 上游运行时契约（XML-free，AOT 安全）

> 落位：**`Mud.HttpUtils.Abstractions/Payloads/`**（命名空间 `Mud.HttpUtils.Payloads`）。
> **为什么不落 `Mud.HttpUtils/`**：该工程是**元包**（`IncludeBuildOutput=false`、零 `.cs`、无 `PublicAPI/`），
> 「落位主包」在物理上不可能产出程序集（P1）。Abstractions 依赖最小、被 `Attributes`/`Client` 传递可达，
> 且其 5 个 TFM 的 PublicAPI 基线目录已存在。

### 3.1 `PayloadNode`——通用源节点

```csharp
namespace Mud.HttpUtils.Payloads;

/// <summary>外部报文的通用节点投影（XML-free / JSON-free / AOT 安全）。</summary>
public sealed class PayloadNode
{
    /// <summary>节点名（XML 元素名 / JSON 键）。</summary>
    public string Name { get; }

    /// <summary>节点文本（对应 <c>XElement.Value</c> 的全后代文本语义）；无文本时为 null。</summary>
    public string? Value { get; }

    /// <summary>子节点（保持源顺序；无子节点时为空只读列表）。</summary>
    public IReadOnlyList<PayloadNode> Children { get; }

    /// <summary>属性集（XML 属性 / JSON 同层伴生字段）；无属性时为空只读字典。</summary>
    public IReadOnlyDictionary<string, string> Attributes { get; }

    /// <summary>按名取直接子节点（区分大小写）；不存在返回 null（不抛）。</summary>
    public PayloadNode? Child(string name);

    /// <summary>是否含指定名的直接子节点。</summary>
    public bool Has(string name);

    /// <summary>公开构造器（F3）：使「节点模型可独立测试」成立于不接触 XML 的前提。</summary>
    public PayloadNode(string name, string? value = null,
        IReadOnlyList<PayloadNode>? children = null,
        IReadOnlyDictionary<string, string>? attributes = null);

    /// <summary>叶节点便捷工厂（测试与「标量字段」用例最常用）。</summary>
    public static PayloadNode Leaf(string name, string? value = null);
}
```

**设计要点**：
- **只读、不可变**：构造期把 `children`/`attributes` **复制**进 `PayloadNode[]` 与 `ReadOnlyDictionary`（实测断言「构造后修改源集合不影响节点」）⇒ 线程安全、可缓存。
- `Value` 采用**全后代文本**语义（与 `XElement.Value` 一致）⇒ 上游不泄漏 XML 类型，消费方「容器节点取其内部全部文本」的行为规则与 `Mud.Wechat` v2 方案 ADR-5 的 `Values` 规则天然一致。
- **无 `Lazy<>`**，也无「惰性物化」（v1 措辞矛盾已删）：节点由消费方适配器一次性构造，避免在 AOT 下引入不确定的延迟异常。
- 空集合使用**共享静态实例**（避免叶节点为空的 `Children`/`Attributes` 反复分配）。

### 3.2 `PayloadFieldBinder<T>` 与 `IPayloadFieldMap<T>`

```csharp
/// <summary>单字段绑定委托；node 为 null 表示元素缺失（必须写默认值，不得抛）。</summary>
public delegate void PayloadFieldBinder<in T>(T target, PayloadNode? node) where T : class;

/// <summary>字段映射契约（由生成器产出实现，消费方引擎消费）。</summary>
public interface IPayloadFieldMap<in T> where T : class
{
    string ContractId { get; }
    string? ScopeFallback { get; }
    IReadOnlyList<string> Elements { get; }
    PayloadNode? ResolveScope(PayloadNode root);
    void Bind(PayloadNode root, T target);
}
```

> **协变/逆变的取舍**：接口用 `in T` 只暴露输入位置，故可逆变。本设计**固定为 `in T`**，
> 实例化职责落在非泛型桥 `IPayloadContractAccessor.CreateInstance()`（§3.4）；
> 若后续需要 `T` 作为返回值（如 `Materialize(root)`），须去掉 `in`（§12 D10）。

### 3.3 `PayloadFieldMap<T>`——唯一构建原语

```csharp
public sealed class PayloadFieldMap<T> : IPayloadFieldMap<T>, IPayloadContractAccessor
    where T : class, new()          // F2：new() 供非泛型桥 CreateInstance
{
    public static PayloadFieldMap<T> Create(string contractId, string? scopeFallback = null);

    /// <summary>追加一条字段映射（空/重复元素名即抛 —— 生成器已在编译期拦截，运行期为版本偏斜防御）。</summary>
    public PayloadFieldMap<T> Map(string element, PayloadFieldBinder<T> binder);

    public string ContractId { get; }
    public string? ScopeFallback { get; }

    /// <summary>已映射元素名（声明序）。首次访问物化并缓存；并发下最坏重复构建一次相同数组（幂等）。</summary>
    public IReadOnlyList<string> Elements { get; }

    public PayloadNode? ResolveScope(PayloadNode root)
    {
        if (root == null) return null;
        // ① 根命中任一映射元素 ⇒ 根
        for (int i = 0; i < _bindings.Count; i++)
            if (root.Has(_bindings[i].Key)) return root;
        // ② 否则回退包装容器（如 BatchJob）；容器不存在 ⇒ 落到 ③
        if (ScopeFallback != null)
        {
            var container = root.Child(ScopeFallback);
            if (container != null) return container;
        }
        // ③ 皆无 ⇒ 根：所有字段的 Child 均落空 ⇒ 全空载荷（而非异常）
        return root;
    }

    public void Bind(PayloadNode root, T target)
    {
        if (target == null) throw new ArgumentNullException(nameof(target));
        var scope = ResolveScope(root);
        for (int i = 0; i < _bindings.Count; i++)
            _bindings[i].Value(target, scope?.Child(_bindings[i].Key));
    }

    // IPayloadContractAccessor（显式实现，避免与泛型 Bind 重载歧义）
    Type IPayloadContractAccessor.PayloadType => typeof(T);
    object IPayloadContractAccessor.CreateInstance() => new T();
    object IPayloadContractAccessor.Bind(PayloadNode root, object target);   // 类型校验 + 返回同一实例
}
```

**v2.0 修正**：
- v1 的「`_elements` 构造期冻结」**不可实现**（`Create()` 之后仍要链式 `Map()`）⇒ 改为**首次访问物化并缓存**（P9）。
- `ResolveScope` 的 ③ 明确「回退容器不存在也退回根」⇒ 对非 null 输入**恒不返回 null**，
  使调用方无需区分「作用域缺失」与「报文为空」（v1 伪码会在此返回 null，与 §0.3 流程图文不符）。

**为什么作用域回退放在上游**：`batch_job_result` 双布局是**通用问题**（消费方 v2 方案 ADR-12 已把它提升为通用机制）；
放在 `ResolveScope` 后，未来任何消费方遇到同构问题零成本复用。

### 3.4 `IPayloadContractAccessor`——非泛型桥（**F2**）

成员：`PayloadType` / `ContractId` / `ScopeFallback` / `Elements` / `ResolveScope` / `CreateInstance()` / `Bind(root, object)`。

**为什么必须有**：消费方需要在**泛型**上下文拿到某载荷类型的映射表（如 `AddPayload<TPayload>(key)`），
但 C# 禁止在泛型上下文访问类型参数的静态成员（`TPayload.PayloadFieldMap` ⇒ **CS0712**），
而 `static abstract` 需 net7+ 运行时支持，消费面含 netstandard2.0 / net6.0 时不可用。
⇒ 本接口由 `PayloadFieldMap<T>`（`T` 在该类内是**具体类型**）实现，消费方改为在**具体类型**上做静态成员访问：

```csharp
// ① 组合根期注册（推荐：注册表持有已物化实例；泛型注册表方法 Register<T>(key, IPayloadFieldMap<T>) 可直接类型推断）
registry.Register(WechatCallbackEventTypes.CreateUser, ContactUserChangedPayload.PayloadFieldMap);

// ② 非泛型视图（按类型分派 / 单例注册表）——必须显式转换（v2.3 修正）
//    IPayloadFieldMap<T> 与 IPayloadContractAccessor 是两条**独立**接口：前者仅 in T（可逆变），
//    不含 CreateInstance()/Bind(object) 等返回位置成员；同时实现两者的是具体类 PayloadFieldMap<T>。
//    而静态成员 PayloadFieldMap 的编译期类型是 IPayloadFieldMap<T> ⇒ 隐式赋值报 CS0266。
var map = ContactUserChangedPayload.PayloadFieldMap;
if (!(map is IPayloadContractAccessor accessor))
    throw new InvalidOperationException(
        "载荷映射表未实现 IPayloadContractAccessor（应由 PayloadFieldMap<T> 承载）。");

object payload = accessor.CreateInstance();
accessor.Bind(root, payload);
```

> 消费方**不得**用反射取静态成员（`Type.GetProperty` / `MakeGenericMethod`）——那正是 F2 要消除的路径，
> 且在 `AotStrictMode=true` 下触发 `IL2070`/`IL3050`。

### 3.5 fluent `Map()` 是**受支持的手写公共 API**（G-ADR-9）

```csharp
// 路径 A：手写链（无需生成器；生成器缺席时体系完整可用）
public static IPayloadFieldMap<ContactUserChangedPayload> PayloadFieldMap { get; } =
    PayloadFieldMap<ContactUserChangedPayload>.Create(nameof(ContactUserChangedPayload))
        .Map("UserID",     (t, n) => { t.UserId        = C.Text(n); })
        .Map("Department", (t, n) => { t.DepartmentIds = C.Delimited<long>(n, ','); });

// 路径 B：生成链（特性声明；由 PayloadFieldMapGenerator 产出上面这段）
[PayloadContract(Converter = typeof(C))]
public sealed partial class ContactUserChangedPayload
{
    [PayloadField("UserID")]     public string? UserId { get; set; }

    [PayloadField("Department", Format = PayloadFieldFormat.Delimited, Separator = ',')]
    public List<long> DepartmentIds { get; set; } = new List<long>();
}
```

**两条路径产出完全同构的运行时对象**（同一个 `PayloadFieldMap<T>` 类型）⇒ 消费方可**逐类**渐进迁移
（「加特性 + 删手写链」在同一提交内完成），且随时可回退。

> **互斥约束**：同一类型**不得**同时声明手写 `PayloadFieldMap` 静态成员与 `[PayloadContract]`
> ——生成物是同名 `partial` 成员，重复声明将导致 **CS0102**。生成器主动报 `PAYLOAD008`，以给出可操作提示。
>
> **消费方注意（v2.0 补充）**：生成成员是 `public static`（与手写链同形），因此对启用了
> PublicApiAnalyzers 的消费方，该成员会进入其公共 API 面（需登记或改用 `internal` 手写链）。

### 3.6 `netstandard2.0` 兼容清单（上游运行时契约 + 生成物）

| 禁用 | 替代 | 依据 |
|---|---|---|
| `init` 访问器 / `record` | `{ get; set; }` + 构造器 | ns2.0 无 `IsExternalInit` |
| `ArgumentNullException.ThrowIfNull` | `x ?? throw new ArgumentNullException(nameof(x))` | ns2.0 无该 API |
| 集合表达式 `[]` | `new List<T>()` / `new T[0]` | **实测** C# 12，`LangVersion=7.3` 报 CS8370 |
| **`static` 匿名函数**（v2.0 新增） | 普通 lambda（无捕获由生成器构造保证） | **实测** C# 9，7.3 报 CS8370 |
| `#nullable enable`（生成物中） | 仅当消费方 `Nullable=enable` 时发射 | **实测** C# 8，7.3 报 CS8630 |
| `Math.Clamp` | `Math.Min` / `Math.Max` | ns2.0 无该 API |
| `FrozenDictionary` | 只读 `Dictionary` 包装（`ReadOnlyDictionary<,>` ns2.0 可用） | — |

### 3.7 线程安全不变式（v1.2）

> 由消费方 v2.2 的三模式支持论证触发：**「一个事件契约服务多种运行模式」会诱使把「当前模式」闭包进 `Map` 委托**。

1. `PayloadFieldMap<T>` 与其 `Map` 委托列表是**可被多线程共享的静态单例**（生成物是 `public static` 属性）。
2. 因此 **`Map` 委托必须无状态**：不得捕获任何可变请求态（当前应用模式 / 应用类型 / 租户 / 用户 / 请求对象 / `CancellationToken`）。
3. 确需上下文时，**在消费方读取器层处理**（先按上下文选择契约、再取无状态映射表），
   **不得**为映射表引入上下文参数（§11.8 A8 已否决）。

```csharp
// ✗ 违规：捕获可变请求态 ⇒ 映射表不再是单例语义（后果是跨请求串扰，且单线程测试全绿）
.Map("Status", (t, n) => { t.Status = Converter.ParseStatus(n?.Value, mode); });

// ✓ 正确：映射表无状态；模式分支在处理器层（evt 为逐请求对象）
.Map("Status", (t, n) => { t.Status = Converter.ParseStatus(n?.Value); });
if (evt.AppType == WechatAppType.Internal) { /* 自建仅回调子集，容忍 null */ }
```

**强制的实际手段（v2.0 修正 P3）**：v1 主张用 `static` lambda 让「捕获外层变量在编译期报错」，但
`static` 匿名函数是 **C# 9**，与 G-ADR-7 的 C# 7.3 基线**互斥**。修正后的强制手段是：

1. **生成物由生成器构造保证无捕获**：渲染器只输出形参 `t`/`n` 与转换器静态方法的调用，
   模板上**没有**任何可捕获的宿主表达式的插槽 ⇒ 生成链不可能违规；
2. **手写链**推荐 `static` lambda（C# 9+，消费方若已启用 nullable 即已 ≥ C# 8，升级成本低）；
3. **守卫**：`PayloadLanguageVersionGuardTests` 断言生成文本不含 `static (`（防未来有人为了「免费强制」而回退基线）；
4. 文档级不变式（本节的职责边界声明）。

### 5.4 格式推断表（生成器侧唯一真相源）+ 转换器签名契约

> **v2.0 重写**：v1 的表述有多处含糊（如「`List<string>` + `Separator`（可默认 `,`）」与「`List<string>` + `ItemName`」两行冲突、
> 「`int`/`long`/`bool` → 非空值类型」会产生 `CS0266`、`string`（非空）会产生 `CS8601`）。
> 下表为**已实现且被测试逐行覆盖**的精确规则：`Method` 存在时**优先**；否则按声明 `Format`，`Format = Auto` 时按属性类型推断。

| 目标属性类型 | 推断 Format | 生成的右值 | 备注 |
|---|---|---|---|
| `string?`（可空标注） | `Text` | `C.Text(n)` | **非空 `string` 在 `Nullable=enable` 下报 `PAYLOAD007`**（否则泄漏 CS8601，P4） |
| `T?`（`T` ∈ `int/long/short/byte/uint/ulong/float/double/decimal/char`） | `Text` | `C.Number<T>(n)` | 非空值类型无「缺失 ⇒ null」语义 ⇒ `PAYLOAD007` |
| `bool?` | `Text` | `C.Flag<bool>(n)` | 同上 |
| **枚举 / 可空枚举** | 无法推断 | — | 值域语义属消费方领域知识 ⇒ **必须 `Method`**，否则 `PAYLOAD007`（枚举仍可作为列表元素类型） |
| `List<T>`（`T` ∈ 标量/枚举），无 `ItemName` | `Delimited` | `C.Delimited<T>(n, ',')` | 分隔符取显式 `Separator` 或默认 `,` |
| `List<T>` + `ItemName`（无 `NameAttribute`/`ValueElement`） | `Items` | `C.Items<T>(n, "Item")` | **v2.5 收紧**：仅 `T` 为标量/枚举时推断 `Items`（`T` 带契约 ⇒ `ItemsObject`，其它 ⇒ `PAYLOAD007`——v2.4 对任意 `T` 都推断 `Items`，`List<复杂对象>` 会编译通过但运行期静默空结果） |
| `List<TItem>` + `ItemName` + `NameAttribute` + `ValueElement` | `ItemsWithAttributes` | `C.ItemsWithAttributes<TItem>(n, "Item", "Name", "Text")` | `TItem` 的形状由**消费方 Converter 的泛型约束**表达（生成器不校验，见下） |
| **`TSingle?`（引用类型带 `[PayloadContract]`，可空标注 ≠ `NotAnnotated`）** | `Object`（v2.5 / G-ADR-17） | `C.Object<TSingle>(n, (IPayloadContractAccessor)…TSingle.PayloadFieldMap)` | 单对象嵌套；优先于一切列表推断；oblivious（nullable 未启用）接受；显式 `Format = Object` 同口径校验，违反 `PAYLOAD007`；泛型实参不含 `?`（可空性由方法返回类型承载，见 §0.9 N4） |
| **`List<TNested>` + `ItemName`（`TNested` 带 `[PayloadContract]`）** | `ItemsObject`（v2.5 / G-ADR-17） | `C.ItemsObject<TNested>(n, "Item", (IPayloadContractAccessor)…TNested.PayloadFieldMap)` | 契约化对象项；内层类型须自行生成/持有 `PayloadFieldMap`（G-ADR-17b：生成器不验证成员存在，缺则消费编译 `CS0117`）；可空元素实参需消费方约束为 `class?`（或无约束） |
| 其它（含 `List<非契约复杂类型>` + `ItemName`、`List<自定义类>` 无 `ItemName`、非 `List<T>` 集合、自定义类型） | 无法推断 | — | `PAYLOAD007`（提示三种出路：改标量 / 给元素类型标 `[PayloadContract]` / 改用 `Method`） |

**转换器方法签名契约**（生成器按此查找并语义校验）：

| 方法 | 签名 | 语义要求 |
|---|---|---|
| `Text` | `static string? Text(PayloadNode? node)` | 节点缺失/空 ⇒ `null` |
| `Number<T>` | `static T? Number<T>(PayloadNode? node) where T : struct` | 解析失败 ⇒ `null`（**不抛**） |
| `Flag<T>` | `static T? Flag<T>(PayloadNode? node) where T : struct` | 同上 |
| `Delimited<T>` | `static List<T> Delimited<T>(PayloadNode? node, char separator)` | 非法片段**跳过**；节点缺失 ⇒ 空列表 |
| `Items<T>` | `static List<T> Items<T>(PayloadNode? node, string itemName)` | 空白项跳过；节点缺失 ⇒ 空列表 |
| `ItemsWithAttributes<TItem>` | `static List<TItem> ItemsWithAttributes<TItem>(PayloadNode? node, string itemName, string nameAttribute, string valueElement)` | `TItem` 由约束表达形状（如 `where TItem : IPayloadNamedValue, new()`）；AOT 安全（**不得**反射） |
| **`Object<TSingle>`（v2.5）** | `static TSingle? Object<TSingle>(PayloadNode? node, IPayloadContractAccessor accessor) where TSingle : class` | 节点缺失 ⇒ `null`；否则 `accessor.CreateInstance()` + `accessor.Bind(node, instance)`；`accessor` 由生成器传入 `TSingle.PayloadFieldMap` 的显式强转 |
| **`ItemsObject<TItem>`（v2.5）** | `static List<TItem> ItemsObject<TItem>(PayloadNode? node, string itemName, IPayloadContractAccessor itemAccessor) where TItem : class` | 逐项 `CreateInstance()` + `Bind(child, item)`；节点缺失 ⇒ 空列表；约束收敛 `class`（实例由桥的 `CreateInstance()` 新建，不强制 `new()`——内层类型经 `PayloadFieldMap<T>` 必然 `class, new()`）；**nullable 启用面推荐 `class?`（或无约束）**——非可空 `class` 约束与 `List<TItem?>` 可空元素实参构成生成期不可调和组合（`PAYLOAD004`） |
| 任意 `Method` | 首参为 `PayloadNode?` 或 `string?`（生成器按签名**自动绑定**，见下）；须 `static`、**非泛型**、**恰一个**参数 | 返回值须可隐式转换为属性类型（否则 `PAYLOAD005`） |

> **首参必须带可空标注（v2.4 收紧，P23）**：上表所有签名都以 `?` 书写契约 —— 这不是风格问题：
> 生成物交给转换器的正是**可能为 null** 的值（元素缺失时辅助方法收到 `null`，`Method` 路径收到 `n?.Value`），
> 首参写成非可空（`PayloadNode node` / `string text`）会让 `Nullable=enable` 的消费工程在**生成文件**里收到
> `CS8604`（`// <auto-generated/>` 不抑制）⇒ 报 `PAYLOAD004`。**唯一例外**：oblivious
> （`#nullable disable` / 未启用 nullable 的声明处，`NullableAnnotation.None`）仍被接受 ——
> 此时生成文件同样处于 oblivious 上下文、不会产生该告警，强行要求 `?` 反而会给消费方引入 `CS8632`。

**`Method` 的入参自动绑定（F1）**：

| 该方法首参类型 | 生成器生成的调用 |
|---|---|
| `PayloadNode?` | `C.M(n)` |
| `string?` | `C.M(n?.Value)` |
| `PayloadNode` / `string`（**非**可空标注，即 nullable 已启用却未写 `?`） | `PAYLOAD004`（v2.4：否则生成物报 `CS8604`） |
| 其它 / 无参 / 不存在 / 非 static / 泛型 | `PAYLOAD004` |

> 消费方**不必记忆**该传哪个：写 `string?` 参数即拿文本、写 `PayloadNode?` 参数即拿节点。
> **实现注记（P10）**：首参判定必须按「名称 + 命名空间」而非显示字符串 ——
> `PayloadNode?` 的可空标注是否出现在 `ToDisplayString()` 里取决于显示格式，字符串比较会漏判（已修）。
> **实现注记（P26）**：同名的**同元数重载**可能并存（如 `Delimited<T>(string, char)` 与 `Delimited<T>(PayloadNode?, char)`），
> 而 `GetMembers` 的返回顺序**不保证**契约签名在前 ⇒ 必须遍历**全部**结构候选、优选「形参类型 + 可空标注」双符合者，
> 否则会误报 `PAYLOAD004`（v2.4 实测）。

**边界声明（`ItemsWithAttributes` 的 `TItem` 形状）**：属性名/子元素名是**运行期字符串**，
生成器无法静态校验 `TItem` 是否具备对应属性；该形状由**消费方 Converter 的泛型约束**表达
（G-ADR-3 的职责边界）。生成器校验「方法存在 + 形参类型符合签名 + 泛型约束可满足 + 返回类型可赋给
`List<TItem>`」，但**不**校验「`TItem` 具备名为 `NameAttribute` 的属性」（同名运行期字符串，静态不可判定）。

**v2.2 收紧：上表由「文档约定」升级为「机器校验」**（修复前只校验「名称 + static + 形参个数 + 泛型元数」，
故形参类型错误会以 `CS1503` 漏到消费方编译期）：

| 校验项 | 实现 | 违反时 | 修复前后果（实测） |
|---|---|---|---|
| 形参**个数** | `FindContractMethod`（原有） | `PAYLOAD004` | — |
| 形参**类型**：首参 `PayloadNode`、`Delimited` 次参 `char`、`Items` 次参 `string`、`ItemsWithAttributes` 后三参 `string` | `HasContractParameterTypes`（v2.2） | `PAYLOAD004` | `CS1503`（`PayloadNode` → `string`） |
| 泛型**元数** | `FindContractMethod`（原有） | `PAYLOAD004` | — |
| 泛型**约束可满足性**：`struct` / `class` / `unmanaged` / `new()` / `ConstraintTypes` | `AreTypeArgumentsSatisfied`（v2.2） | `PAYLOAD007` | `CS0315`（`long` 不满足 `where T : IShape`） |
| 返回类型可赋值 | `ClassifyCommonConversion`（原有） | `PAYLOAD005` | — |

> **约束校验的两个实现细节**（都源自「误报比漏报更致命」）：
> ① `ITypeSymbol.IsValueType` 为真时**短路视为满足 `new()`** —— Roslyn 的 `InstanceConstructors`
> 不包含隐式结构体默认构造，直接查构造器会把 `Delimited<T> where T : new()` 配 `List<long>` 误判为违约；
> ② 约束项本身是类型参数（`where T : U`）时**跳过** —— 转换判定不可用，且本生成器的类型实参恒为具体类型
> （载荷类非泛型）。两类正向对照已进测试矩阵（§7.2）。

**v2.2 收紧：类型实参保留可空标注**（G-ADR-16）：渲染泛型实参时使用

```csharp
SymbolDisplayFormat.FullyQualifiedFormat.WithMiscellaneousOptions(
    SymbolDisplayMiscellaneousOptions.UseSpecialTypes |
    SymbolDisplayMiscellaneousOptions.IncludeNullableReferenceTypeModifier)   // 与既有生成器同口径
```

⇒ `List<string?>` 渲染为 `Delimited<string?>(n, ',')`（而非 `Delimited<string>`），
与属性类型的可空性一致（否则消费方收 `CS8619`）。同一格式也用于「字段类型指纹」，
使 **可空标注变化必然触发本类重生成**（否则「只补一个 `?`」会命中增量缓存、产出过期生成文件）。

**渲染纪律**（v2.0 已按实测收紧）：

| 规则 | 理由 |
|---|---|
| 一律 `global::` 全限定、**零 `using`**（`GenerateFileHeader` 传空命名空间列表） | 消除「消费方 `GlobalUsings` 差异 ⇒ 生成代码编译失败」 |
| **不使用 `static` lambda** | 实测 C# 9，ns2.0 默认 `LangVersion=7.3` 报 CS8370（P3）；无捕获由生成器构造保证 |
| 文件头用 `TransitiveCodeGenerator.GenerateFileHeader` + `GeneratedCodeConsts` | 单一事实源；FIX-16 固定 `\n` 换行 |
| `[CompilerGenerated]` + `[GeneratedCode]` 随 `MudEmitGeneratedCodeMarkers` 开关 | 复用既有开关（**不新增** `PayloadFieldMapEmitMarkers`） |
| **生成成员带 XML 文档注释** | 实测 auto-generated 头**不**抑制 CS1591（消费方 `GenerateDocumentationFile=true` 即告警，P4） |
| 换行固定 `\n`；缩进 4 空格 | 同 FIX-16 |
| `partial` 而非生成完整类 | 类名与属性由消费方手写（公共 API 的 XML 文档亦由消费方负责）；实测「无访问修饰符的 partial 声明 + `public sealed partial`」**合法**（无 CS0262） |
| 成员名固定为 `PayloadFieldMap`（常量，非配置项） | 它是**契约的一部分**：消费方注册入口直接书写该名；集中定义 `GeneratedMemberName`（供互斥检查复用） |
| **声明的标识符（类名 / 属性名）必须做保留字转义**（v2.4 / P24） | `ISymbol.Name` **不含** `@`：`public partial class @class` / `[PayloadField] public string? @event` 直接拼接会产出 `partial class class` / `t.event = …`，生成文件报 `CS1001`/`CS1519`/`CS1513`，且消费方的类被连带报 `CS0260`（指向错误位置）。渲染器用 `SyntaxFacts.GetKeywordKind` 判定后补 `@`；`TypeDisplay` 侧由 `FullyQualifiedFormat` 自带的 `EscapeKeywordIdentifiers` 覆盖 |
| 属性 `get { return …; }`（每次读取构造新映射表） | 列表很小；消费方若在热路径反复取用可自行 `static readonly` 缓存（§12 D3） |

### 9.2 消费方（`Mud.Wechat`）采用路径

`Mud.Wechat` v2 方案的 Phase 1（手写 binder）**不受本设计影响，可先行落地**。本设计是 Phase 2 的可选替换：

#### ⭐ 关键接入步骤（v2.3 补，缺陷 22）

**「声明载荷类的工程」必须显式再挂一次生成器**——这是最容易漏、且症状最远离根因的一步：

```xml
<!-- 该工程＝真正写下 [PayloadContract] 的那个工程（如 Mud.Wechat 自身） -->
<ItemGroup>
  <!-- Mud.HttpUtils 元包只把生成器传给「直接引用它的工程」；
       生成器包以 PrivateAssets="all" / OutputItemType="Analyzer" 引用 ⇒ 不会流向间接引用工程。 -->
  <PackageReference Include="Mud.HttpUtils.Generator" Version="…" PrivateAssets="all" OutputItemType="Analyzer" />
</ItemGroup>
```

- **缺失时的症状**：该工程**不运行**生成器 ⇒ `[PayloadContract]` 类缺少 `PayloadFieldMap` 成员 ⇒ csc 报 **`CS0117`**（"不包含 PayloadFieldMap 的定义"），且**生成器不会给出任何 `PAYLOAD*` 诊断**（因为它根本没被加载）。
- **误判陷阱**：症状表现为「生成器坏了」，实际是「生成器没到场」。由于无任何诊断，靠日志/诊断无法定位，只能靠检查**该工程自身的** `PackageReference`/`ProjectReference` 是否带 `OutputItemType="Analyzer"`。
- **自检**：构建后确认该工程的 `obj/…/generated/`（或 `EmitCompilerGeneratedFiles=true` 输出目录）中存在 `<载荷类>.PayloadFieldMap.g.cs`；或临时写入一个非法载荷（如给 `struct` 加 `[PayloadContract]`）确认能收到 `PAYLOAD009`。

| 步 | 消费方动作 | 可回退性 |
|---|---|---|
| 1 | 载荷类改 `partial` + 加 `[PayloadContract]`/`[PayloadField]`，**同时删除**同文件手写 `BuildBinder()` | 单提交可回退（Git） |
| 2 | binder/注册表改为持有 `IPayloadFieldMap<T>` / `IPayloadContractAccessor` | 保留旧路径，两条并存 |
| 3 | 过渡期完成后删除旧路径 + 更新其守卫与 README | 单提交可回退 |
| 4 | `scripts/` 中若未来出现字段映射类脚本，一并退役 | — |

> **G-ADR-5 的收益**：切换是**逐类**的（有特性即生成，无特性即保留手写），不需要 `#if`，可按 5 个结构族载荷分 5 个提交灰度。

## 11. 被否决的备选方案

### 11.1 A1：文本模板 / PowerShell 脚本生成（消费方现状）
无语义（元素名拼错、属性改名均无法发现）、无 IDE 体验、无法校验转换方法签名。**否决**。
文本形态在本仓库的唯一存续理由是 STJ 链式不可行，本设计不受该约束。

### 11.2 A2：为「配置键无消费点」等审计需求做生成器
属**语义分析**，正确形态是 `DiagnosticAnalyzer` + `RegisterCompilationAction`，**生成器无法报告诊断**。**否决**。

### 11.3 A3：让本生成产物被 `System.Text.Json` 消费
**否决（硬约束）**：Roslyn 生成器**互不可见**（dotnet/roslyn#57239）⇒ 静默空 Context。
本设计刻意让生成物**只被手写引擎消费**（G-ADR-1）。

### 11.4 A4：反射 / `Expression.Compile` 生成映射
触发 `IL2067/IL2070/IL3050`；`Expression.Compile` 在 `AotStrictMode=true` 下直接打红门禁。**否决**。

### 11.5 A5：T4 文本模板
无语义校验能力（与 A1 同类缺陷），且模板引擎依赖需随包分发。**否决**。

### 11.6 A6：把转换逻辑内联生成（不依赖消费方 Converter）
**否决**：① 同一语义在 N 个字段重复生成，无法集中单测；② 生成文件体积与可读性显著变差；③ 枚举/自定义类型仍需回落方法引用。
改为 G-ADR-3（`typeof` 强类型 Converter + 生成器语义校验）。

### 11.7 A7：新建独立工程 `Mud.HttpUtils.Payloads.Generator`
**否决**：① 使 `pack.ps1` 的 10 个包变 11；② 与「多个生成器族同处 `Mud.HttpUtils.Generator`」的既有形态不一致；③ 需重复整套 `netstandard2.0` + `IsRoslynComponent` + `AnalyzerReleases` + `PublicAPI` 配置。

### 11.8 已评估但不采纳（后续候选）

| 候选 | 说明 |
|---|---|
| 生成载荷类的 `Values` 全量袋填充代码 | 袋的构建需要「作用域节点 + 敏感节点排除清单」，与消费方策略强相关 ⇒ 留在消费方运行时 |
| 字段级必填/范围校验生成 | 属运行期契约（消费方 `Status` 状态机），不在生成期 |
| 载荷类的 `ToString()`/相等性生成 | 无实际需求（载荷是快照，不作值比较） |
| 跨程序集载荷契约（契约在 A 程序集、载荷在 B） | 无消费方诉求；`partial` 要求同程序集是 Roslyn 固有约束 |
| 生成 `PayloadNode` 的 XML→节点适配器 | 该适配器**必须**由消费方写（上游不得引入 `System.Xml`，见 §11.9） |
| **A8** 为「应用模式 / 租户 / 多租户」维度提供映射上下文参数 | **否决（v1.2）**：映射表须保持**无状态**才能安全地被多线程共享（§3.7）。引入上下文参数会诱发「把当前模式闭包进委托」⇒ 跨请求串扰，且单线程测试全绿 |
| **A9** 支持泛型 / 嵌套载荷类（v2.0） | **否决**：与 `new()` 约束、`partial` 容器链互斥，收益低于复杂度（`PAYLOAD009`） |
| **A10** `PAYLOAD101`（Info：建议显式指定 `Method`）（v2.0） | **否决**：为纯风格建议引入编译级分析器属过度设计；可操作场景由 `PAYLOAD007` 覆盖 |
| **A11** 新增 `DisablePayloadFieldMapGenerator` / `PayloadFieldMapEmitMarkers` / `PayloadGeneratorConfigSnapshot`（v2.0） | **否决**：与既有开关/快照语义重复，且需 props/README/测试三处同步（G-ADR-12） |
| **A12** 支持「继承基类上的 `[PayloadField]`」（v2.2 评估后否决，改为 fail-fast） | **否决**：① `GetMembers()` 只返回本类成员且特性 `Inherited=false` ⇒ 静默忽略等于**静默丢字段**（本能力的存在理由）；② 真正「支持」需处理一连串语义——基类→派生类的字段序、`override` 使同一属性被收集两次（会误报「元素名重复」）、基类 `private setter` 的可达性、`internal` 基类跨程序集——收益低于复杂度；③ 消费方有零成本出路（字段下沉到本类，或该类改用手写映射表）。⇒ 生成期 `PAYLOAD009` + 可操作修法 |
| **A13** 支持索引器 / 显式接口实现属性（v2.2 评估后否决） | **否决**：生成物以 `t.<属性名> = …` 赋值，两者成员名不可这样书写；「支持」需生成不同赋值语法（`t[i]`、`((IFoo)t).X`）并推导索引参数——属**推测需求**（无消费方诉求）⇒ `PAYLOAD006` |
| **A14** 对 `List<string?>` 等可空元素形态改用「拒绝」而非「可空标注渲染」（v2.2 评估后否决） | **否决**：拒绝会把**本可正确表达**的声明（`List<string?>` 是合法载荷属性类型）判为非法，而 `?` 的信息在符号层完整可得；正确解是**忠实渲染**（G-ADR-16）。风险（nullable 关闭的消费工程会多一条 `CS8632`）与其源码自身已有的同码告警同源，可接受 |

### 11.9 硬边界复核：上游不得引入 **LINQ to XML**（v2.1 已机器化守卫）

`PayloadNode`（§3.1）是 XML-free 的纯数据投影。**上游 `Mud.HttpUtils`、`Mud.HttpUtils.Abstractions`、
`Mud.HttpUtils.Attributes` 与 `Mud.HttpUtils.Generator` 均不得出现 LINQ to XML**
（`System.Xml.Linq` / `XDocument` / `XElement` / `XAttribute` / `XName` / `XNamespace`）。
XML→`PayloadNode` 的适配器写在**消费方**（`Mud.Wechat` 的 `XElementPayloadSource`）。

> **⚠️ v2.0 表述过宽，v2.1 已收窄（重要更正）**：v2.0 原写「均不得出现 `System.Xml.*`」——
> 该表述**与既有实现冲突**：`Mud.HttpUtils.Generator` 为 `[SerializationMethod(Xml)]` 特性
> **合法生成** `System.Xml.Serialization.XmlSerializer` / `System.Xml.XmlWriter` 代码
> （`RequestBuilder.cs:496-502`、`ConstructorGenerator.cs:307-316`、`MethodGenerator.cs:852-891`），
> `Mud.HttpUtils.Abstractions` 亦有公共属性 `ResponseDescriptor.XmlSerializer`。
> ⇒ 拦截面**只**是 **LINQ to XML**，`XmlSerializer` / `XmlWriter` / `XmlSerializerNamespaces` /
> `System.Xml.Serialization` **不在**拦截面内。按原表述设守卫会立刻误报。

**机器化守卫（v2.1 已实施）**：`Tests/Mud.HttpUtils.Generator.Tests/Guards/GeneratorSourceContractTests.cs`
的 `UpstreamPayloadSurface_MustNotDependOnLinqToXml` 扫描上述 4 个工程的 `.cs`（排除 `obj`/`bin`）。

> **实现要点（v2.0 的「~20 行文本扫描」不够）**：`PayloadNode.cs:20,21,95` 的 **XML 文档注释**中即出现
> `XElement` / `System.Xml` 字样（用于说明「对应 `XElement.Value` 的全后代文本语义」）。
> 朴素物理行匹配会把这些**说明性注释**判为违规实现 ⇒ 守卫必须做**字符串感知的注释剥离**
> （含 `//`、`/* */`、普通/逐字字符串与字符字面量），实际成本 ~40 行。
> **非空转已验证**：临时注入 `System.Xml.Linq.XElement` 依赖 ⇒ 守卫失败并精确定位到
> `Mud.HttpUtils.Abstractions/<probe>.cs:7`；移除探针后恢复绿。

### 11.10 上游契约不得反向依赖 HTTP 语义

运行时契约落在 `Mud.HttpUtils.Abstractions`，但**不**引用任何 HTTP 类型（`HttpClient` / `HttpRequestMessage` / `HttpContent`），
仅依赖 `System.Collections.Generic` + `System`。⇒ 「报文投影」与「HTTP 传输」在编译期无耦合，
未来可被非 HTTP 场景复用（如本地文件/队列报文的载荷映射）。
