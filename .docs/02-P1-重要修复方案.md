## #10 🟠 超时异常类型不一致（`TimeoutRejectedException` vs `ApiRequestException`）

### 问题定位

| 触发源 | 抛出类型 | 位置 |
|--------|----------|------|
| Polly 悲观超时（全局或方法级） | `Polly.Timeout.TimeoutRejectedException` | `PollyResiliencePolicyProvider.cs:197-199`（全局）与 `:355-365`（方法级 `BuildMethodPolicy`） |
| `HttpClient.Timeout` | `ApiRequestException(isTimeout: true)` | `EnhancedHttpClient.cs:1030-1034`（`ExecuteHttpRequestCoreAsync` 的 catch） |

上游无法用统一模式识别超时；且 Polly 第三方类型泄漏到框架公共 API 面。

### 原方案的漏洞（验证结论）

原方案把包装放在 `ResilientHttpClient` 出口 —— 但**方法级弹性路径不经过 `ResilientHttpClient`**
（executor 先 `SetSkipResilienceFlag` 使其直通），方法级 `[Timeout]` 的 `TimeoutRejectedException`
仍会裸抛，修复不完整。

### 修复设计（修订）：包装下沉到两条路径共用的 `EnhancedHttpClient.ExecuteHttpRequestCoreAsync`

`ExecuteHttpRequestCoreAsync`（`EnhancedHttpClient.cs:1005-1066`）是**所有**请求（内置方法 + 生成代码 +
全局弹性 + 方法级弹性）的汇聚点，且位于 Polly 策略**之内**（被重试包装）——不能在这里包装
`TimeoutRejectedException`（会被 Polly 的 `Or<TimeoutRejectedException>` 判定吞掉、破坏重试计数）。

正确位置是**策略边界之外、用户边界之内**的两个包装点，且二者逻辑相同 → 抽共享方法：

```csharp
// Mud.HttpUtils.Resilience 内新增 internal 工具（两处复用）
internal static class PollyExceptionNormalizer
{
    public static Exception? TryNormalize(Exception ex, HttpRequestMessage? request)
    {
        if (ex is TimeoutRejectedException)
            return new ApiRequestException(
                $"请求超时: {request?.RequestUri}", ex,
                isTimeout: true, requestUri: request?.RequestUri?.ToString());
        if (ex is BrokenCircuitException)
            return new ApiRequestException(
                $"熔断器已打开: {request?.RequestUri}", ex,
                isCircuitOpen: true, requestUri: request?.RequestUri?.ToString());
        return null;   // 无需包装
    }
}
```

接入点（两处，覆盖全部流量）：

1. **全局路径**：`ResilientHttpClient` 各公共方法在 `policy.ExecuteAsync` **返回后** catch 包装
   （原方案的 `NormalizeOutcomeAsync` 模式，保留）。
2. **方法级路径**：`ResiliencePolicyResolver.ResolvePolicyWrapper:73-94` 的返回 lambda 外层
   同样 catch 包装。

**要点**

- 包装必须在 `policy.ExecuteAsync` 之外（两条路径都是），否则异常被喂回 Polly、重试判定失真。
- `ApiRequestException` 已有 `isTimeout`；新增 `isCircuitOpen` 属性（公共 API，同步 4 份
  `PublicAPI.Unshipped.txt`）。
- 不要在 `ExecuteHttpRequestCoreAsync` 里包装（见上）。

### 验收

- 用例：**全局** Polly 超时触发 → 抛 `ApiRequestException` 且 `IsTimeout == true`，`InnerException is TimeoutRejectedException`。
- 用例：**方法级** `[Timeout]` 超时触发 → 同上（原方案会漏掉这条）。
- 用例：断言超时**仍会重试**（包装未破坏 `Or<TimeoutRejectedException>()` 判定）。
- 用例：熔断打开 → `ApiRequestException.IsCircuitOpen == true`。

## #12 🟠 默认对非幂等方法重试（重复提交风险）

### 问题定位

```
RetryOptions.cs:22（Options 子目录）        Enabled = true（默认开启，且不限方法）
ResilientHttpClient.cs:74-87                 ShouldSkipRetry 仅比较 Content-Length，不看 HTTP 方法
```

### 原方案的漏洞（验证结论）

原方案把幂等判定放在 `ResilientHttpClient.ShouldSkipRetry` —— 只挡住**全局**重试；
**方法级** `[Retry]` 的策略在 `PollyResiliencePolicyProvider.BuildMethodPolicy:436-501` 构建，
不经过 `ResilientHttpClient`，POST 照样被方法级重试。

### 修复设计（修订）：幂等判定下沉到**策略构建层**

`BuildMethodPolicy` 构建重试 `Handle` 谓词时，把"请求方法是否可重试"编入判定；
全局路径 `BuildRetryPolicy` 同样处理。判定依据是 `ExecuteAsync` 传入的 request ——
但 Polly v7 `WaitAndRetryAsync` 的谓词只收到 `exception`，拿不到 request。
因此改在**克隆决策层**做（方法级在 `ResiliencePolicyResolver`，全局在 `ResilientHttpClient`），
模式统一为"先判定是否允许重试，不允许则只建超时+熔断策略"：

#### 12.1 共享判定（放 `Mud.HttpUtils.Resilience`，两处复用）

```csharp
internal static class RetryGuard
{
    public static bool IsRetryAllowedForMethod(
        HttpRequestMessage request, ResilienceOptions? options)
    {
        if (options?.Retry?.AllowNonIdempotentRetry == true) return true;
#if NETSTANDARD2_0
        if (request.Properties.TryGetValue(
                HttpExecutionConstants.AllowNonIdempotentRetryPropertyKey, out var v) && v is true)
            return true;
#else
        if (request.Options.TryGetValue(new HttpRequestOptionsKey<bool>(
                HttpExecutionConstants.AllowNonIdempotentRetryPropertyKey), out var v) && v)
            return true;
#endif
        return options?.Retry?.RetryableHttpMethods?.Contains(request.Method.Method) ?? false;
    }
}
```

#### 12.2 新增常量与配置

```csharp
// HttpExecutionConstants.cs（Abstractions）
public const string AllowNonIdempotentRetryPropertyKey = "__Mud_HttpUtils_AllowNonIdempotentRetry";

// RetryOptions.cs（Resilience）
public bool AllowNonIdempotentRetry { get; set; } = false;
public HashSet<string> RetryableHttpMethods { get; set; } =
    new(StringComparer.OrdinalIgnoreCase) { "GET", "HEAD", "OPTIONS", "PUT", "DELETE", "TRACE" };
```

#### 12.3 两个决策点

1. **全局路径**：`ResilientHttpClient` 各公共方法入口（`SendAsync`/`SendRawAsync`/`SendStreamAsync`/
   `SendXmlAsync`/流式重载），在现有 `ShouldSkipRetry:74-87` 中**增加方法判定**：
   不可重试 → 走 `ExecuteWithoutRetryAsync`（保留超时+熔断）——正是现状对大内容请求的处理模式。
2. **方法级路径**：`ResiliencePolicyResolver.ResolvePolicyWrapper:57-58` 的"无策略启用返回 null"
   之前增加：若 `options.RetryEnabled && !RetryGuard.IsRetryAllowedForMethod(requestTemplate, _retryOptions)`
   → 把 `retryEnabled` 置 false 再构建（即方法级退化为超时+熔断，重试静默关闭 + `LogInformation` 一条）。
   `ResiliencePolicyResolver` 需注入 `IOptions<ResilienceOptions>` 获取 `Retry` 配置（构造函数已接收
   `IOptions<ResilienceOptions>`，直接用）。

> 谓词为什么不在 `BuildMethodPolicy` 里加：Polly v7 重试谓词只有 exception，没有 request；
> 且策略按 `PolicyCacheKey`（参数组合）缓存，无法按请求方法区分实例。决策放在 resolver/装饰器层
> 是唯一正确位置。`ResilienceExecutionOptions`（Abstractions，`:61-107`）是**每个方法的描述符**，
> 也无法承载全局 `RetryOptions` —— 因此判定输入取"全局 RetryOptions + 请求属性标记"，方法级特性
> `AllowNonIdempotent` 通过生成代码写请求属性（12.4）。

#### 12.4 生成器侧（M2 内完成，非 M3）

1. `RetryAttribute`（`Mud.HttpUtils.Attributes/RetryAttribute.cs`）新增
   `public bool AllowNonIdempotent { get; set; }`；
2. `MethodGenerator.WriteExecutionDescriptorCode`（`:506-523` 附近）生成代码时，若
   `AllowNonIdempotent == true`，在请求构造后写
   `__httpRequest.Properties/Options[AllowNonIdempotentRetryPropertyKey] = true`（沿 `SetSkipResilienceFlag`
   的双 TFM 写法）；
3. 新增诊断 `HTTPCLIENT020`（Warning）：接口方法声明 `[Retry]` 且 HTTP 方法为非幂等但未显式
   `AllowNonIdempotent = true`（R-6 的最小版，提前到 M2，因未发布无静默期）。

### 验收

- 用例：**全局** `[Retry]` 等效配置 + POST + Stub 连续 503 → 断言仅 1 次请求（不重试）。
- 用例：**方法级** `[Retry]` + POST + 503 → 断言仅 1 次请求（原方案会漏掉这条）。
- 用例：`[Retry(AllowNonIdempotent = true)]` + POST → 断言重试生效。
- 用例：GET + 503 → 断言重试仍生效（防过度防护）。
- 用例：断言非幂等跳过重试时，**超时与熔断策略仍然生效**（走 `ExecuteWithoutRetryAsync` / 退化构建）。

## #13 🟠 流式枚举提前退出被记为错误

### 问题定位

```
EnhancedHttpClient.cs:424-484（options 重载）与 :494-668（AOT JsonTypeInfo 重载，同样逻辑）
  424:  recordedSuccess = true;                 // 仅完整枚举后设置
  455-477:  else 分支构造 InvalidOperationException("流式异步枚举未成功完成") 记 error 指标 + Error Span
```

（"流式异步枚举未成功完成" 字符串出现于 `:457` 与 `:631` 两处，验证确认。）

调用方 `break` / `FirstOrDefaultAsync` / `Take(n)` 是**合法用法**，却被记录为 error 指标 + Error Span。

### 修复设计：引入三态

```csharp
HttpResponseMessage? response = null;
var faulted = false;         // 真正的失败
Exception? pendingException = null;
try
{
    ...
    await foreach (var item in ...) { yield return item; }
}
catch (Exception ex) { faulted = true; pendingException = ex; throw; }
finally
{
    response?.Dispose();
    if (!alreadyObserved)
    {
        var elapsedMs = sw.GetElapsedTime().TotalMilliseconds;
        if (faulted)
        {
            // 保留原异常语义（而非伪造 InvalidOperationException）
            MudHttpObservability.RecordError(activity, pendingException, elapsedMs, ClientName, request);
            AddRequestFailedEvent(...);
        }
        else
        {
            // 完整枚举 or 提前退出（break）→ 都是成功
            MudHttpObservability.RecordSuccessFromRequest(activity, request, elapsedMs, ClientName);
            AddRequestStoppedEvent(...);
        }
        MudHttpObservability.MarkObserved(request);
    }
    activity?.Dispose();
}
```

**要点**

- `catch` 中保存异常引用，`finally` 中使用（`throw` 在 catch 中已发生，`pendingException` 仅供 finally 读）。
- **两处**重载都要改：`:305`（options）与 `:494`（AOT JsonTypeInfo，错误标记在 `:631`）。
  （生成代码路径经 `DefaultHttpRequestExecutor.SendAsAsyncEnumerable:466-473` 直通这两个方法，修好即全覆盖。）
- 可选：成功事件加 `stream_completed` 布尔 tag（区分完整完成与提前退出；事件 tag 非指标 tag，无基数问题）。

### 验收

- 用例：`await foreach` 中取 1 个后 `break` → 断言 `mud.http.requests` 的 `outcome != "error"`，Activity 状态为 `Ok`。
- 用例：枚举中途抛异常 → 断言仍记录 error，且异常类型与实际抛出一致（不再是 `InvalidOperationException("流式异步枚举未成功完成")`）。
- 用例：AOT 重载（JsonTypeInfo）同样验证 break 场景。

## #14 🟠 `MemoryHttpResponseCache` 缓存条目可变字段并发读写

### 问题定位

```
Mud.HttpUtils.Client/HttpClient/MemoryHttpResponseCache.cs
   49-55:  TryGet 中 entry.ExpireTime / entry.LastAccessTime 无锁写
   86-91:  Set 中直接索引赋值
  227-243: CacheEntry 为可变类（ExpireTime/LastAccessTime 为 { get; set; }，DateTimeOffset 16 字节赋值非原子）
```

### 修复设计：条目不可变化 + `TryUpdate` 原子替换

```csharp
private sealed class CacheEntry
{
    public readonly object Value;
    public readonly DateTimeOffset ExpireTime;
    public readonly long LastAccessTime;
    public readonly bool UseSlidingExpiration;
    public readonly TimeSpan SlidingWindow;

    public CacheEntry Touch(long seq) =>
        new CacheEntry(Value,
            UseSlidingExpiration && SlidingWindow > TimeSpan.Zero
                ? DateTimeOffset.UtcNow.Add(SlidingWindow) : ExpireTime,
            seq, UseSlidingExpiration, SlidingWindow);
}

public bool TryGet<T>(string key, out T? value)
{
    if (!_cache.TryGetValue(key, out var entry)) { value = default; return false; }
    if (entry.ExpireTime <= DateTimeOffset.UtcNow)
    {
        _cache.TryRemove(new KeyValuePair<string, CacheEntry>(key, entry));  // 条件移除，避免误删新值
        value = default; return false;
    }
    _cache.TryUpdate(key, entry.Touch(Interlocked.Increment(ref _accessCounter)), entry);
    value = (T?)entry.Value;
    return true;
}
```

**要点**

- `ConcurrentDictionary.TryUpdate(key, newValue, comparisonValue)` 做 CAS，天然幂等且无锁。
- `TryRemove(KeyValuePair)` 重载避免"读到旧值 → 另一线程已换新值 → 误删"。
- `EvictIfOverCapacity` 的 LRU 排序在并发下本就是近似值，保持现状（不引入锁）。
- `GetOrFetchAsync` 的 `_fetchLocks`（`SemaphoreSlim`）逻辑不动（其无界增长是 #24，独立处理）。

### 验收

- 用例：64 线程并发 `GetOrFetchAsync` 同一 key → 断言回源次数为 1。
- 用例：滑动过期条目并发 `TryGet` → 断言 `ExpireTime` 不出现撕裂值（循环 10 万次，断言始终 `> UtcNow` 或已过期，不出现中间态）。

## #16A 🟠 `QueryParameterBuilder.Add` 静默丢弃空串导致 `IncludeNullValues` 失效

### 问题定位

```
Mud.HttpUtils.Abstractions/HttpClient/Query/QueryParameterBuilder.cs:45-55
   50:  if (string.IsNullOrWhiteSpace(value)) return;     // ← 空串 / 空白一律丢弃

Mud.HttpUtils.Generator/Generators/Implementation/Binders/QueryParameterBinder.cs:522-531
   IncludeNullValues=true 时生成 __queryParams.Add("<key>", string.Empty)
```

生成器为 `IncludeNullValues = true` 生成的 `Add(key, string.Empty)` 被 `Add` 静默丢弃，
该配置项**完全失效**。注意 `QueryMapHelper.FlattenObjectToQueryParams`（Client，`:65-77`）在
`includeNullValues=true` 时同样产出 `key=` 空串对 —— 两条路径都被 `Add` 的空串过滤拦截。

### 修复设计（修订：直接改语义，不新增重载）

`null` 与"空字符串"是两种语义：前者应跳过，后者是**值**（`key=` 是合法 query 表达）。

```csharp
/// <summary>添加查询参数（null 将被忽略；空串按值保留，序列化为 "key="）。</summary>
public void Add(string name, string? value)
{
    if (string.IsNullOrWhiteSpace(name))
        throw new ArgumentNullException(nameof(name));

    if (value is null)
        return;                       // ← 只过滤 null

    _params.Add(new KeyValuePair<string, string>(name, value));
    _cachedQueryString = null;
}
```

原方案的"方案 4"（新增 `Add(name, value, includeEmpty)` 重载，保持 `Add` 现状）是为兼容旧行为设计的；
**项目未发布，无兼容义务**，直接改语义更干净——否则 `Add`（公共 API）将携带两个语义重叠的重载，
属于冗余设计。空白串（`"  "`）按新语义同样保留（它是调用方显式给的值；若下游不想发送应传 null）。

**配套核查结论**（已逐点验证，不影响其他调用方）：

- `QueryParameterBinder.GenerateSimpleQueryParameter`（string 类型）→ 传参数值，null 仍被过滤 ✓
- `QueryParameterBinder.GenerateArrayQueryUrl`（`:255`，`string.Join` 结果）→ 数组为空时外层已 `Any()` 判断，空数组路径不进 `Add` ✓
- `RequestBuilder.GenerateQueryParameters:173-183` / `GenerateInterfaceQueryProperty` → null 过滤路径 ✓
- 各强类型重载（`DateTime?` 等）最终 `ToString()` 产生 null 时仍被过滤 ✓
- `QueryMapHelper` 的 raw 路径（`key=` 直接拼串，不经 `Add`）行为不变 ✓

### 验收

- 用例：`[QueryMap(IncludeNullValues = true)]` 对象含 `null` 属性 → 断言生成的 URL 含 `key=`。
- 用例：`[QueryMap(IncludeNullValues = false)]`（默认）→ 断言 `key` 不出现。
- 用例（锁定契约）：`Add("a", null)` 不产生参数；`Add("a", "")` 产生 `a=`；`Add("a", "  ")` 产生 `a=%20%20`（转义后）。

### 问题定位

## #19 🟠 重试克隆破坏流式上传与上传进度语义（含 N-3）

### 问题定位（验证修订：共 **3 处**首次克隆，原方案只列 1 处）

```
ResilientHttpClient.cs:121              全局路径 ExecuteWithCloneAsync（SendAsync/SendRawAsync/SendStreamAsync/SendXmlAsync）
ResilientHttpClient.cs:221/259          流式枚举连接期 ExecuteStreamWithResilienceAsync ×2
ResiliencePolicyResolver.cs:79         方法级弹性路径（原方案遗漏）
```

**首次尝试也克隆**，导致：

- `RequestBodySerializationMode.Streamed`（`EnhancedHttpClient.cs:975`）的流式上传被整体缓冲进内存；
- `ProgressableStreamContent` 在克隆阶段就通过 `SerializeToStreamAsync` 跑满进度（N-3）；
- 大文件上传时 `MaxCloneContentSize` 默认 10 MB，超限直接抛异常而非降级发送。

### 修复设计：首次不克隆，仅重试时克隆（**3 处同步**）

```csharp
// 模式（以 ExecuteWithCloneAsync 为例；ResiliencePolicyResolver 与流式路径同构）
return await policy.ExecuteAsync(async (ctx, ct) =>
{
    var isRetry = ctx.TryGetValue(PollyResiliencePolicyProvider.RetryCountContextKey, out _);
    HttpRequestMessage execRequest;
    bool ownsRequest;
    if (isRetry)
    {
        execRequest = await HttpRequestMessageCloner.CloneAsync(request, MaxCloneContentSize, ct).ConfigureAwait(false);
        ownsRequest = true;
    }
    else
    {
        execRequest = request;      // 原样发送，保持流式/进度语义
        ownsRequest = false;
    }

    try
    {
        if (isRetry && ctx.TryGetValue(PollyResiliencePolicyProvider.RetryCountContextKey, out var rc) && rc is int retryCount)
            MudHttpObservability.RecordRetryCount(execRequest, retryCount);
        return await executeFunc(_innerClient, execRequest, ct).ConfigureAwait(false);
    }
    finally { if (ownsRequest) execRequest.Dispose(); }
}, context, cancellationToken).ConfigureAwait(false);
```

**要点**

- `RetryCountContextKey`（`PollyResiliencePolicyProvider.cs:49`，`"__mud_retry_count"`）由 `onRetryAsync`
  在**每次重试前**写入（`:148`/`:470`），首次执行时不存在，语义天然正确。
- **不得 dispose 原请求**（调用方持有生命周期）。
- 首次执行修改原请求的安全性（R7）：`ApplyRequestConfig`（`DefaultHttpRequestExecutor.cs:695-714`）
  net5+ 用 `Options.TryAdd`（不覆盖，幂等）、ns2.0 用索引赋值（覆盖同值，幂等）——已核查安全；
  `EnhancedHttpClient` 侧首次发送会 `SetStatusCode`/`SetContentLength` 写请求属性，同样幂等覆盖。
- **流式路径**（`ExecuteStreamWithResilienceAsync`）改造时注意：返回 `IAsyncEnumerable`，克隆在
  iterator 内部首次 `MoveNextAsync` 才发生——首次不克隆意味着 iterator 直接枚举原请求，语义不变。
- **便捷方法**（`ExecuteWithoutCloneAsync:185-194`，GetAsync/PostAsJson 等）已天然"每次执行重建请求"
  （`EnhancedHttpClient.SendJsonWithBodyAsync:938` 每次 new），保持现状，见 00 册 N-5。

### 验收

- 用例：`RequestBodySerializationMode.Streamed` + 5 MB 流 + 无重试 → 断言上传期间进程内存不出现 5 MB 级托管堆缓冲（对比修复前）。
- 用例：`ProgressableStreamContent` + 重试策略 + 首次即成功 → 断言进度回调在网络传输阶段触发（而非在发送前跑满）。
- 用例：首次失败触发重试 → 断言第二次使用的是克隆请求（原请求未被 dispose）。
- 用例（方法级路径）：`[Retry]` + Streamed 上传 + 首次成功 → 断言未被克隆缓冲（原方案会漏掉这条）。

## #7 🟠 AES-CBC 无 MAC（非认证加密）

### 问题定位

```
Mud.HttpUtils.Client/Encryption/DefaultAesEncryptionProvider.cs:122-158
  126-127:  aes.Mode = CipherMode.CBC;  aes.Padding = PaddingMode.PKCS7;   // IV 随机 ✓，无 MAC ✗
```

IV 随机已满足语义安全，但 CBC 不提供完整性，密文可被位翻转篡改，配合错误回显存在填充预言机风险。

### 修复设计（修订：未发布 → 无旧密文兼容负担，直接上认证加密为默认）

**密文格式**（带 1 字节版本前缀，为未来演进预留，**不承担兼容义务**）：

```
[1 byte version][v2: nonce(12)][tag(16)][GCM ciphertext]         net8.0/net10.0
[1 byte version][v3: IV(16)][tag(32 = HMAC-SHA256)][CBC ciphertext]   netstandard2.0/net6.0（无 AesGcm）
```

- `AesGcm` 可用性：net8/net10 有；net6 有（`System.Security.Cryptography.AesGcm` 自 net6 起存在）；
  **ns2.0 无** → v3 CBC-then-MAC。**以运行时探测为准**（`AesGcm.IsSupported`，net6+），而非写死 TFM：
  net6.0 上理论上可用 GCM，但 `Mud.HttpUtils.Client` 的 ns2.0/net6 目标不引 `System.Security.Cryptography.AesGcm` 包 →
  v3 路径覆盖 ns2.0+net6，v2 覆盖 net8+。
- 解密按首字节版本分派；长度/tag 校验失败抛 `CryptographicException`。

```csharp
public class AesEncryptionOptions
{
    public bool EnableAuthenticatedEncryption { get; set; } = true;   // 默认开启（未发布，直接定为安全默认）
    // false = 回退裸 CBC（v1 无前缀格式），仅供调试用途，文档标注不推荐
}
```

- HMAC 常量时间比较复用 `DefaultHmacSignatureProvider.cs:149-163` 的既有实现
  （抽为共享 `SecurityHelper.FixedTimeEquals` —— 注意 Abstractions 已有一个 `SecurityHelper`
  （字节清零工具，`Encryption/SecurityHelper.cs:10`），**放入 Client 包的 DefaultHmacSignatureProvider 旁
  或重命名 `CryptoHelper`，避免与现有类撞名**）。
- `MemoryEncryptedTokenStore` 解密失败已包装 `InvalidOperationException`（`:83-84`）触发重新取令牌，无需改。

### 兼容性

未发布：无旧密文存在，不需要 v1 回退路径的"配置驱动 + 回退 + LogWarning"设计（原方案整段删除）。

### 验收

- 用例：同一明文加密两次 → 断言密文不同（IV/nonce 随机）。

- 用例（net8+）：断言密文首字节为 0x02 且 GCM 路径生效。

## #8 🟠 SSRF 防护的 DNS 预检 TOCTOU + 同步阻塞

### 问题定位

```
Mud.HttpUtils.Client/Helpers/UrlValidator.cs
   15:  private static readonly ConcurrentDictionary<string, IPAddress[]> _dnsCache = new();  // 无 TTL
  154-165/210-211:  Dns.GetHostAddressesAsync(h).GetAwaiter().GetResult()                     // 同步阻塞
  102:  AllowCustomBaseUrls=true 时显式放行 localhost（IsPrivateIpAddress && !IsLoopback 才拒）
```

1. **TOCTOU**：校验时解析一次 IP，`HttpClient` 建连时再解析一次 → DNS rebinding 可绕过。
2. **同步阻塞**：`GetAwaiter().GetResult()` 在同步上下文可能死锁；`GetOrAdd` 工厂可能被并发多次调用。
3. **永久缓存**：`_dnsCache` 无 TTL。

### 修复设计

#### 8.1 M2：DNS 缓存 TTL + 工厂竞态治理（`Microsoft.Extensions.Caching.Memory` 已引用）

```csharp
private static readonly MemoryCache DnsCache = new(new MemoryCacheOptions { SizeLimit = 10_000 });

private static IPAddress[] ResolveWithCache(string host)
    => DnsCache.GetOrCreate(host, e =>
    {
        e.AbsoluteExpirationRelativeToNow = DnsCacheTtl;   // 默认 5 分钟
        e.Size = 1;
        return Dns.GetHostAddressesAsync(host).GetAwaiter().GetResult();
    })!;
```

- 同步阻塞的**彻底**消除（`ValidateUrlAsync`）涉及所有调用点改造（`EnhancedHttpClient.ValidateRequest`
  等），收益/风险比在 M2 不划算 → M2 只做 TTL + 竞态治理（`MemoryCache.GetOrCreate` 工厂有内部锁，
  同 key 并发只执行一次，优于裸 `GetOrAdd`），异步化列 Roadmap（R-8）。
- 备选：`Dns.GetHostEntryAsync` 配 `TaskCompletionSource` 做 per-key 去重的异步预热 —— 过度设计，不做。

#### 8.2 M2：连接期校验（opt-in，根治 DNS rebinding）

新增 `SsrfSafeSocketsHttpHandler`（注意 TFM 约束：`SocketsHttpHandler.ConnectCallback` 与
`DnsEndPoint` 在 **ns2.0 不可用**，net6+ 可用 → 该类型仅 net6.0+ 目标编译，ns2.0 消费方不提供此能力）：

```csharp
// Mud.HttpUtils.Client/Http/SsrfSafeSocketsHttpHandler.cs（net6.0+ only，#if 或条件编译进 csproj）
public sealed class SsrfSafeSocketsHttpHandler : SocketsHttpHandler
{
    public SsrfSafeSocketsHttpHandler(IIpAddressPolicy policy)
    {
        ConnectCallback = async (context, ct) =>
        {
            var ip = context.DnsEndPoint.Address;     // ← 实际建连的 IP，不受 DNS rebinding 影响
            if (!policy.IsAllowed(ip) && !IPAddress.IsLoopback(ip))
                throw new InvalidOperationException($"不允许连接到目标地址: {ip}");
            var socket = new Socket(SocketType.Stream, ProtocolType.Tcp) { NoDelay = true };
            try { await socket.ConnectAsync(context.DnsEndPoint, ct).ConfigureAwait(false); return socket; }
            catch { socket.Dispose(); throw; }
        };
    }
}
```

- `IPNetwork`（`UrlValidator.cs:281`，internal）提升可见性为共享（仍在 Client 内 internal 即可，
  Resilience 不需要它），实现 `IIpAddressPolicy`（新增于 **Client** 包，ns2.0 可编译——接口本身无 TFM 依赖，
  只是默认实现类放 Client）。
- 注册扩展：`HttpClientServiceCollectionExtensions`（`Mud.HttpUtils.Client/ServiceCollectionExtensions.cs:26`）
  新增 `AddMudHttpClientSsrfProtection()`。
- 注意 `context.DnsEndPoint.Address` 在连接前可能是 `IPAddress.None`（hostname 尚未解析，.NET 8 的
  `ConnectCallback` 语义）——实施时以**实际解析回调签名**为准：若 `DnsEndPoint.Address` 未填，
  需在回调内自行 `Dns.GetHostAddressesAsync` 再校验后连接。实施时写一个集成用例（127.0.0.1 / 169.254.169.254）
  实测行为再定稿。

#### 8.3 文档

README 增加"SSRF 防护"章节，明确：

- 默认 `AllowCustomBaseUrls = false` 时强制 HTTPS + 白名单（fail-closed）；
- `AllowCustomBaseUrls = true` 时显式放行 localhost（`UrlValidator.cs:102`），URL 来自用户输入必须自行校验；
