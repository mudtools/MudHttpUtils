## 一、总体策略

1. **兼容性红线**（全程约束）：
   - 公共 API 增删必须同步 `PublicAPI.{Unshipped,Shipped}.txt`（RS0016/RS0017），按 TFM 分目录维护；

   - 多目标 `netstandard2.0;net6.0;net8.0;net10.0` 全通过；AOT 严格模式（`-p:AotStrictMode=true`）无 IL20xx/IL3xxx 新告警；

2. **工程纪律**（沿用项目惯例）：热路径字符串用 `ValueStringBuilder`；候选过滤延迟枚举；DEBUG 构建对生成代码跑 `CSharpSyntaxTree.ParseText` 校验；新增生成器行为配 `HttpClientGeneratorConstants` 常量 + 诊断 ID 治理；EmitCompilerGeneratedFiles 验证输出到 `obj\GeneratedOut`。
3. **阶段切分**：Phase 0（缺陷修复，可立即实施）→ Phase 1（P0 功能）→ Phase 2（P1）→ Phase 3（P2）。每阶段独立可发布、独立全量回归。
4. **实施门槛**（评审后明确）：Phase 0（B-1/B-2/B-3）+ Phase 1（F-1/F-2，均为 P0 功能）按用户偏好直接实施；Phase 2 起（P1/P2）须用户确认后排期。

## 三、Phase 0 — 缺陷修复（立即实施）

### B-1 令牌管理器键注册期冲突诊断

- **现状**：共享 `ITokenManagerRegistry` 下多产品线令牌键（如 `Wechat.Channels.AccessToken` 与公众号令牌）冲突时，`DelegateTokenManagerRegistry.Resolve` 只是透传委托（[DelegateTokenManagerRegistry.cs](../Mud.HttpUtils.Client/TokenManager/DelegateTokenManagerRegistry.cs)），冲突表现为运行期 `Resolve` 返回 `null` → errcode 令牌自愈**静默失效**（下游注释实证）。
- **方案**：
  1. 新增内部 `TokenManagerKeyRegistry`（Client）：注册期记录 `key → MetricsKey/管理器类型`，重复键（序数比较）即诊断；
  2. `AddMudHttpTokenManager` / `AddAppScopedTokenManagerRegistry` / `AddTokenManagerRegistry` 帮助器接入该登记簿；
  3. 诊断出口走既有 `AppManagementStartupValidator`（启动期校验）+ `AppManagerDiagnostics` 委托（Abstractions 无日志依赖），新增 EventId（沿用 19x 段）；重复键默认 **Error 级启动失败**，提供 `MudHttpOptions.AllowDuplicateTokenManagerKeys` 逃生开关（默认 false）。
- **涉及**：`Mud.HttpUtils.Client/TokenManager/`（新增登记簿）、`ServiceCollectionExtensions.cs`、`AppManagementStartupValidator.cs`、`AppManagerDiagnostics.cs`。
- **测试**：重复键注册 → 启动校验抛出/记 Error；逃生开关下降级为 Warning；大小写不同视为不同键（与 AppKey 序数语义一致）。
- **评审修订（2026-10-13，架构师 + 高级程序员）**：
  1. **现状再核实**：核心 `ITokenManagerRegistry` 是**委托式**（[DelegateTokenManagerRegistry.cs#L31-L32](../Mud.HttpUtils.Client/TokenManager/DelegateTokenManagerRegistry.cs) 透传 `Func<string, ITokenManager?>`），键在委托内部（per-app 动态解析），核心侧**不存在**可枚举的 `key → manager` 静态映射 ⇒ "内部登记簿挂在既有帮助器上"不可行（`AddAppScopedTokenManagerRegistry` 委托运行期才见键）。实际静默冲突面有三处：
     - a) `AddTokenManagerRegistry`/`AddAppScopedTokenManagerRegistry` 均 `TryAddSingleton`（[ServiceCollectionExtensions.cs#L1638](../Mud.HttpUtils.Client/ServiceCollectionExtensions.cs)）——**后注册者被静默丢弃**，无诊断（对比 `RegisterSwitcherFactory` 已有 MT-08 覆盖告警）；
     - b) `AddMudHttpTokenManager<T>` 用 `services.Add`（非 TryAdd）——同类型重复注册**静默叠加**；
     - c) 下游私有注册表的键冲突（`ChannelsTokenTypes` 实证）发生在下游字典里，核心无官方字典式注册表可替换。
  2. **修订实施面**（三层，覆盖 a/b/c）：
     - 诊断 A：`AddTokenManagerRegistry`/`AddAppScopedTokenManagerRegistry` 检测到 `ITokenManagerRegistry` 已注册 → 警告"后注册被忽略"（新 EventId 194，19x 段沿用）；
     - 诊断 B：`AddMudHttpTokenManager<T>` 同类型重复注册 → 警告（新 EventId 195）；
     - 诊断 C：新增**公开** `TokenManagerKeyRegistry`（Client，字典式 `ITokenManagerRegistry` 实现，`Register(key, manager)` 序数比较，重复键即诊断/抛出），作为下游私有注册表的官方替代——键在宿主侧，**internal 化则核心根本看不到键**，故由方案原定的"internal 登记簿"改为公开注册表实现。
  3. **逃生开关落点修正**：`MudHttpOptions` 类**不存在**——挂到既有 `MudHttpAppManagementOptions`（[MudHttpAppManagementOptions.cs](../Mud.HttpUtils.Client/Configuration/MudHttpAppManagementOptions.cs)，已被 `AppManagementStartupValidator` 消费），新增 `AllowDuplicateTokenManagerKeys`（默认 false）。注册期检测、启动期升级：默认 Error 抛出，逃生开关下 Warning + 后键覆盖。

### B-2 `ITokenStore` 自动桥接（消除暗门）

- **现状**：注册 `ITokenStore` 不会自动获得持久化能力，必须手动经 `TokenStoreBackedTokenCache<T>` 桥接；库靠启动校验 EventId 191 提示（[ITokenStore.cs#L15-L23](../Mud.HttpUtils.Abstractions/TokenManager/ITokenStore.cs)）。
- **方案**：
  1. `AddMudHttpTokenManager` 装配链改为：`ITokenCache` 显式注册 **优先**；未注册 `ITokenCache` 但注册了 `ITokenStore` → **自动**以 `TokenStoreBackedTokenCache` 包装；
  2. EventId 191 语义改为"检测到 ITokenStore 但因显式 ITokenCache 存在而未桥接"（信息级），保留原行为的显式覆盖路径；
  3. `ITokenStore` 文档注释同步改写（删除"不会自动获得持久化能力"的旧契约描述）。
- **涉及**：`ServiceCollectionExtensions.cs`（`AddMudHttpTokenManager`/`AddMudHttpTokenManager<T>`）、`TokenStoreBackedTokenCache.cs`（如有装配缺口）、`ITokenStore.cs` 注释、`AppManagementStartupValidator.cs`。
- **兼容性**：此前"手动桥接"的下游（`Mud.Wechat.Redis` 路径）不受影响——显式 `ITokenCache` 注册优先，行为不变。
- **测试**：三种注册组合（只 Store / 只 Cache / 两者）× 桥接结果断言；既有 `TokenStoreBackedTokenCache` 测试全绿。
- **评审修订（2026-10-13，架构师）**：
  1. **装配落点修正**：`AddMudHttpTokenManager<T>` 只注册管理器本身（[ServiceCollectionExtensions.cs#L1528-L1570](../Mud.HttpUtils.Client/ServiceCollectionExtensions.cs)），缓存经构造注入 `ITokenCache<CredentialToken>`（[TokenManagerBase.cs#L167](../Mud.HttpUtils.Abstractions/TokenManager/TokenManagerBase.cs)）⇒ "装配链内部包装"不存在可改的链。正确落点是 **DI 回退注册**：在 `AddMudHttpTokenManager<T>` 与 `AddMudHttpClientInfrastructure` 中 `TryAddSingleton<ITokenCache<CredentialToken>>(sp => …)`（及用户维度 `ITokenCache<UserTokenInfo>`）——运行期解析时若显式 `ITokenCache` 未注册（TryAdd 天然保证显式优先、与顺序无关）而 `ITokenStore`/`IEncryptedTokenStore`/`IUserTokenStore` 已注册，则用既有便捷工厂 `TokenStoreBackedTokenCache<T>.CreateForCredentialToken` / `CreateForUserTokenInfo`（[TokenStoreBackedTokenCache.cs#L198/L229](../Mud.HttpUtils.Client/TokenManager/TokenStoreBackedTokenCache.cs)）自动桥接；两者皆无则维持现状（管理器内建内存缓存）。
  2. **帮助器名勘误**：方案原文"`AddMudHttpTokenManager` / `AddMudHttpTokenManager<T>`"两个帮助器实际只有泛型一个（L1528）。
  3. **EventId 191 新语义**：自动桥接后，"注册了 ITokenStore 但未桥接"只剩一种情形——宿主**显式**注册了 `ITokenCache`（覆盖优先）且同时注册了 store；此时 store 由宿主自理，降为**信息级**提示（原 Warning 文案"RegistrationIgnored"同步改写），并保留手动桥接路径文档。
- **实施修正（2026-10-13，落地时与修订 #1 的偏离）**：
  1. **生命周期改为 Transient（非修订 #1 的 `TryAddSingleton`）**：`ITokenCache<T>` 的缓存键是作用域键（`ScopeKeyBuilder` 产出，**不含管理器身份**）——Singleton 共享实例会让多个令牌管理器共写同一键（如 `"default"`），造成**跨管理器令牌串扰（安全问题）**；且与"两者皆无则维持现状（各自内建内存缓存）"的语义矛盾。Transient 使每个管理器实例持各自缓存，与内建缓存隔离语义一致；代价（经容器解析的桥接实例不与管理器共享镜像）由 `TokenManagerBase` 既有 IAsyncTokenCache 读穿透（S2）覆盖，冷启动水合非必需。已写入 `TryAddTokenCacheStoreFallback` 的 remarks。
  2. **EventId 191 文案覆盖两情形**：除修订 #3 的"显式 `ITokenCache` 覆盖"外，还存在"注册了 store 但未注册任何令牌管理器消费方（回退注册未触发）"的情形；191 文案统一为"未接入自动桥接——显式覆盖或尚未注册消费方，store 由宿主自理"（信息级），既有 `AppManagementRegistrationTests` 的 191 用例断言由 Warning 同步改 Information。
  3. **测试落地**：`TokenCacheStoreAutoBridgeTests`（三组合矩阵 + C7 维度分流 + Transient 隔离 + 构造注入消费路径）、`TokenManagerKeyRegistryTests`（含 B-1 诊断 A/B 与重复键升级口径）。

## 四、Phase 1 — P0 功能

### F-1 `[Token]` 方法级免令牌 opt-out（G-1）

- **现状**：`TokenAttribute`（[TokenAttribute.cs](../Mud.HttpUtils.Attributes/Interface/TokenAttribute.cs)）只有"怎么注入"没有"不注入"；接口级 `[Token]` 会被所有方法继承，方法级只能覆盖参数不能取消。下游被迫把免令牌应急端点（`clear_quota/v2`）拆成独立接口。
- **设计**：
  1. **主选**：`TokenAttribute` 新增 `bool Disabled { get; set; }`（默认 false）。语义：**显式阻断接口级 `[Token]` 继承**，方法不取令牌、不注入、不参与令牌恢复。方法级 `[Token(Disabled = true)]` 与其他注入参数（`InjectionMode`/`Name`/`Scopes` 等）同用 → 新诊断 **警告**（参数被忽略）。
  2. **备选**：独立 `[Anonymous]`/`[NoToken]` 特性。表达更醒目但多一个公共 API；若评审倾向"一个入口一种语义"可切换，实现点一致。
  3. 生成器改动点：
     - `MethodAnalyzer.AnalyzeMethodTokenExtended`（[MethodAnalyzer.cs#L1314](../Mud.HttpUtils.Generator/Analyzers/MethodAnalyzer.cs)）提取 `Disabled`，方法级优先于接口级（沿用 MT-21"方法级覆盖接口级"语义）；
     - `MethodGenerator.ShouldInjectToken`（[MethodGenerator.cs#L1328](../Mud.HttpUtils.Generator/HttpInvoke/Implementation/MethodGenerator.cs)）短路：`Disabled == true` → 不生成 `GetTokenAsync` 调用与注入代码；
     - `TokenManagerLifetimeAnalyzer` / MUD005（URL 承载令牌）对 Disabled 方法豁免；
     - 令牌恢复（`TokenRecoveryContext`）不为 Disabled 方法建恢复上下文。
  4. `TokenAttribute` 主构造兼容：`Disabled = true` 时忽略 `tokenType`/`TokenManagerKey` 语义（不写入生成代码）。
- **涉及**：`Mud.HttpUtils.Attributes/Interface/TokenAttribute.cs`（+ `PublicAPI.*.txt`，Attributes 仍零运行时行为）、Generator `MethodAnalyzer`/`MethodGenerator`/`TokenMethodHelper`/`TokenManagerLifetimeAnalyzer`/`Diagnostics.cs`。
- **测试**：生成器 golden 测试（Disabled 方法无 `GetTokenAsync` 调用）、接口级继承阻断、与 `Justification`/MUD005 交互、DEBUG 生成代码语法校验通过；下游场景复刻测试：同一接口内"常规端点取令牌 + 逃生端点 Disabled"。
- **验收**：`IChannelsBasicTokenFreeService` 式拆接口 workaround 可合并回单接口。
- **评审修订（2026-10-13，架构师 + QA）**：
  1. **主选裁决**：采用主选 `Disabled`（单入口一种语义；Attributes 纯元数据零运行时，[TokenAttribute.cs](../Mud.HttpUtils.Attributes/Interface/TokenAttribute.cs) 的 `AttributeUsage` 含 `Parameter`——`Disabled` 在**参数级无意义**，参数级 `[Token(Disabled=true)]` 出诊断警告并忽略）。
  2. **模型指纹红线**（项目历史教训）：新增 `Disabled` 必须进入生成器 token 模型的 fingerprint（`WithoutTrivia()` 风格），否则宿主改属性不触发重新生成——实施时逐一核对 `MethodAnalyzer` token 模型指纹构造处。
  3. **验收用例落地口径**：下游复刻测试以"同一接口：常规方法断言生成 `GetTokenAsync` 调用 + 逃生方法断言**零**令牌代码"双向断言为准（防只测豁免不测未豁免的假阳性）。
- **实施修正（2026-10-13，落地记录）**：
  1. **三态回退而非两态**：`Disabled` 解析为「方法级 `bool?` ?? 接口级 `bool?` ?? false」（`MethodAnalysisResult` 记 `MethodTokenDisabled`/`InterfaceTokenDisabled`/`EffectiveTokenDisabled`），使方法级 `[Token(Disabled = false)]` 可对已标 `[Token(Disabled = true)]` 的接口内**单方法重新启用**令牌——与"方法级覆盖接口级"（MT-21）语义完全一致；修订 #1 的"方法级显式设置优先"按此实现。
  2. **诊断取号**：新诊断定号 **HTTPCLIENT039**（`Disabled = true` 与注入参数同用 → 参数被忽略，警告）、**HTTPCLIENT040**（参数级 `[Token(Disabled = …)]` 忽略并告警），登记 `Diagnostics.cs` + `AnalyzerReleases.Unshipped.md` + Generator README 诊断表，与既有 HTTPCLIENT0xx 序列衔接。
  3. **RequestBuilder 短路补强**（超出修订清单的必要补强）：`ShouldGenerateTokenQuery` 对 `EffectiveTokenDisabled` 短路之外，**Query/Path 注入模式的 Disabled 方法必须同时跳过占位符替换**——否则生成代码引用未声明的 token 变量直接 CS0103，"零令牌代码"验收无法成立。`MethodGenerator.ShouldInjectToken`/`ShouldGenerateTokenRecoveryContext` 与 `RequestBuilder` 三处短路共同构成完整 opt-out。
  4. **指纹核对结论**（修订 #2 红线）：`InterfaceModel` 源文本指纹用 `WithoutTrivia()`，`Disabled` 作为特性命名参数天然进入源文本 ⇒ 无需额外改动即满足"改属性触发重新生成"；已补 2 个 `InterfaceModelFingerprintTests` 指纹用例钉死。
  5. **参数级 040 语义**："忽略"= 忽略 `Disabled` **标志**本身（参数仍按普通令牌参数注入），非忽略整个 `[Token]`；避免误读为参数级令牌整体失效。
  6. **主构造默认值误报修复**：`TokenAttribute(string tokenType = TokenTypes.AccessToken)` 的默认值被 Roslyn 填入 `ConstructorArguments`，致 `[Token(Disabled = true)]` 误报 039"TokenType 被忽略"——`HasExplicitPositionalConstructorArgument` 改**语法判定**（`AttributeSyntax.ArgumentList` 中无 `NameEquals` 的实参才算显式位置参数）。该缺陷在落地中发现并修复，回归测试覆盖。

### F-2 令牌归属模型一等化（G-2 / TK-1）

- **现状**：微信三类归属（per-corp 一企一份 / 全局共享 / 链式）只能拼装：scopes 当路由键（`GetTokenAsync(new[]{ authCorpId })`）、`ISharedTokenManager` 标记、下游自拼 `{tokenType}:{appKey}:{scopeKey}` 三段式；`CompositeKey` 为 internal（[CompositeKey.cs](../Mud.HttpUtils.Abstractions/TokenManager/CompositeKey.cs)），键构建契约未公开。
- **设计**（分两步，控制爆炸半径）：
  1. **公开键契约**：Abstractions 新增 `public readonly struct TokenScopeKey`：
     - `TokenScopeKey.ForApp(string tokenType, string appKey)` / `ForScope(string tokenType, string appKey, string scopeKey)` / `ForShared(string tokenType)` 三个命名工厂，编码委托 `CompositeKey`（长度前缀单射，保持内部实现）；
     - `TokenManagerBase` 新增 `GetOrRefreshTokenAsync(TokenScopeKey, ...)`/`InvalidateTokenAsync(TokenScopeKey, ...)` 重载（新重载，不改既有 `string[] scopes` 签名）；
     - 语义映射：`ForScope` 的 `scopeKey` 即下游 `authCorpId` 场景的路由键，文档明确"scopeKey 是归属键而非 OAuth scope"。
  2. **归属语义文档化 + 显式化**：把既有 `EnforceTenantBinding`/`ISharedTokenManager`（WX-02）整理为归属模型一等概念：
     - Abstractions 新增 `enum TokenBindingMode { PerApp, PerScope, Shared }`；
     - `TokenManagerBase` 新增 `protected virtual TokenBindingMode BindingMode => ...`（默认由 `ISharedTokenManager`/`EnforceTenantBinding` 推导，保持既有行为逐位一致）；
     - `BindTenantGuard` 按 `BindingMode` 分档（`Shared` 跳过、`PerScope` 以 appKey+scopeKey 绑定）。
  3. 下游三段式迁移路径写入 F-6 对账清单（`{tokenType}:{appKey}:{scopeKey}` → `TokenScopeKey.ForScope(...)`）。
- **涉及**：`Mud.HttpUtils.Abstractions/TokenManager/`（`TokenScopeKey` 新增、`TokenManagerBase` 重载、`TokenBindingMode`）、`PublicAPI.*.txt`、README。
- **兼容性**：全部为新增面；`string[] scopes` 旧路径语义不变（`ScopeKeyBuilder` 规则不动）。
- **测试**：`TokenScopeKey` 单射性测试（复用 CompositeKey 断言风格）；`BindingMode` 三档 × `BindTenantGuard` 矩阵；与 `ScopeKeyBuilder` 键互通性（同一归属键 ⇒ 同一缓存条目）。
- **验收**：下游"一企一份"可一行声明归属；`ISharedTokenManager` 语义收敛为 `BindingMode.Shared` 的标记等价物。
- **评审修订（2026-10-13，架构师 —— 关键设计张力裁决）**：
  1. **内在矛盾**：原设计"编码委托 `CompositeKey` 三段式（tokenType+appKey+scopeKey）"与验收"与 `ScopeKeyBuilder` 键互通（同一归属键 ⇒ 同一缓存条目）"**不可同时成立**——`TokenManagerBase` 的缓存键只由 scopes 段经 `ScopeKeyBuilder.Build` 生成（[TokenManagerBase.cs#L385-L388](../Mud.HttpUtils.Abstractions/TokenManager/TokenManagerBase.cs)），tokenType/appKey 由管理器实例天然承载（每管理器一个 tokenType、per-app 实例隔离），三段式全键进缓存 ⇒ 必然双缓存。
  2. **裁决：`TokenScopeKey` 双形态**：
     - **定位符形态**（驱动缓存互通）：`GetOrRefreshTokenAsync(TokenScopeKey, …)`/`InvalidateTokenAsync(TokenScopeKey, …)` 新重载按段映射到既有路径——`ForScope(t,a,s)` → `scopes = [s]`、`ForApp(t,a)`/`ForShared(t)` → `scopes = null`（"default"）；`tokenType`/`appKey` 段仅作**一致性校验**（与当前管理器 tokenType / 上下文 AppKey 不符 → 诊断/参数异常，绝不参与缓存键），保证与 `ScopeKeyBuilder` 旧路径**单缓存互通**；
     - **编码键形态**（替换下游自拼键）：`ToCompositeKey()`/`ToString()` 输出 `CompositeKey` 长度前缀三段式（编码委托保持 internal 不变），仅供下游当字典/分布式键用，**不进** `TokenManagerBase` 缓存键。
  3. **`TokenBindingMode` 单一真源**：与既有 `EnforceTenantBinding`/`ISharedTokenManager` 收敛为一处语义——`BindingMode` 默认推导 = `ISharedTokenManager` ⇒ `Shared`；`!EnforceTenantBinding` ⇒ `Shared`；否则 `PerApp`（绑定粒度与现行 `BindTenantGuard` 逐位一致，`PerScope` 为新增档位显式覆写才启用）。旧入口保留为推导来源，禁止双向覆写造成分歧（矩阵测试钉死）。
- **实施修正（2026-10-13，落地记录）**：
  1. **默认推导顺序裁决（修订 #3 的落地偏离）**：修订 #3 字面"ISharedTokenManager ⇒ Shared 优先"与钉死测试 `SharedTokenManagerMarkerTests.Marker_ExplicitOverride_ShouldStillTakePrecedence`（既有语义钉死测试不得改动断言）冲突——后者钉死"派生类显式覆写 `EnforceTenantBinding` 优先于 `ISharedTokenManager` 标记"。裁决落地为 **`BindingMode => EnforceTenantBinding ? PerApp : Shared`**：`ISharedTokenManager` 经 `EnforceTenantBinding` 默认表达式（`this is not ISharedTokenManager`）传导为 `Shared`，显式覆写 `EnforceTenantBinding` 时以其为准；显式覆写 `BindingMode` 则优先于一切推导。与既有行为逐位一致，矩阵测试钉死。
  2. **校验基准**：`TokenScopeKey` 定位符形态的 `appKey` 段校验基准 = `BoundTenant`（已绑定租户对不符 → 参数异常；**未绑定时跳过**，因绑定发生在首次取令牌时）；`tokenType` 段校验基准 = `protected virtual TokenType`（可覆写点，供多令牌类型管理器自述）。
  3. **`PerScope` 档位实现口径**：`_tenantBinding` 由 `(AppKey, ScopeKey)` 双槽重构为 `TenantBindingRecord{AppKey, ScopeKey}` 单字段 CAS（lock-free，`Interlocked.CompareExchange` 语义）——`PerScope` 为**单槽 bind-once 归属对**（appKey+scopeKey 首绑后钉死，后续不符即拒），非每 scope 一槽的多归属表；多归属需求留给 F-7 链式依赖图，避免本档位膨胀。
  4. **测试落地**：`TokenScopeKeyTests`（工厂/单射性/编码键形态/定位符映射）、`TokenBindingModeTests`（三档 × `BindTenantGuard` 矩阵 + 显式覆写优先钉死）、`TokenScopeKeyLocatorTests`（校验基准 + 与 `ScopeKeyBuilder` 单缓存互通），三 TFM 全绿。

## 九、多维方案评审记录（2026-10-13，已并入正文）

> 评审方式：三视角并行核查 + 逐条对照源码实证；结论以"评审修订"块并入上文对应条目，本章为汇总裁决。

### 9.1 高级程序员视角（问题真实性 / 必要性 / 冗余排查 / 最优性）

| 条目 | 问题真实性 | 裁决 |
| --- | --- | --- |
| B-1 | **属实**，但键面定位偏了 | 核心注册表是委托式、键不可枚举；真实静默冲突面是"注册表 TryAdd 丢弃后注册者 / AddMudHttpTokenManager 重复叠加 / 下游私有字典键冲突"三层 ⇒ 按修订版三层诊断实施；`MudHttpOptions` 不存在，逃生开关落 `MudHttpAppManagementOptions` |
| B-2 | **属实**（EventId 191 证据链完整） | 装配落点改为 DI 回退注册（显式 `ITokenCache` 优先、`CreateForCredentialToken` 便捷工厂已备），比原"装配链内部包装"更贴合现状且成本更低 |
| B-3 | **属实**（SW-05 自证） | Obsolete 保守路线成立，但消息须按"生成器场景 vs AOT 低层接缝"分层（SW-05 现行文档把工厂定位为 AOT 接缝，不能一概判死）；BC 编号取 BC-30 |
| F-1 | **属实**（下游拆接口实证） | 主选 `Disabled`（备选 `[NoToken]` 落选：一个入口一种语义）；补模型指纹红线与双向断言口径 |
| F-2 | **属实**（scopes 语义泛化 + 自拼键实证） | 存在**内在设计张力**（三段式编码键 vs ScopeKeyBuilder 互通），裁决为"定位符 + 编码键"双形态（见 F-2 修订）；`TokenBindingMode` 收敛为单一真源，`EnforceTenantBinding`/`ISharedTokenManager` 保留为推导来源 |

**冗余排查**：
- F-2 `TokenBindingMode` vs `EnforceTenantBinding` vs `ISharedTokenManager` 三套语义 → 收敛规则已钉（单一真源 + 推导，矩阵测试防分歧）；
- F-3 官方 Redis 与下游 `Mud.Wechat.Redis` 能力重复 → 留待 Phase 2 确认时经 F-6 对账裁决（吸收 / 分层共存），不在 Phase 0/1 处理；
- F-1 备选 `[Anonymous]/[NoToken]` 与 `Disabled` 重复 → 二选一，落选方案不再保留设计（避免半实现状态）；
- B-1 原"内部登记簿 + MetricsKey"与既有 `AppManagerDiagnostics`/`AppManagementStartupValidator` 职责重叠 → 修订版明确：登记与冲突检测在 `TokenManagerKeyRegistry`，升级/出口复用既有校验器与诊断委托，不新建诊断通道。

**最优性评估**：Phase 0/1 全部为"新增面 + 诊断面 + Obsolete 警告面"，无接口签名变更、无行为语义变更（除 B-2 装配默认值——被"显式优先"护栏保护），是当前能力下破坏半径最小的路线；未采纳的激进路线（删除死 API、`[NoToken]` 新特性、三段式全键进缓存）已记录否决理由。

### 9.2 系统架构师视角（逻辑闭环 / 架构合理性 / 兼容性）

- **声明→生成→注册→解析→注入链路闭环核验**：F-1 五个改动点（`AnalyzeMethodTokenExtended` 提取 → `ShouldInjectToken` 短路 → `TokenManagerLifetimeAnalyzer`/MUD005 豁免 → `TokenRecoveryContext` 不建恢复 → 模型指纹）覆盖了链路的全部令牌触点，闭环成立；`GeneratorContext` 特征传播（`HasApiKeyInjection` 等）需同步核对 Disabled 方法不触发注入特征。
- **F-2 关键张力已裁决**（双形态），实施红线：`GetOrRefreshTokenAsync(TokenScopeKey)` 与 `GetOrRefreshTokenAsync(string[])` 必须命中**同一缓存条目**，由互通性测试钉死。
- **兼容性红线核验**：B-3 Obsolete 仅编译告警（钉 3.0.6 下游零影响）；B-2 "显式 `ITokenCache` 优先"保住 `Mud.Wechat.Redis` 手动桥接路径；F-1 仅对新增属性生效（无属性生成代码逐字节不变，golden 全量对照）；F-2 全新增面 + PublicAPI 按 TFM 分目录同步；`Mud.HttpUtils.Attributes` 保持纯元数据（`Disabled` 是纯属性）。
- **AOT 核验**：B-2 自动桥接走既有便捷工厂（显式委托、零反射）；F-1/F-2 无反射面，`-p:AotStrictMode=true` 无新增 IL20xx/IL3xxx 预期。
