## 0. 摘要（Executive Summary）

占位实现落地后，"生成器无法处理某成员"不再表现为难以定位的 `CS0535`，而是"占位成员 + 一条说明原因的诊断"。但本次落地过程中暴露出一类**跨诊断的系统性风险**，并有 3 项遗留能力/一致性问题待处理：

1. **分析器诊断可被生成器诊断"连坐"抑制**（P0）：实测「生成器报出 `Error` 且带 `NotConfigurable` 标签的诊断」时，**同一编译中的全部分析器诊断（`MUD001`/`MUD002`/`MUD004`）不再呈现**。当前 Generator 有 **15 个 `Error + NotConfigurable`** 诊断，命中任意一条即触发。这意味着"接口规范检查"在最需要它的编译（有生成错误的编译）中恰好完全静默。
2. **`Task<Stream>` 是可编译但运行期必然失败的"伪支持"**（P0）：`MUD002` 与 README 都把 `Stream` 列为受支持，生成器实际走 `ExecuteAsync<Stream>`（把响应体 JSON 反序列化进 `Stream`）。属"分析器沉默 + 生成语义错误的代码"，与本次修复的 `CS4032` 同族。
3. **三方一致性缺少可执行守卫**（P1）："生成器门禁 / `MUD002` / README 诊断表"三者目前靠人工同步（`DocumentationContractTests` 只覆盖 README ↔ `Diagnostics.cs` 的 ID 与级别），无"能力口径"守卫。
4. **诊断元数据与死路径清洁度**（P2）：37 条 `RS2008`（缺 `AnalyzerReleases` 发布跟踪，每个描述符一条）、`IsVoidType` 分支对字面 `void` 已不可达、`TypeDetectionHelper.IsAsyncEnumerableType` 生产路径已无调用、占位异常消息缺少诊断 ID 便于线上定位。

| 成员标注 `[IgnoreGenerator]`，或使用方已在 partial 实现类手写 | 不发射 | 无（由使用方负责） |

### 1.2 问题 I1：分析器诊断被"连坐"抑制（P0）

**规律（实测）**：生成器报出 **`Error` 且带 `WellKnownDiagnosticTags.NotConfigurable`** 的诊断时，本次编译的**分析器**诊断整体不再呈现。

| 实验 | 变量 | 结果 |
|---|---|---|
| A | `HTTPCLIENT004`(Error + `NotConfigurable`) + 缺 HTTP 特性方法 | **`MUD001` 不呈现** |
| B | 同上，但把 `HTTPCLIENT004` 降为 `Warning` | `MUD001` 呈现 |
| C | 同上，保留 Error 但**移除** `NotConfigurable` | `MUD001` 呈现 |
| D | 改用未改动的 `HTTPCLIENT005`(Error + `NotConfigurable`) | **`MUD001` 不呈现** |

> **重要**：本规律与"编译错误（如 `CS0029`）会抑制分析器诊断"**无关** —— 对照实验中无关编译错误存在时 `MUD001` 正常呈现。决定因素是标签与级别的组合。

**机制结论（2026-09-14，已定位到 Roslyn 源码；阶段一任务 1.1 交付物）**：

机制在 **csc（`Microsoft.CodeAnalysis.CommonCompiler`）** 层，而非 MSBuild 层，与 `NotConfigurable` 的"不可配置"语义无关。

1. 判定函数（`src/Compilers/Core/Portable/Diagnostic/Diagnostic.cs`）：

   ```csharp
   /// Only diagnostics which have default severity error and are tagged as NotConfigurable fall in this bucket.
   /// This includes all compiler error diagnostics and specific analyzer error diagnostics that are marked as
   /// not configurable by the analyzer author.
   internal bool IsUnsuppressableError() => DefaultSeverity == DiagnosticSeverity.Error && IsNotConfigurable();

   /// Returns true if a diagnostic is not configurable, i.e. cannot be suppressed or filtered or have its severity changed.
   internal virtual bool IsNotConfigurable() => AnalyzerManager.HasNotConfigurableTag(this.CustomTags);
   ```

   注意用的是 **`DefaultSeverity`**（不是有效级别）：这解释了实验 B —— 把 HTTPCLIENT004 的**默认级别**降为 Warning 后 `IsUnsuppressableError()` 为 false，闸门放行。

2. 闸门（`src/Compilers/Core/Portable/CommandLine/CommonCompiler.cs`，`CompileAndEmit`）：

   ```
   ① compilation.GetDiagnostics(CompilationStage.Parse, ...)  → diagnostics
   ② if (HasUnsuppressableErrors(diagnostics)) { ...; return; }      // Parse 闸门（生成器尚未运行）
   ③ RunGenerators(compilation, ..., diagnostics)                   // 生成器运行；其诊断并入同一 DiagnosticBag
   ④ initializeAnalyzerDriver(...)                                  // 仅创建驱动，尚未求值
   ⑤ compilation.GetDiagnostics(CompilationStage.Declare, ...)      // 声明阶段诊断（含生成产物）
   ⑥ if (HasUnsuppressableErrors(diagnostics)) { ...; return; }      // Declare 闸门 ← 关键
   ⑦ ... analyzerDriver.GetDiagnosticsAsync(...)                    // 分析器诊断在此才被取出
   ```

   第 ⑥ 步提前 `return`，第 ⑦ 步永不执行 ⇒ **本轮编译的分析器诊断整体不产生**。而第 ③ 步已把生成器诊断并入同一个 `diagnostics` bag ⇒ 生成器的「Error + NotConfigurable」诊断正是触发条件。`HasUnsuppressableErrors` 即对 bag 逐条调用 `IsUnsuppressableError()`。

3. 与"无关编译错误"对照实验并不矛盾：闸门只检查 **Parse / Declare 两个阶段**的诊断。方法体内的绑定错误（如 `CS0029`）属 **Compile** 阶段，在第 ⑥ 步之后才产生，不影响闸门；而 `CS0535`（缺少接口成员）属**声明**阶段错误，同样会触发闸门 —— 这正是"早期实现跳过成员产生 `CS0535`，从而掩盖 `MUD001`"的成因，也印证了占位实现（消除 `CS0535`）+ `HTTPCLIENT024`（必报且无标签）的必要性。

4. 结论：**§3.2 方案 C（标签分层）成立**，且"`Error + NotConfigurable` ⇒ 跳过分析器"的确切路径为
   `CommonCompiler.CompileAndEmit` 的 Declare 闸门 → `HasUnsuppressableErrors` → `Diagnostic.IsUnsuppressableError`。
   另外两个推论：①降级为 Warning 同样能解除连坐（但会把编译期失败变成运行期故障，不采用）；
   ②任何"用户可修复"的生成器诊断都不应带该标签。

**端到端实测（修复前/修复后对照，见 `Tests/AnalyzerOnlyProbe`）**：
- 修复前：`HTTPCLIENT004`（Error + NotConfigurable）+ 缺 HTTP 特性方法 → **`MUD001` 不呈现**；
- 修复后（去标签）：同一工程、同一诊断组合 → **`HTTPCLIENT004` 与 `MUD001` 同时呈现**（构建仍因两条 Error 失败）。
该对照已固化为 CI 步骤「连坐抑制回归验证（生成器开启）」。

### 1.3 问题 I2：`Task<Stream>` 是"可编译但运行期必然失败"的伪支持（P0）

- 生成结果（实测）：`public async Task<global::System.IO.Stream> StreamAsync()` →
  `return await _executor.ExecuteAsync<System.IO.Stream>(...)`。编译通过（有 `await` + `async`），但 `ExecuteAsync<T>` 会尝试把响应体 **JSON 反序列化**为 `Stream` → 运行期失败。
- 而 `MUD002` 与 README 均把 `Stream` 列为受支持（白名单口径），生成器门禁也放行 → **无任何编译期提示**。
- 运行期**已有**正确的直达 API：`IBaseHttpClient.SendStreamAsync(HttpRequestMessage, CancellationToken) → Task<Stream>`（[IBaseHttpClient.cs:39](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Abstractions/HttpClient/Clients/IBaseHttpClient.cs#L39)），`AsyncEnumerableExtensions` 已在用它（[AsyncEnumerableExtensions.cs:42](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Client/HttpClient/AsyncEnumerableExtensions.cs#L42)）。
- 与 `HttpResponseMessage` 的"直达返回（架构红线例外）"完全同构，实现路径明确（§4）。

### 1.4 问题 I3：三方一致性缺少可执行守卫（P1）

当前"返回类型是否受支持"由 `ReturnTypeSupport.IsSupported`（生成器 + `MUD002` 共用）单点决定，但：

- **README 诊断表**中的"解决方案"文案与支持集合仍需人工同步（`DocumentationContractTests` 只校验 ID 与级别，不校验能力口径）；
- 无"对同一组类型样本，生成器是否发射占位 == `MUD002` 是否报告"的一致断言；
- `IAsyncEnumerable` 死分支（本次修复）正是"文档 + 分析器都认为支持、生成器实际不支持"的漏网案例，说明这类守卫有实际价值。

### 3.3 任务 1.3：标签分层落地（1 人日）

**判定准则**（写入 `Diagnostics.cs` 顶部注释，供后续新增诊断遵循）：

> `NotConfigurable` 仅用于**使用者无法通过修改自身源码/配置按预期修复的错误**（生成器内部异常、语法损坏、注册阶段内部失败）。
> 凡"使用者改一行代码即可修复"的诊断（参数修饰符、URL 模板、互斥配置、类型名/方法缺失、特性标记缺失等），**不加**该标签，以保证同编译中的分析器诊断（`MUD*`）不被连坐抑制。

## 4. 阶段二：`Task<Stream>` 语义收敛（P0）

### 4.1 决策矩阵

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A｜**实现流式直达返回**（推荐） | 生成器对 `Task<Stream>`/`ValueTask<Stream>` 发射 `SendStreamAsync` 直达调用（与 `HttpResponseMessage` 同构） | 语义正确；复用既有运行期 API（`IBaseHttpClient.SendStreamAsync`）；零反射、AOT 安全；改动局部化 | 新增"自管"语义（不支持 Cache/Resilience/`Response<T>` 包装）；需明确流所有权 | ✅ 推荐 |
| B｜降级为"不支持" | `ReturnTypeSupport` 去掉对 `Task<Stream>` 的支持判定 + `MUD002` 文案去掉 Stream | 最保守；彻底消除"伪支持" | 砍掉文档已承诺的能力；用户如确有 NDJSON/大文件流式需求只能自行实现 | △ 备选 |
| C｜仅文档说明 | 不改代码，README 标注"`Stream` 返回不保证流式语义" | 零改动 | 沉默的运行期失败仍然存在（违反本轮确立的"编译期可见"原则） | ✗ |

### 4.2 任务 2.1：实现 A（1 人日）

**改动点**（参照 `HttpResponseMessage` 直达返回的既有实现）：

1. `MethodGenerator`：新增 `IsStreamType(string)`（同时接受 `Stream`/`System.IO.Stream`，与 [IsHttpResponseMessageType](file:///d:/Repos/MudHttpUtils/Mud.HttpUtils.Generator/Generators/Implementation/MethodGenerator.cs) 同构），并在 `GenerateExecutorCall` 中于 `HttpResponseMessage` 分支旁新增：

## 附录 A：证据复现（本方案 §1.2 / §1.3 的实验手法）

> 手法：新建临时探针工程（`ProjectReference` + `OutputItemType="Analyzer"` 引用 Generator），
> 用"改样例 → 构建 → 统计诊断"的方式做**单变量**对照；每组只改一个变量，其余保持不变。

```powershell
# D1：Error + NotConfigurable → MUD001 不呈现
#     样例：接口含"指针参数方法"（触发 HTTPCLIENT004）+"缺 HTTP 特性方法"（触发 MUD001）
#     预期：仅出现 HTTPCLIENT004/HTTPCLIENT024，无 MUD001
dotnet build .probe/Probe.csproj -c Debug -t:Rebuild

# D2：仅把 HTTPCLIENT004 降为 Warning（其余不动）→ MUD001 恢复呈现
# D3：仅移除 HTTPCLIENT004 的 customTags（仍为 Error）→ MUD001 恢复呈现
# D4：改用未改动的 HTTPCLIENT005（Error + NotConfigurable）→ MUD001 再次不呈现
```

```powershell
# 统计方式（注意：构建输出中各诊断可能出现两次——明细一次、结尾汇总一次）
$c = (dotnet build .probe/Probe.csproj -c Debug -t:Rebuild 2>&1 | Out-String) -replace '\x1b\[[0-9;]*m',''
($c -split "`n") | Where-Object { $_ -match ': (error|warning) ' -and $_ -match '\.probe\\Cases' } |
    ForEach-Object { $t=$_.Trim(); $i=$t.IndexOf('.probe\'); $t.Substring($i) } | Select-Object -Unique
```

**已实测结论（2026-09-14）**：
- `Task<Stream>` 生成 `ExecuteAsync<System.IO.Stream>`（编译通过，运行期失败）；
- 裸 `byte[]`/`Stream`/`HttpResponseMessage` 生成 `return await ...` 于非 `async` 方法体 → `CS4032`；
- `IAsyncEnumerable<string>`（修复前）同样 → `CS4032`（正则匹配限定名永不命中）；
- 存在 `Error + NotConfigurable` 生成器诊断时，`MUD001`/`MUD002` 均不呈现；去掉标签或降为 Warning 即恢复。

## 附录 B：术语

| 术语 | 含义 |
|---|---|
| 占位实现 | 生成器为无法生成的接口成员发射的、成员体抛 `NotSupportedException` 的成员，用于满足接口契约、消除 `CS0535` |
| 返回类型门禁 | `ReturnTypeSupport.IsSupported`：生成器决定"发射真实实现 or 占位实现"、`MUD002` 决定"是否报错"的共享判定 |
| 连坐抑制 | 生成器 `Error + NotConfigurable` 诊断导致同编译分析器诊断（`MUD*`）整体不呈现的现象 |
| 直达返回 | 绕过 `IHttpRequestExecutor`、直接调用客户端原始 API 的返回路径（`HttpResponseMessage` 已有，本方案为 `Stream` 增补） |
